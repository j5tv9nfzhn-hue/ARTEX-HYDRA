# 移动端策略：不做双端 App，做三条通道

> **范围以 `移动端总控台-范围与轮次-2026-10-22.md` 为准**：手机端是一个总控驾驶舱（控制管理 / 消耗面板 / 完整通知 / 进度 / 模型消耗），本文只解决「怎么连上」。
>
> 本文取代 `archive/双端APP-多轮计划-已驳回.md`。
> 前一版把 PC 的页面与功能搬到手机上，属于**冗余设计**——这条判断成立，本文据此重写。

## 1. 为什么不做 App（决策依据）

两类使用者其实都不需要一个新的 App：

| 使用者 | 已有/更短的路径 | App 能额外提供什么 | 结论 |
| --- | --- | --- | --- |
| **有服务器的人** | 公网面板（浏览器直接开），PC/手机同一套 | 只是换个壳 | 把面板做成窄屏可用 + 可安装，比做 App 便宜一个数量级 |
| **只在本机用的人** | 远程桌面（RDP / Parsec / ToDesk / Sunshine+Moonlight）看到完整 PC 界面 | 更小的界面、更少的点击 | 用 IM Bot 指挥即可；重操作交给远程桌面 |

而被省掉的东西是实打实的：双端两套签名与商店审核、iOS 开发者账号、APNs/FCM 证书维护、
每次 PC 侧改 UI 都要重新发版、以及一个永远追不上 Web 的功能子集。

**结论**：mobile 目录存在的意义不是"造 App"，而是**把已存在的能力接到手机上**。

## 2. 三通道

### A. 公网面板（主要通道 · 服务器使用者）

- 现状：`web/` 是 Next.js，构建产物由 Go 内嵌提供（`server/assets.go`），
  所以"远程访问"= 把服务端口经反代/Tunnel 暴露出去 + TLS，页面本身已经是同一套。
- 缺口只有三个：**窄屏可用性**、**可安装（PWA）**、**暴露到公网后的安全加固**。
- 仓库实测：`web/src` 里 tailwind 断点命中 78 个文件，说明并非纯桌面布局，
  但**没有 `manifest.json`**，也无 `apple-mobile-web-app` 相关声明 → 现在只能当网页用，不能"装"。

### B. 远程桌面（辅助通道 · 本机使用者）

- 零开发。要交付的是**一篇手册**：选型（局域网用 Sunshine+Moonlight 延迟最低，
  外出用 Parsec/Todesk）、断电/休眠策略、分辨率与触屏映射、以及"面板与桌面二选一"的取舍。
- 唯一可能要改代码的地方：让 ARTEX 端在无键盘环境下也顺（大按钮、回车类操作可点），
  这属于面板窄屏工作的一部分，不单独开一项。

### C. IM Bot 指挥（主要通道 · 两类使用者通用）

手机上不装 App，在**已有的聊天软件里**发一句话就能指挥 PC/服务器上的 ARTEX。
这条路在 ARTEX 里**已经有一半**了，缺的是另一半：

| 能力 | 现状（实测） | 缺口 |
| --- | --- | --- |
| 出站通知 | ✅ `notify/` 已有 telegram / feishu / dingtalk / wecom / email / webhook / http 七种通道，任务是事件驱动 | — |
| 入站命令 | ❌ 全仓**没有任何** `getUpdates` / `setWebhook` / inbound handler；notify 是纯单向 | **要新增**入站适配器 |
| 会话控制面 | ⚠️ `mcpserver/` 有 Bearer 鉴权（`server/mcp_token.go`，常量 `mcp_server_token`）+ `tools/list` / `tools/call`，但暴露的是 `mcpbuiltin` 的**扫描工具**，没有"列会话 / 拉对话 / 停任务 / 审批"这类控制工具 | **要把控制面 MCP 化**（或提供等价 HTTP） |
| 现成的机器人 | ✅ 用 **OpenClaw** 这类自托管 Gateway（MIT，一个进程接 Telegram/WhatsApp/飞书/Slack 等 20+ 渠道，并自带 macOS/iOS/Android 客户端与 Gateway WS 配对） | 只需让 OpenClaw 能调到 ARTEX |

**关键收益**：手机端的 App 由这类 Gateway 免费提供，我们只把 ARTEX 变成一个可被它调用的工具源。
这也是"三端同步"真正的解法——**状态只存在服务端一份，手机看到的是同一份**，不需要同步协议。

## 3. 轮次（替代原 R0–R5）

| 轮次 | 范围 | 交付物 | 验收（可观测） |
| --- | --- | --- | --- |
| **M1 面板可装可用** | 窄屏适配补齐（会话 / 工具流 / 输入框三个高频页）、PWA manifest + 图标 + 启动画面、无网时的壳 | 前端改动 + `web/public/manifest.webmanifest` | 手机浏览器打开公网面板：能读会话、工具行实时增长、能发一句话；iOS「添加到主屏幕」后有独立图标且全屏无地址栏 |
| **M2 暴露到公网的安全前置** | TLS、登录限速与锁定、会话超时、管理接口二次校验、反向代理信任边界 | 安全清单 + 配置文档 | 未登录访问 `/api/*` 全部 401；爆破 20 次被锁；只有显式配置的 Origin 能过 CORS/WSS |
| **M3 控制面 MCP 化** | 新增只读+受限写的控制工具：`conversation.list` / `conversation.tail` / `conversation.send` / `task.stop` / `approval.decide`；沿用现有 Bearer 与 Tier/allowlist | `mcpserver/` 与 `server/` 改动 + 工具文档 | 用 curl 走 MCP：列出正在跑的会话 → 读到最近 20 条 → 发一句话 → 停任务；越权工具返回拒绝 |
| **M4 入站 Bot 通道** | IM → ARTEX 的入站：优先 Telegram long-poll（无需公网回调），其次飞书事件订阅；命令白名单 + 高危二次确认 + 全量审计 | 新 `bot/`（或 `notify/inbound`）+ 审计表 | 在 Telegram 里发 `/list` 得到会话列表、发 `/stop <id>` 真停、发普通文本进会话；非白名单用户一律静默丢弃并记审计 |
| **M5 通知闭环** | 任务完成 / 需要审批时把卡片推回 IM，卡片带深链（跳面板或直接回一条命令） | notify 模板扩展 + 深链 | 手机上收到审批卡片，点一下即通过，PC 端任务继续跑 |
| **M6 远程桌面手册** | 选型、部署步骤、触屏与分辨率建议、安全建议 | `mobile/docs/远程桌面接入手册.md` | 照手册从零配好，手机能看到并操作完整桌面 |
| **M7（可选，触发式）** | 极薄原生壳：**只做推送 + 深链**，不复制任何功能 | Capacitor 工程 | 仅当 M1 的 PWA 推送在 iOS 上不可用、而 M5 的 IM 卡片又不够时才启动 |

顺序建议：M1 → M2（两者合起来才叫"可远程用"）→ M3 → M4 → M5，M6 随时可插，M7 默认不做。

## 4. 三条通道的边界（防止再次跑偏）

- 不在手机上跑 agent、跑 Bash、跑代理（沙盒与合规都不允许）。
- 不在手机端复制数据模型；手机只做"视图 + 控制面"。
- **不做 PC 功能搬运**，但手机端是完整的**总控台**：控制管理、消耗面板、完整通知（含系统提示）、
  进度展示、模型消耗——五块都要有，不是"只能看一眼"。范围细则见《移动端总控台》。
- 不做自研推送体系，除非 M1/M5 实测不够（那时的形态也是薄壳，不是 App）。
- 任何"顺手把 PC 功能搬上手机"的需求，先问"远程桌面能不能代替"。

## 5. 与调研文档的关系

`Go与移动端适配度调研-2026-10-22.md` 保留价值不变，但用途从"选 App 技术栈"变成
**"否决证据"**：即使将来真要 App，gomobile 也只在需要端侧离线引擎时才局部引入（体积 8.4–35 MB、
不支持泛型与 `any`/`map`/`func`、iOS 必须 macOS 构建、iOS 后台 socket 被挂起）。这些数据让
"用 web + 原生壳"这个结论有据可依，而不是拍脑袋。

## 6. 待定

1. **先做哪条**：M1+M2（面板手机可用）先落地，还是 M3+M4（Bot 指挥）先落地？
   若你日常就是"手机上问一句、让 PC 干"，M3+M4 的价值更直接；若是要在手机上翻记录与长文本，M1 优先。
2. **IM 渠道选哪个**：Telegram（long-poll 最简单、无需公网回调）还是飞书/企业微信（公司内更常见、但要事件订阅与验签）？
3. **是否引入 OpenClaw**：如果你是"用 OpenClaw 指挥"，那 M3 做完即可对接，M4 可以不做（省一个入站适配器）；
   若想 ARTEX 自己就是那个 Bot，M4 必做。
