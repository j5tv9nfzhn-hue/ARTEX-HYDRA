# ARTEX 双端 APP · 多轮计划（草案 v0）

前提结论（见 `Go与移动端适配度调研-2026-10-22.md`）：App 是**远程客户端**，Go 留在服务端；
主线技术栈 = 现有 `web/` + Capacitor 原生壳；同步靠服务端增量接口，不靠手机端跑 agent。

## 1. 目标与非目标

**目标**：Android + iOS 两个 App，能连上「PC 上的 ARTEX」或「云上的 ARTEX」，实时看到会话与工具流、
下发指令、审批高危工具调用；三端（Web / Android / iOS）数据一致。

**非目标（明确不做）**
- 不在手机上执行 agent、跑 Bash、跑流量代理（沙盒与法律都不允许）。
- 不在手机上复制 SQLite 全量数据（只做增量缓存 + 只读投影）。
- 不做手机端常驻后台长连接（iOS 会挂起 socket，见调研 4 节）。

## 2. 总体架构

```
        ┌──────────────┐   ①配对/登录    ┌──────────────────────────────────┐
        │  Android APP │ ──────────────► │ ARTEX 服务端（Go）                │
        │              │                 │  server/：/api/* + /api/stream    │
        │   UI: 复用    │ ◄────────────── │  新增: /api/pair /api/devices     │
        │   web/ 静态包 │  ②WSS 事件流    │        /api/sync?since=<cursor>   │
        ├──────────────┤                 │        /api/push/register         │
        │    iOS APP   │ ◄─────────────► │  agent/：照旧在本机跑             │
        └──────────────┘                 └──────────────────────────────────┘
                 ▲                                     ▲
                 └──────── ③ 可选：Tailscale / 反代 ────┘
```

## 3. 六轮计划

| 轮次 | 范围 | 交付物 | 验收（可观测） | 主要风险 |
| --- | --- | --- | --- | --- |
| **R0 调研与决策**（本轮） | 技术选型、路径对比、协议草案 | `mobile/README.md`、调研文档、本计划 | 选型结论与待验证项清单落库 | 结论是否被后续推翻（用 R1 的 spike 校准） |
| **R1 服务端接入层** | 设备配对、设备令牌、增量同步接口、事件游标 | Go：`server/mobile_*.go` + 测试；OpenAPI 片段 | 用 curl 完成：配对→拿令牌→拉增量→断点续拉；令牌可吊销；越权返回 401/403 | 令牌模型设计过重；与现有 JWT/setup_token 冲突 |
| **R2 只读 MVP** | 会话列表 / 任务详情 / 日志与工具流（实时） | Capacitor 工程 + 复用 web 页面 + 原生壳打包 | 真机安装后：登录→看到 PC 上正在跑的会话→工具行实时增长；断网重连自动补历史 | WebView 与 SSE/WSS 的兼容；证书与自签域名 |
| **R3 指令与推送** | 发消息、停止任务、审批工具调用；APNs/FCM | 原生插件（推送、生物识别）+ Go 推送注册 | 手机上点「停止」→ PC 端任务真的停；后台收到推送并点开定位到对应会话 | iOS 后台唤醒不可靠；推送证书维护成本 |
| **R4 离线与双向同步** | 增量缓存、离线只读、回到前台补拉；冲突策略 | 本地缓存层（SQLite/文件）+ 同步游标 | 飞行模式下能看最近 N 条；恢复网络后无重复无丢失（按事件 ID 幂等） | 若要求"离线可写"，需引入 CRDT → 这时才评估 gomobile |
| **R5 打包与安全加固** | Android AAB / iOS TestFlight、TLS、设备管理页 | 发布流水线 + 设备/令牌管理界面 | 双端可在真机装包；吊销某设备后其立即失效；传输强制 TLS | 应用商店审核（纯网页壳可能触发 4.2 最小功能）；签名与密钥保管 |

## 4. 连通性：手机怎么找到 PC

| 方式 | 适用 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 同局域网直连（mDNS 发现 + 配对码） | 家里/办公室 | 零依赖、低延迟 | 跨网络不可用；企业 Wi-Fi 常隔离 |
| Tailscale / WireGuard 组网 | **推荐主线** | NAT 穿透、每台设备固定 IP、可做 ACL | 需要账号；手机上多一个常驻 VPN 配置 |
| 自建反代（Cloudflare Tunnel / frp + 域名 + TLS） | 长期在外的单人使用 | 无需装 VPN，浏览器与 App 通用 | 把服务暴露到公网 → 必须 TLS + 强制鉴权 + 限速 + 审计 |

不管走哪条，三条硬要求不变：**强制 TLS**、**设备级令牌（可单独吊销）**、**高危操作二次确认**。

## 5. 同步协议草案（R1 要定死）

- 事件流：服务端给每个可同步实体（会话、消息、工具调用、任务状态）一个单调递增 `seq`；
  App 保存 `last_seq`，用 `GET /api/sync?since=<last_seq>&limit=500` 拉增量，返回 `{items[], next_seq, has_more}`。
- 幂等：所有写操作带客户端生成的 `op_id`，服务端按 `op_id` 去重（重试安全）。
- 删除：用墓碑记录（`deleted_at`）随增量下发，避免"删了又回来"。
- 顺序：以 `seq` 为准，不依赖客户端时间；客户端时钟只用于展示。
- 游标存储：App 侧「每设备一行」，服务端不下发全局游标（多设备各自推进）。

## 6. 与现有代码的关系

- 复用：`web/` 的页面与 API 客户端；`server/` 的鉴权中间件；`db/` 的实体（只读投影）。
- 新增：`server/` 下的移动端接入层（配对/设备/同步/推送），以及 App 壳工程（R2）。
- 不动：`agent/`、`selfupdate/`、`cmd/artex/`（除必要的启动参数与日志以外）。

## 7. 每轮结束的固定动作

1. 更新本目录文档与 `CHANGELOG.md` 的 Unreleased；
2. 一个语义一个中文提交（移动端与服务端改动分开提交）；
3. 记录本轮的「已验证 / 未验证」，未验证项写进下一轮的验收里，不留"应该没问题"。

## 8. 待你定的三件事（影响 R1 之后的所有设计）

1. **主线路线**：确认走 A（web + 原生壳），还是要我先做个 B（Flutter）的对比 spike？
2. **连通方式**：先做局域网直连（最快见效），还是一上来就 Tailscale 组网？
3. **是否需要离线可写**：只读够用，还是要在手机上新建任务/改配置？（决定 R4 是否引入 CRDT）
