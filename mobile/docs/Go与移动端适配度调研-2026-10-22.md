# Go 与 Android / iOS 的适配度调研（面向 ARTEX 双端 APP）

> **用途变更（2026-10-22）**：双端 App 方案已驳回（见 `移动端策略-三通道-2026-10-22.md`）。
> 本文保留为**否决证据**与"若将来真要 App"的技术底座：体积、类型限制、构建前提、iOS 后台限制都在这里。


调研时间：2026-10-22 · 结论先行 · 所有数字与限制均可复核（见第 10 节来源）

## 0. TL;DR

1. **Go 能上手机，但只能当「被调用的库」，当不了 UI 框架。** 官方工具是 `gomobile bind`：Android 产出
   `.aar`，Apple 产出 `.xcframework`；UI 仍然是 Kotlin/Java 与 Swift。
2. **跨语言边界的能力被严重裁剪**：只支持有符号整数、浮点、`string`、`bool`、`[]byte`、由这些组成的
   结构体/接口；**泛型、`any`、`map`、非字节切片、可变参数、`func` 回调一律不支持或静默跳过**，panic
   跨边界会直接把 App 打死。
3. **体积不小**：一个"几乎空的"库，Android `arm64` 的 `libgojni.so` 约 3.7–4.1 MB、四架构 AAR 约 8 MB；
   真实的同步/网络库可以到 27 MB（AAR 压缩后 9 MB）；iOS 静态 framework 15–37 MB，链进 App 前还要算。
4. **构建 iOS 必须有 macOS + Xcode**，Windows 上无法产出 iOS 产物；Android 需要 NDK，且 NDK 27 起
   **必须 `-androidapi 21`**（默认 16 会直接报 unsupported API version）。
5. **对 ARTEX 这件事，gomobile 不是关键路径**：ARTEX 的 agent 依赖 Bash/工具链、工作目录、SQLite、
   本地 CA 与流量代理，手机上跑不了也不该跑。手机 App 的角色是**远程客户端**，用 HTTP/WSS 说话即可。
6. **推荐把 Go 留在服务端**，App 走「复用 web 前端 + 原生壳」（路线 A）；只有当手机上真的需要
   离线协议栈/隧道/增量合并引擎时，才引入 gomobile（路线 C）。

## 1. gomobile 能做什么、怎么产出

| 命令 | 产出 | 说明 |
| --- | --- | --- |
| `gomobile bind -target=android` | `*.aar`（Java 存根 + `jni/<abi>/libgojni.so` + assets） | 可直接被 Android Studio 当模块导入 |
| `gomobile bind -target=ios` | `.xcframework`（device arm64 + simulator 切片） | **必须在 macOS + Xcode 上跑** |
| `gomobile build -target=android\|ios\|iossimulator\|macos\|maccatalyst` | APK / App | 纯 Go 的 `main` 包才能用；本项目用不上 |

默认 `-target=android` 会打齐全架构（arm/arm64/386/amd64），可以用 `-target=android/arm64` 只保一档。

## 2. 能力边界（这是最容易低估的一条）

`gobind` 官方文档写明的可导出类型只有：有符号整数、浮点、`string`、`bool`、`[]byte`（按引用传递、
可原地修改）、参数/返回都满足约束的函数类型、方法都满足约束的接口、字段都满足约束的结构体。

现实中的坑（社区实证）：

- `any` / `map[K]V` / `chan T` / `func(...)` 作为参数会被**静默跳过**——不报错，生成了没有该方法的类型。
- **泛型会让 bind 这一步直接失败**（不是警告）。
- 导出非字节切片（如 `[]string`、`[]any`）同样不受支持。
- 回调只能以**接口**形式跨边界（Swift/Kotlin 实现接口传进去），`func` 值不行。
- 异常/panic 跨语言边界**不支持**：一旦穿过去，进程直接退出。

对 ARTEX 的直接含义：现有 Go 代码里大量 `map[string]any`、`any`、泛型、`func` 回调（工具定义、
事件回调、SSE 通道），要复用就必须写一层"bind 安全"的门面（只收发 `string`/`[]byte`/`int64`/`error`），
等于把协议再序列化一遍——而这一步用 HTTP + JSON/Protobuf 做，成本更低、还能被 Web 端复用。

## 3. 体积与构建链成本

| 场景 | 实测/报告数字 |
| --- | --- |
| 极小库（四个 ABI） | AAR ≈ 8.4 MB；单架构 `libgojni.so` ≈ 3.7–4.1 MB |
| 同步/网络类真实库 | Android arm64 `.so` 27.4 MB（AAR 压缩后 9.3 MB）；iOS arm64 静态 framework 35 MB |
| 老案例 | iOS framework 37 MB vs Android AAR 1.7–7 MB |
| 构建耗时 | `gomobile bind` 单次 10 秒–数分钟不等（与包体积、ABI 数量强相关） |

App 体积不是唯一代价：**每加一个 Go 依赖，iOS 的静态链接时间与内存基线都会涨**；而 App Store 上
用户对体积很敏感。相反，纯 HTTP 客户端方案的增量几乎为零（甚至能复用现有的 Next.js 静态包）。

## 4. 平台侧的硬约束与历史坑

- **iOS 必须 macOS 构建**：团队里若没有 Mac，就得用 GitHub Actions 的 `macos-*` runner，或云 Mac。
- **Xcode 15.3+ 曾出现 gomobile 产出的 xcframework 无法用于真机归档/发布**（#66500，后有修复路径），
  说明这条链路随 Xcode 版本漂移，需要持续跟进。
- 更早还有 **Apple 因二进制里带 `_ptrace`（私有 API）拒审**、以及 bitcode 相关的历史问题（bitcode 现已废弃）。
- **Android NDK 27 起不再支持 API < 21**：不带 `-androidapi 21` 会报
  `unsupported API version 16 (not in 19..33)`。
- **iOS 后台限制**：App 进入后台后监听 socket 会被挂起，只能靠有限的后台唤醒（在充电时大约每小时 5 分钟）
  或推送唤醒。Syncthing 的 iOS 客户端作者明确说这是系统限制、无法绕过。
  → 任何"手机端常驻长连接做实时同步"的设计在 iOS 上都不成立，必须改成"前台实时 + 推送唤醒 + 打开时拉增量"。

## 5. 成功先例（说明"能做"和"值得做"是两件事）

- **Tailscale**：Go 核心 + gomobile 桥接，UI 从早期的 Gio（纯 Go UI）改回**原生界面**；官方说集成 gomobile
  "简化了 Go 后端与 Android 平台之间的接口"。也就是说：即便是最硬核的 Go 团队，最终也是"Go 做内核 + 原生做 UI"。
- **Syncthing 生态**：`syncup` 把 Syncthing daemon 通过 gomobile 跑在 App 进程内，UI 用 React Native。
  他们的驱动因素是"必须在设备上跑完整 P2P 同步引擎"——这正是 ARTEX 不需要的东西。

## 6. 与 ARTEX 的匹配度评估

| ARTEX 需要的能力 | 手机上跑 Go 内核能否提供 | 说明 |
| --- | --- | --- |
| 执行 Bash/工具、读写工作目录 | ❌ | iOS 沙盒根本无法执行任意二进制；Android 也只能跑打包进去的代码 |
| 本地 SQLite（10+ 张表、agent 状态机） | ⚠️ 能跑但没意义 | 与 PC 端数据一致性反而变成新问题 |
| 本地 CA / mitmproxy 流量代理 | ❌ | 需要系统级证书与端口，移动端不成立（且有合规风险） |
| 实时看会话/工具流 | ✅ 但用 WSS 更简单 | 现有服务端已有 SSE/WSS 接口 |
| 下发指令、审批工具调用 | ✅ 但用 REST 更简单 | 无需跨语言绑定 |
| 离线缓存 + 增量同步 | ⚠️ | 若真要做 CRDT/合并引擎，Go 有优势（但也只有这一块） |

**结论：把 agent 搬上手机的性价比极低；App 应该是薄客户端。** Go 的价值集中在服务端，以及
（可选的）"服务端与 App 共用的协议/校验代码"——而后者用 OpenAPI/JSON Schema 生成客户端更省事。

## 7. 三种路线对比

| 维度 | A. web 前端 + 原生壳（Capacitor/WebView） | B. Flutter / React Native | C. Go 核心 + gomobile + 原生 UI |
| --- | --- | --- | --- |
| 首版速度 | ★★★★★（几乎复用现有 `web/`） | ★★★ | ★ |
| 三端 UI 一致性 | ★★★★★ | ★★★ | ★★ |
| 原生体验/性能 | ★★ | ★★★★ | ★★★★★ |
| 后台任务/推送 | ★★（需原生插件） | ★★★★ | ★★★★ |
| 构建链复杂度 | ★★（一次配好） | ★★★ | ★★★★★（macOS + NDK + 版本漂移） |
| 体积增量 | ★★★★★（≈0） | ★★ | ★ |
| 与 Go 代码复用 | 无需复用（走 API） | 无需复用（走 API） | 高（但受类型限制） |
| 适合的 ARTEX 阶段 | **MVP 与长期主力** | 需要原生感时 | 手机端要跑离线引擎时 |

## 8. 推荐

1. **主线走 A**：把 `web/` 的 Next.js 导出为静态站，用 Capacitor 包成 Android/iOS 壳；新增的原生能力
   （推送、生物识别解锁、剪贴板、扫码配对）通过插件补。这样"三端"（Web/Android/iOS）共享同一套 UI 与 API。
2. **API 层在 Go 里加**：设备配对、设备令牌、增量同步（`/api/sync?since=<cursor>`）、推送注册。
   这些是纯服务端工作，不涉及 gomobile。
3. **仅在 R4 之后、且确有离线需求时**，再评估把"同步合并/加密"这一小块做成 gomobile 库——即路线 C
   的局部使用，而不是把整个 agent 塞进去。
4. 若后续发现 App Store 审核因"纯网页壳"被 4.2 条款挑战，再补原生功能（推送、离线、Widget），
   而不是此时就选 B/C 承担成本。

## 9. 待验证的问题（R0/R1 要闭环）

- [ ] Android 最低支持版本定多少？（NDK 27 起 API 21 是地板；企事业设备可能更老）
- [ ] iOS 最低版本？（gomobile 默认 13.0；Capacitor 目前要求 13/14+）
- [ ] 手机与 PC 的连接方式优先级：同局域网直连 / Tailscale 组网 / 自建反代（见轮次计划第 4 节）
- [ ] 是否需要离线可写？（决定 R4 是否引入 CRDT，以及是否值得上 gomobile）
- [ ] 推送通道：APNs + FCM 都需要证书与账号，谁维护？
