# AI 聚合中转站业务逻辑审计（ai-gateway-logic）

AI 中转站（LLM API 聚合网关）的**表面漏洞极少**：登录页、参数校验、WAF 通常都做得不错。真正的风险集中在**登录之后**的资金与权限链路——计费、余额、API Key 生命周期、租户归属、支付回调。

传统扫描器对这类目标系统性失效：OWASP 明确指出业务逻辑缺陷"没有输入净化或输出转义的特征"，扫描器因缺乏业务规则而无从判定。本 skill 提供的是**业务不变量清单**，不是 PoC 集合。

---

## 边界（Agent 必读）

| 允许 | 禁止 |
|---|---|
| 在**已授权**目标上验证下列不变量 | 对未授权目标执行任何验证 |
| 使用自有账号/测试租户构造最小验证 | 使用真实用户凭据、真实支付渠道 |
| 记录"不变量被违反"的可观测证据 | 实际造成资金损失、批量注册、薅取真实额度 |
| 判定为"配置缺失"或"需人工确认" | 把配置缺失直接写成"高危漏洞" |

**证伪纪律**：未配置定价的模型零成本放行 ≠ 漏洞已利用成功。必须区分「运营配置缺失」「预期行为」「可恶意利用的绕过」三种结论。只观测到一次异常不足以定论，需给出最小复现路径。

## 一、目标识别指纹

先确认目标类型，再选用对应不变量集。

| 指纹 | 指向 |
|---|---|
| `/api/status` 返回 `{"data":{"version":...,"start_time":...,"system_name":...}}` | NewAPI / OneAPI 系 |
| `/api/setup` 存在且返回 `root_init` 字段 | NewAPI（注意该字段可能误导，不代表已初始化） |
| `/v1/models` + `/pricing` 或 `/api/pricing` | 通用中转站 |
| 前端 React SPA + `/static/js/index.<hash>.js` | NewAPI 前端，从 bundle 提取 `/api/*` 候选路由 |
| `/ui/`、`/sso/key/generate`、`/key/list` | LiteLLM Proxy |
| `/api/v1/auth/login`、Redis 余额键、`API_KEY_NOT_FOUND` 日志 | sub2api 类实现 |
| 响应含 `quota`、`remain_quota`、`used_quota`、`token_name` | 计费型网关 |

**侦察顺序**：`/api/status` → `/api/setup` → `/v1/models` → 前端 bundle 路由提取 → 登录后 `/api/user/self` → 计费相关端点。

## 二、核心不变量（逐条验证，禁止跳跃）

每条不变量给出：**断言**、**违反时的可观测信号**、**最小验证序列**。

### INV-01 结算与鉴权解耦

**断言**：请求准入时快照用户/配额上下文；结算阶段不得依赖「API Key 仍然存在」。

**违反信号**：日志出现 `API_KEY_NOT_FOUND`、`record_usage_failed`、`quota_not_found`，且该请求已正常返回内容。

**验证序列**：`http_sequence(overlap=true)`
1. 发起一个**流式**长响应请求（选择输出 token 多的模型）。
2. 在响应未结束时（`delay_ms` 取实测响应耗时的 50%~80%）发送删除该 Key 的请求。
3. 等待首个请求完成，比对：响应是否完整返回 + 账单是否新增该笔消耗。

**判定**：请求返回成功但账单无记录 → 违反。仅 Key 删除失败 → 不可判定。

---

### INV-02 定价缺失必须 fail-closed

**断言**：计费路径遇到「该模型无定价配置」时，必须拒绝请求或挂账告警，不得零成本放行。

**违反信号**：`pricing_missing_record_zero_cost`、`price_not_found` 且请求成功、账单金额为 0。

**验证序列**：请求一个 `/v1/models` 列出但 `/pricing` 未覆盖的模型，比对账单。

**判定**：需区分「运营未配置」（配置问题，可提示）与「配置了但被绕过」（逻辑问题）。

---

### INV-03 计费数值必须溢出安全

**断言**：所有参与计费的用户可控数值（`n`、`max_tokens`、`audio duration`、图片数量）必须有上界，且参与乘法前做溢出检查。

**违反信号**：超大 `max_tokens` 或 `n` 导致余额**增加**（负扣费翻转）、账单出现负数、余额超过充值总额。

**验证序列**：在自有账号上用极小余额，提交边界值（`n=2^31-1`、`max_tokens` 极大值），观察余额与账单变化。**不要**在真实付费账户上执行。

**判定**：余额增加或出现负费用 → 违反。返回 400/422 → 已防护。

---

### INV-04 余额唯一事实源是数据库

**断言**：余额以 DB 为唯一真值；缓存只能读穿透或写失效，不得整体回写快照。

**违反信号**：并发扣费后余额「回弹」；`PUT /api/user/self` 类接口保存后余额恢复旧值。

**验证序列**：
1. 记录当前余额。
2. 发起 N 个并发小请求（`http_sequence` 并发模式）。
3. 等待全部完成后立即调用一次「更新用户资料」接口（只改昵称等无关字段）。
4. 再次读取余额。

**判定**：余额高于「初始 - 实际消耗」→ 快照覆盖了扣费，违反。

---

### INV-05 负余额/负费用是非法状态

**断言**：余额不得小于 0（或不得低于配置的透支下限）；任何账单金额不得为负。

**验证**：所有涉及数值的用例执行后统一检查该后置条件。

---

### INV-06 Key 状态变更即时生效

**断言**：删除/禁用 Key 后，鉴权缓存必须在有界时间（建议 ≤1s）内失效；在途请求的语义需明确定义（要么允许完成并计费，要么拒绝）。

**违反信号**：删除后仍可用该 Key 成功请求；或请求成功但未计费（与 INV-01 交叉）。

**验证序列**：删除 Key → 立即用旧 Key 请求 → 记录结果；等待 5s 再请求一次。

**判定**：5s 后仍可成功 → 鉴权缓存未失效。

---

### INV-07 租户归属必须强制 scoped

**断言**：所有带 `user_id` / `team_id` / `org_id` / `key_id` 的查询，必须强制限定为鉴权主体的可访问范围，不得信任客户端传入的 ID。

**违反信号**：低权 Key 可读取他人消费记录、Key 列表、完整 Key 对象（`return_full_object=true`）。

**验证序列**：用 A 租户的低权 Key，请求带 B 租户 ID 的查询接口。**只在自有双租户测试环境执行**。

**判定**：返回非空他人数据 → 违反。返回 403/404/空 → 已防护。

---

### INV-08 支付回调必须完整验签

**断言**：回调验签必须满足：签名密钥非空、签名算法正确、订单状态前置校验（pending → paid）、金额与订单一致、幂等（重复回调不重复入账）。

**违反信号**：密钥为空时验签通过；重复回调导致重复充值；金额可篡改。

**验证序列**（仅在自有测试商户号下）：
1. 检查配置中签名密钥是否为空（管理面可读则读，否则观察日志）。
2. 用错误签名提交回调 → 应拒绝。
3. 用正确签名重复提交同一事件 → 应幂等。

**判定**：空密钥下伪造事件被接受 → 严重违反。**禁止**在真实支付渠道上测试。

---

### INV-09 本地信任不得来自客户端 Header

**断言**：判断请求是否来自本地，必须基于 socket peer 地址，不得信任 `Host`、`X-Forwarded-For`、`X-Real-IP`。

**验证序列**：向目标发送带 `Host: localhost` 的未鉴权请求，观察是否绕过。

**判定**：未鉴权请求被当成本地请求放行 → 违反（开放中继风险）。

---

### INV-10 管理面必须做角色层级校验

**断言**：管理 API 必须比较操作者与被操作者的角色层级；敏感字段（`access_token`、`secret`、`password_hash`）永不回显。

**验证序列**：用普通管理员账号访问用户列表/重置密码/提权接口，检查：① 是否可操作同级或上级；② 响应是否含敏感字段。

**判定**：可操作上级 或 响应含明文 token → 违反。

---

### INV-11 促销与注册滥用防护

**断言**：免费额度、邀请返利、优惠券兑换需有：设备/IP/支付前置、单账号上限、关联图检测。

**验证**：仅在自有环境构造 2~3 个测试账号验证上限是否生效。**禁止**批量注册真实服务。

## 四、输出要求

每个不变量给出结构化结论，禁止含糊：

```
INV-XX <名称>
  状态: 满足 | 违反 | 不可判定 | 已防护
  证据: <请求/响应摘要 + 账单前后快照>
  最小复现: <步骤>
  影响: <资金/数据/权限>
  置信度: confirmed | inferred
```

- **不可判定**是合法结论。缺证据时必须用它，不得为了"有产出"而升级为违反。
- 「配置缺失」不得写成「漏洞」。写成 `需人工确认：运营配置`。
- 任何涉及真实资金的验证，先确认环境为测试商户/测试额度。

## 五、止损

以下情况立即停止该类验证并切换方向：

1. 连续 3 次相同响应（400/403/422）→ 该方法在当前目标上无效，记录后转向。
2. 验证可能影响真实用户资金 → 立即停止，改为静态配置审计。
3. 目标无测试租户/测试额度 → 只做只读审计（`/api/status`、`/pricing`、前端 bundle），不做写操作。
4. 检测到目标有异常监控告警（响应突然全部 429/403）→ 停止，记录已观测状态。

## 六、参考缺陷模式（真实案例，仅作模式识别）

以下均为**已公开且多已修复**的案例，价值在于理解断裂点位置，不是可直接使用的 PoC：

| 模式 | 断裂点 |
|---|---|
| 支付回调空密钥验签通过 | 验签函数未校验密钥非空 |
| 流式请求中删 Key 导致结算静默跳过 | 结算依赖「Key 仍存在」 |
| 无定价模型零成本放行 | 计费路径 fail-open |
| `max_tokens`/`n` 整数溢出翻转负扣费 | 未做上界与溢出检查 |
| 用户资料写回覆盖 Redis 余额 | 快照整体回写缓存 |
| 软删除后鉴权缓存未失效 | 状态变更未联动缓存 |
| `Host: localhost` 绕过鉴权 | 信任客户端 Header |
| 用户列表 API 回显 root token | 敏感字段未过滤 |
| 跨租户 `user_id` 无归属校验 | 查询未 scoped |

**重要**：遇到与上表相似的现象，先核对版本与配置，再判断是否构成可恶意利用的缺陷。现代版本多数已修补，直接照搬结论会产生误报。
