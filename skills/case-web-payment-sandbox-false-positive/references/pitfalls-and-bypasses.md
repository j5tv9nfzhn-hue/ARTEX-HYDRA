## 1. 本案最重要的一课：支付沙盒 ≠ 越权漏洞

### 1.1 现象与它为什么"诱人"

原报告把它写成一条 **[MEDIUM] 漏洞**：

> `staging-api.overchat.ai` 的 `POST /v1/billing/buy-subscription` 在返回 Stripe【测试模式】结算会话后、未收到任何支付确认的情况下，
> 就直接把订阅行改写为激活态（`planCode=apple_pay_test_1`、`status=3`、`stripeId=sub_1USaPbGWUebql6H99HbSZLPb`、
> `paidThroughPeriodEnd=+7天`、`hasEverSubscribed=true`），而同一会话 `GET /v1/billing/stripe-session` 明确回显
> `payment_status="unpaid"`、随后的 `POST /v1/billing/checkout/sync-package` 也判定 `session_not_paid` 且不回滚权益
> ⇒ 付费权益在结算确认之前即已发放（INV-01 结算与鉴权/发放解耦、INV-08 支付确认未与权益发放绑定），403 付费权益层随之被打开。

它诱人，是因为它**逐条命中**了经典漏洞模板：
- 教科书级不变量破坏：`结算 ↔ 权益发放` 解耦；
- 有完整的"前后快照"：`status=0 → status=3`、`paidThroughPeriodEnd=+7天`；
- 有可观测的**能力提升**：403 付费权益层被打开，后续端点从 403 变成 201；
- 有"可复现"的样子：一条固定的请求序列；
- 甚至能挂上不变量编号（INV-01 / INV-08），看起来**很专业**。

### 1.2 掉坑的五层机制（逐层剥）

**第 1 层：把真钱链路的状态语义套到了测试链路上。**
`payment_status="unpaid"` + `session_not_paid` 这两个信号只有在**存在"真实支付确认"事件**的通道里才有意义。
测试通道（`cs_test_`）永远不会产生支付确认事件，因此这两个返回值在该链路上是**常量**，不是异常。
> **通则**：**"状态机矛盾"只有在矛盾的两端属于同一条真实业务链路时才是缺陷。** 跨链路比对状态字段，是误报的第一大来源。

**第 2 层：测试 SKU 发放的是"假权益"。**
`planCode=apple_pay_test_1` 是测试夹具。它带来的 +7 天 `paidThroughPeriodEnd` 不对应任何真实金额、真实上游算力、真实可交付资源。
把它当成"高级套餐"来评估影响，等于给一张**没有面额的储值卡**估了价。

**第 3 层：预发环境把"影响面"抹平了。**
`staging-api.overchat.ai` 上没有真实用户、没有真实收入、没有真实履约。它的 403 → 201 变化不产生任何业务损失。
于是"影响面"一栏是空的，**一条没有受害方的缺陷不构成漏洞**，最多是运维噪声。

**第 4 层：杠杆心理放大。**
这个发现恰好"打开了 403 付费权益层"，直接服务于任务主线（取上游 provider base_url 与明文 api_key）。
**有用的发现会被不自觉地当成成立的发现。** 定级必须先于用途。
> **通则**：**"帮我打开了下一扇门"是用途，不是证据。** 任何发现的成立性判定，都要在它被当作杠杆**之前**完成。

**第 5 层：结论被下游继承，污染扩散。**
原报告随后写下：

> 【重要纠偏·假阴性推翻】finding #133（staging `POST /v1/billing/buy-subscription` 未收支付确认即激活订阅）已经打开了 403 付费权益层。
> 此前意图 1757/1780/1814 给出的『错误回显已彻底净化』『上游面被 403 门禁挡住』等结论是在【付费层未开】时取得的，属假阴性：
> 在已激活订阅（planCode=apple_pay_test_1、status=3、+7天）的 staging 会话上，付费 persona 的 `/v1/chat/completions`
> 现在会真正把请求打进上游调用层，届时错误对象/响应头里的 base URL、Authorization、x-request-id、上游 provider 信息才可能被观测到。

这段把**沙盒开关**当成了**上游情报的门禁**：一整串"上游回显能否被观测到"的推理，建立在一个测试权益上。
更危险的是它还顺手把一批**当时正确**的结论（"付费层未开时被 403 挡住"）标成了"假阴性"——**如果那个开关本身是沙盒，那么 403 才是生产真实行为，被推翻的其实是这条错误结论。**
> **通则**：**发现被降级/撤回时，其下游结论默认作废，必须逐条重验；反过来，"假阴性推翻"同样需要先验证它推翻的对象是不是真的假阴性。**

- 若 G1–G3 全不命中（生产 + live + 真实 SKU）⇒ 才进入真·支付绕过论证，仍需满足 G4。

| 条目 | 现象 | 环境 / 成本归属 / 受害方 | 判定 |
| --- | --- | --- | --- |
| 被撤回的 staging `apple_pay_test_1` | 零支付拿到付费权益 | 预发 / 假钱 / 无受害方 | **误报** |
| 生产 `POST /v1/prompt/enhance` | 未订阅（`planCode=free`、`hasEverSubscribed=false`）、未计费（余额与负债无变化）的游客即得真实上游模型输出 | **生产 / 真上游算力 / 站方承担成本** | **真 MEDIUM**（付费门禁覆盖不全） |

> **结论**：同一套"免费访问"外形，判定完全取决于**环境 + 成本归属 + 受害方**。
> **不要因为一次误报就学会"支付类都别信"，也不要因为"免费"就放过生产链路上的免费算力。**

### 1.6 杠杆污染：机制与处理

**机制**：发现 F 被用作杠杆 → 派生出结论 C1、C2、C3…→ F 被降级/撤回 → C1、C2、C3 失去前提但仍留在报告里 → 读者（或后续 agent）把它们当作已验证事实使用。
**本案的实际扩散路径**：`F（沙盒权益）` → `403 付费层已开` → `付费 persona 可触达上游调用层` → `上游错误回显/响应头可能被观测到` → `此前"错误回显已彻底净化"的结论被标为假阴性`。
**处理纪律**：
1. 建立**依赖登记**：凡基于某发现得出的结论，在笔记里显式写"依赖 F"。
2. F 被降级/撤回 ⇒ **默认把依赖 F 的结论全部标记为"待重验"**，而不是只删 F。
3. 写进报告的"纠偏"段落必须自带**前提自检**："这个开关本身是否成立？"——本案缺的正是这一句。
4. **反向纪律**：用杠杆之前先定级；用杠杆之后保留依赖标记，别让"我靠它拿到的结果"倒过来替它背书。

### 1.7 降级留证写法（不要删，要留痕）

```

生产前端确认为 Stripe live 模式、无测试模式可复刻（G5）

```

## 2. 本案其余高频踩坑（与支付误报同源，通用性同样强）

### 2.1 未鉴权 ≠ 越权：先做「部署差分」再定性
- 现象：`widget-api.overchat.ai` 的 `/v1/users`、`/v1/chats`、`/v1/personas/paginated`、`/v1/canvas`、`/v1/dashboards` 匿名 200，而**同名同路径**在 `api.amigochat.io` 已加固为 401。
- 结论：**鉴权守卫是按部署逐个加的，存在漏配部署** ⇒ 这是真缺陷（生产某部署漏配），但结论要写成"**某部署漏配**"，而不是"全站越权"。
- **手法**：拿到匿名 200 后，**去另一个同名部署上打同一个路径**。差分结果决定严重等级与归因。
- 反面：`staging-api.overchat.ai` 的 `/v1/auth/google/mock` 在生产 `api.overchat.ai` / `widget-api.overchat.ai` 均 404 ⇒ 影响面限预发，**归类为"预发环境暴露"**，不是"生产认证绕过"。

### 2.2 mock / 调试端点：定域比"能不能用"更重要
- `POST /v1/auth/google/mock` 免鉴权，隐藏字段 `code` 按 `<code>@overchat.ai` 反查用户库（`code=demo` → `demo@overchat.ai`，`code=admin` → `admin@overchat.ai`）⇒ 可签发既有账号的有效 HS256 JWT。
- **定域三问**：① 生产有无此路径（404 ⇒ 限预发）；② 预发签发的 token 能否在生产复用（需**实测**，别假设）；③ 预发是否连真实上游/真实数据（连 ⇒ 另立"预发暴露真成本"一条）。
- 报告里"该路由在生产均不存在（404），影响面限于预发环境"这类**显式定域句**是必须的，别丢。

### 2.3 客户端头当凭据（这才是真问题，别和支付沙盒混为一谈）
- `widget-api.overchat.ai` 把请求头 `x-device-uuid` 当**唯一身份凭据**：不带该头 401；带**任意** deviceId 即返回该账号完整档案（含 `stripeCustomerId`、`takosCoin` 余额、订阅对象）。实测三个不同受害者 deviceId 换回三个不同账号 ⇒ 服务端按 deviceId 精确解析身份。
- 之所以是真漏洞：**凭据完全由客户端提供、可任意伪造** ⇒ 等同于无鉴权；且受害方是**他人**。
- 与支付沙盒的差别，正是 G4「受害方」这一项。

### 2.4 预签名端点：host 忽略 + path 当 key ⇒ 存在性预言机
- `GET /v1/s3/download?url=<URL>` 零鉴权，用站点自有 AWS 凭据签发 3600 秒有效的 SigV4 GetObject 预签名 URL。
- **关键工程细节**：该接口**忽略输入 URL 的 host**、把站点自有桶写回，**只把 path 当作 S3 key 签名** ⇒ 传入 `url=http://127.0.0.1:3000/v1/model-cost`，签出的 key 就是 `v1/model-cost`。
- **预言机语义**：签名有效但 key 不存在 → S3 返回 `404 NoSuchKey`；key 存在且该凭据可读 → `200` + 真实字节 ⇒ **精确的对象存在性 oracle**，可枚举私有对象命名空间。
- 附带：预签名 URL 的 `X-Amz-Credential` 会**泄露站点 AWS Access Key ID**（`AKIA…`，prod 与 staging 共用同一 ID）。
- 定级注意：本条是**真漏洞**（零鉴权 + 可读非公开对象 + 存在性 oracle），与 §1 的支付沙盒误报性质完全不同 —— 判据同样是 G1–G4：生产 ✓、无鉴权 ✓、真实对象 ✓、可规模化 ✓。

### 2.5 假阴性外推：门禁未开时的 403 结论不可外推
- 反向教训：若某个门禁（订阅、配额、鉴权）当时是关的，**"打不开"不能推出"打不开"是产品的有意设计"**；也不能推出"一旦打开就能看到上游信息"。
- 正确做法：把"当前被挡"与"打开后会发生什么"**分成两条待验证命题**，不要合并。
- 更深的坑（本案的翻车点）：**当"打开门禁"的手段本身是沙盒时，"打开后会发生什么"根本无从验证** —— 你打开的是假门。所以**先定级杠杆，再用杠杆**。

### 2.6 "测试模式"这三个字要查它的落点
- 看到 `testMode` / `cs_test_` / `pk_test_` / `sandbox` 时，**不要立刻判为"正常"或"缺陷"**，先问：它在**哪个环境**、**哪条链路**、**哪个 SKU**上？
- 生产残留 testMode（civpn）= 漏洞；预发 testMode（本案）= 沙盒。**同一个词，两个结论。**

### 2.7 预发可达真上游时，结论要换但级别不降
- 若预发环境的 mock / 测试套餐能**打到真实上游**并消耗站方真实额度，那是另一条真问题（"预发环境消耗生产成本 / 预发可直接取上游响应"），应单独成条并给出真实成本证据，而不是继续说"支付绕过"。

## 3. 3-Strike 止损矩阵

| 场景 | Strike 1 | Strike 2 | Strike 3（止损） |
| --- | --- | --- | --- |
| 疑似支付绕过 | 查生产同名端点通道模式（live/test） | 查 SKU 是否测试件 / 价目表是否收录 | 仍指向沙盒 ⇒ 判误报、降级留证、**停** |
| 疑似"未鉴权即越权" | 换另一个同名部署打同一路径做差分 | 查该凭据是否客户端可控（头/参数/空值） | 仍为部署级漏配 ⇒ 归因到具体部署，**停** |
| 疑似上游凭据泄露 | 找错误回显 / 指标 / 配置端点 | 换部署、换模型、换错误触发方式 | 仍无回显 ⇒ 换方向，**停** |
| 疑似 SSRF / LFI | 换 payload 形态（编码/绝对 URL/参数污染） | 换端点（同一后端不同路由） | 连续 3 次同形态无回显 ⇒ 换方向，**停** |
| 连续 3 次相同错误响应/固定状态码 | — | — | **必须停**，不得在同一形态上重试 |
| 工具报错（`http_request` / `Grep` / `extract_data`） | 核对参数、授权、网络、目标状态码 | 换等价工具 | **不要原样重试** |

> **本案额外一条**：**沙盒性质一旦成立，扩大规模不会改变性质，只会让误报更可信。** 禁止为"让报告更饱满"去重复验证、找生产复刻路径或把下游结论往上搭。

## 4. 取证边界（复盘也必须守）

- 本案全程以**只读**为主；对他人账号仅取 2–3 个非自己样本，控制数据面。
