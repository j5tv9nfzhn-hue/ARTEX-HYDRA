# 控制台后端 AI 工具调用稳定性：三端差异定位与本机错误修复

> 范围：`agent/`（工具边界与原生工具）+ `server/`（工具目录同步）。**未改动 HARNESS**。

## 一、结论摘要

| # | 结论 | 证据强度 |
|---|---|---|
| 1 | **同一份代码在不同机器上会给模型看不同的"工具说明书"** —— 内置工具的 Description/JSON Schema 首次 seed 后永不更新，是本机 4% 与三端 50%+ 之间唯一能解释"同码不同行为"的结构性机制 | 机制已读透 + 本机实测 7/75 漂移 |
| 2 | 本机 20 条工具错误里，**60% 是"信息不足导致的盲目重试"**（漏必填 6 + 路径不存在 5 + 类型不符 2 中可自愈的部分），不是模型能力问题 | 逐条错误原文 |
| 3 | 弱模型是**放大器**而非根因：同一台机器上 `oc/deepseek-v4.1-flash-free` 3.2% vs `minimax-m3.1-flash:free` 0.7% | llm_usage 27,546 行交叉统计 |
| 4 | 本机 3.77% 的错误率里，有 1 条是 `tool_steering` 拦截被计成 error，口径偏高 | activity 原文 |

## 二、"三端 50%+ vs 本机 4%"的四个叠因

### 1. 工具说明书漂移（结构性，可修）

- `db.SeedTool` 是 `ON CONFLICT (key) DO NOTHING`：**首次安装写入后永不更新**。
- 之后所有"改工具描述/参数结构"的修复，都只能靠 `server/orchestration.go` 里的一次性开关 + 白名单补：
  - `refreshBuiltinToolSchemas()` → flag `tool_schema_refresh_v7_list_facts_paging`
  - `refreshOverlapToolDescriptions()` → flag `tool_desc_refresh_v1_overlap_steering`
- 后果：① 白名单之外的 key 永远拿不到新说明；② 刷过一次就再也刷不动，之后改描述必须记得改 flag；③ **有没有生效，界面上完全看不出来**。

**本机实测（`/api/tools/drift` 同口径，代码 vs 库）**：

```
code_fingerprint=cea07eee963f31ea row_fingerprint=d3c9a832a341aca2 drifted=true
counts = { in_sync: 68, drifted: 7 }
drifted: distill_task_skill, http_sequence, kill_work, list_skill_proposals,
         software_analysis, spawn_task, tactical_kb
```

注意 `http_sequence` 恰好是**本机错误率最高的工具（42 次调用 / 6 次失败 = 14.3%）**。老库上这个工具的说明停留在安装当天，模型看到的是旧措辞与旧参数结构——这正是"漏必填 + 参数类型错"的温床。

> 说明：本机是"紧跟仓库"的机器，仍漂了 7 个；换到一台几天不升级的机器，漂移面只会更大。

### 2. 小样本放大

本机 530 次工具调用才 20 次失败。三端若只有几十次调用，**一次"漏 mode → 重试 → 再漏 → 再重试"的连环**就能把失败率推到 30–50%。错误率与样本量强相关，不能直接横向比。

### 3. 模型差异

`llm_usage` 27,546 行（10-16 → 10-20）：

| profile | model | ok | err | err% |
|---|---|---|---|---|
| openroter | minimax/minimax-m3.1-flash:free | 7364 | 52 | **0.7%** |
| 9router | oc/deepseek-v4.1-flash-free | 6972 | 233 | **3.2%** |
| 调试 | trae/deepseek-v4.1-flash | 4153 | 36 | 0.9% |
| 新疆中转站 | Qwen3.8-Flash-Next | 2168 | 62 | 2.8% |

同一套工具、同一台机器，换模型差 4–5 倍；`claude-opus-5.5` 甚至是 8/9（上游问题，不是工具问题）。

### 4. 工具面规模

按 agent 统计可见工具：`auto 35`、`mainagent 30`、`worker 26`、`planner 25`、`pentest 22`。`auto`/`mainagent` 已进入业界观测到的 30–50 工具退化区间。

## 三、本机 20 条错误的逐类处置

| 类别 | 条数 | 典型原文 | 处置 |
|---|---|---|---|
| 漏必填参数 | 6 | `missing required property "mode"` / `"url"` | ①错误文本自愈化（见 4.1/A）②`http_sequence` 按入参反推 mode（4.2/B） |
| 引用路径不存在 | 5 | `data/tasks/26/cmd-output/output-1792496464-28.txt`、`wl/probe_get3.txt`、planner `tasks/task_1.output` | 路径诊断：回列同目录相近文件 + 工作目录（4.3/C） |
| 超时 / 槽位排队 | 4 | `等待同目标执行槽位已取消`、`context deadline exceeded` | 报错补上目标标识与处置建议（4.4/E） |
| schema 与 Go 类型不符 | 2 | `cannot unmarshal object into ... strip_headers of type []string` | `stringList` 宽容解码三种写法（4.5/D） |
| 正则超 RE2 上限 | 1 | `{0,2200}` 编译失败 | 识别超 1000 次重复并给改写建议（4.6/F） |
| PowerShell 语法 | 1 | `= : The term '=' is not recognized` | 模型侧问题，保留原始报错（不改工具） |
| tool_steering 拦截 | 1 | `<tool_steering> 已拦截` | 行为正确（拦截即失败），仅统计口径需剥离 |
| 执行中断 | 1 | `tool execution interrupted` | run 被取消，非工具缺陷 |

## 四、改动清单

### A. 参数校验失败 → 一次就能改对（`agent/assembly.go` + `agent/toolinput_repair.go`）

原来只有一句"请核对工具参数说明后重新调用"。现在返回：

```
参数校验未通过（stage=tool_validate，工具 http_sequence）：input: missing required property "mode"。
本次实际收到字段：url。 必填但缺失：mode。 [mode] string；执行模式：chain | replay | bola | race | timing | diff；
提示：mode 可省略，但必须能由入参唯一确定（steps→chain，base_exchange_id/override_*→replay，identities→bola，
race_count→race，baseline_*→timing，exchange_id_a/b 或 text_a/b→diff）。
请按上述说明修正后重新调用，不要原样重试。
```

包含：原始错误 + **你实际发了哪些字段** + 必填但缺失 + 该字段声明的类型/枚举/说明首句。

### B. `mode` 缺失时按入参反推（`agent/assembly.go` normalizeToolInput）

`steps→chain`、`base_exchange_id/override_*→replay`、`identities→bola`、`race_count→race`、`baseline_*→timing`、`exchange_id_a/b|text_a/b→diff`。
**只在唯一可判定时生效**；两种模式同时被暗示则不猜；反推会写日志 `[tools] http_sequence 未传 mode，已按入参反推 mode=chain`。

### C. 路径不存在 → 回列候选（`agent/pathhint.go`，接入 `http_fuzz` / `extract_data` / `dns_probe`）

```
读取文件失败：路径不存在 C:\...\cmd-output\output-1792496464-29.txt（参数值 "cmd-output/..." 为相对路径，已按工作目录解析）；
该目录下相近的文件：output-1792496464-28.txt, output-1792496464-27.txt。
请先用 LS 或 Read 确认实际路径（相对路径按工作目录解析）后重试，不要重复提交同一路径。
```

### D. `strip_headers` 三种写法都收下（`agent/tools_sequence.go`）

线上原错：`cannot unmarshal object into ... strip_headers of type []string`。模型写 `{"Cookie": true}` 是完全合理的"集合"表达，语义与 `["Cookie"]` 相同。新增 `stringList` 同时接受 `["a","b"]`、`"a"`、`{"a":true}`；并把 `identities.items` 的 properties 写全（name/cookie/headers/strip_headers），让模型不用猜结构。

### E. 槽位/取消报错带上目标与建议（`agent/loop_breaker.go`）

`等待同目标执行槽位已取消：context deadline exceeded。同一目标同一时刻只允许一次调用…目标标识：<key>`

### F. 正则超上限给出可执行建议（`agent/toolinput_repair.go` re2RepeatHint）

Go RE2 重复次数上限 1000，模型习惯写 `{0,2200}` 表示"最多吃 2200 字符"，原报错只有 `invalid repeat count`，导致反复重试。现在直接说明上限并给出 `{0,1000}` / `.*?` + `max_matches` 的替代写法。

### G. 工具目录同步：从"一次性 flag"改为"内容寻址"（`server/toolcatalog_sync.go`）

- 每个工具在 `settings` 记一个 `toolseed:<key>` = 上次同步时的代码指纹（Description+Schema 的 sha256 前 16 位）。
- 启动时：行内容仍等于指纹 → 运维没改过 → 代码变了就自动刷；行内容已不等于指纹 → 运维改过 → **永久保留**（记日志，不静默覆盖）；老库没有指纹 → 首次接管一次，旧值先备份到 `toolseed_backup:<key>`。
- 绑定关系（agents）与启用开关（enabled）永远不动。
- `tool_catalog_sync=off` 可整体关闭接管（只诊断不写库）。
- 新增只读诊断 `GET /api/tools/drift`：返回 `code_fingerprint` / `row_fingerprint` / `drifted` / 逐项状态。

## 五、三端如何验证（一次一条命令）

**方式 1（运行中的实例）**：


- 相同 → 模型看到的工具说明书逐字一致，"漂移"这个因素被排除；
- 不同 → 输出里的 `drifted` 项就是被旧版本钉住的工具，升级到本 commit 后重启即自动对齐（日志会打印"工具目录首次接管：…"）。

```bat
set ARTEX_TOOLCATALOG_DB=C:\path\to\artex.db
go test ./server -run TestToolCatalogDriftOnDB -v
```

只读副本，不碰线上库。

## 八、复核（2026-10-20 22:10，线上库副本实测）

动机：确认「三端 / 本机 差距」在 7cd527c 之后是否还存在，以及差距到底落在哪一端。

做法：
1. 把线上库 `ARTEX程序rtex.db`（含 `-wal`/`-shm`）复制到 `%TEMP%\dbcopy6`，与代码里的
   `agent.BuiltinToolSeeds()` 逐条比对；
2. 用当前源码构建新的 `artex_new.exe`，以「工作目录 = 库副本所在目录」的方式冷启动一次
   （端口 8797/8798，不触碰正在运行的 8787/8788），再读同一个副本。

结果（同一份库，启动前 → 启动后）：

| 观察点 | 启动前（线上现状） | 启动后（新构建） |
| --- | --- | --- |
| `settings` 里 `toolseed:*` 行数 | **0** | 75 |
| `toolseed_backup:*` 行数 | 0 | 7 |
| `http_sequence.properties.identities.items.properties` | **不存在**（模型只看到 `{type:object}`） | `cookie / headers / name / strip_headers` 齐全 |
| `tactical_kb` 描述 | 407 字符，只有 4 个模式 | 680 字符，含 `case_skills` / `logic_invariants` |
| 启动日志 | 无 | `工具目录指纹 code=cea07eee963f31ea row=cea07eee963f31ea 一致=75 差异=0` |

结论：
- **`toolseed:*` 为 0 是硬证据**：线上这一实例从未执行过 `syncToolCatalog()`，
  即它跑的二进制早于 7cd527c。工具说明书仍是装库当天的快照——`http_sequence` 的
  `identities[]` 没有字段说明，模型只能猜 `strip_headers` 的形态（线上原错
  `cannot unmarshal object into []string` 正对应这里）；`tactical_kb` 少两个模式。
- 新构建在**同一份库**上冷启动一次后，代码指纹与库指纹完全一致（75/75），
  首次接管的 7 个工具旧值已备份到 `toolseed_backup:*`，可人工回滚。
- 因此「换模型也没用」的原因是：变的不是模型，是**模型看到的那份说明书**。
  远端成功率高的端 = 新库（说明书即代码）；本机 = 旧库 + 旧二进制。

需要的动作：**重建并重启一次**（同步只在启动时跑）。重启后判断标准只有一条——
启动日志里 `code=` 与 `row=` 相等、`差异=0`，或 `GET /api/tools/drift` 的
`code_fingerprint == row_fingerprint`。

遗留：`/api/tools/drift` 目前只有接口没有界面（`web/src` 下没有任何消费方），
运维无法在页面上直接看到「哪一端是旧的」。下一步补一个只读徽标：显示
`code/row` 指纹与 `in_sync / drifted / kept_local` 计数，三端各看一眼即可对齐。
