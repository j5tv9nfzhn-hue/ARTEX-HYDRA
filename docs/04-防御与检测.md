# 防御与检测

> 本目录内容只用于**防御与检测自有或获得明确书面授权的系统**。
> 检测规则均基于本仓库源码实际存在的字符串或行为，而不是猜测。不得将泛化行为误称 ARTEX 专属指纹。

## 自主 AI 攻击防御与检测指南

> 本指南帮助防御者了解 ARTEX 等自主 AI 渗透代理，建立检测与阻断能力，不是攻击教程。仅用于保护自有或书面明确授权系统；未授权探测/攻击他人信息通信网络可能违法，参见[根 README 的安全告知](../README.md)。
>

自主 AI 工具将人工渗透流程变为可持续运行的自动过程：LLM 分解目标、执行真实工具、积累发现。防御者面对的不再只是单个操作人员，也可能是持续工作的代理群；本指南整理检测与响应所需变化。

---

### 1. 自主 AI 攻击与传统扫描器的区别

传统固定签名扫描器按预设项目依次检测。自主代理结合[系统架构](02-系统架构.md)中的组件，支持无人介入的多阶段链路：

- **多角色代理：** goals 分解目标，planner 是唯一 intent 生成者，多 worker 并行执行，mainagent 提供人工交互。
- **双图积累状态：** 资产图记录“有什么”，探索图记录“测到哪里”，通过锚点连接；可从不同角度重访、基于旧观察推进。
- **事件闭环：** 图变更唤醒 planner，worker 写入又触发下一轮，向目标证明迭代。
- **有序链路：** planner 在共享 todolist 记录依赖，仅为前置完成的步骤分配 intent，避免无状态会话使顺序漂移。
- **上下文变体：** 工具与载荷并非固定常量，LLM 按环境生成，请求形态可变化。

#### 检测为何更难

- **固定签名容易漏检：** 按上下文变化的请求可能绕过精确恶意字符串匹配。
- **可低速且间歇：** 轮间暂停、依据发现改向，仅看短时请求量不足。
- **侦察与后续动作连续：** 人工分析间隔缩短，首次接触到数据外流可更快。

#### 仍可检测：行为比静态指纹难隐藏

UA 和固定字符串可以修改，但多阶段自适应行为更难完全改变。第 2–4 节重点采用行为视角。

- 同一来源以连续会话完成性质不同的多阶段请求。
- 在人工通常会暂停的时段仍持续探索。
- 依据失败响应系统性调整请求，而非随机变异。

### 2. 防御者可观察的指纹（IoC 与签名）

区分**目标侧**收到的流量与**运营者/取证侧**实际运行或中转主机的证据，不能混用。目标侧静态指纹有限，行为关联更关键。

#### 目标侧：面向本系统的流量

- **补全 UA artex-enrich/1.0：** enrich/enrich.go 在 DNS/HTTP 补全直接发送 GET，非 LLM 生成；不跟随重定向、关闭 keep-alive、只读响应前部提取 title，默认并发 4。多资产短连接、单 GET、读取标题即断开是线索，但 UA 可改，缺失不代表安全。
- **主测试流量遵循工具默认：** worker 执行 Bash 外部工具或 HTTP，平台只注入 HTTP_PROXY/CA 环境尝试记录，不强制独有 UA。工具默认或自定义头可类似浏览器，不能仅靠 UA，须结合行为。
- **内置 WebFetch 留下 norma/0.4：** norma SDK 的默认 UA，不等同 Bash 外部工具。可在明文或 TLS 终结处观察，[Suricata sid 1000003](#随仓库发布的检测规则)匹配 norma/ 前缀。其他 SDK 使用者也有该 UA，只是辅助线索，缺失不排除 ARTEX。
- **无目标专用内置限速：** 速率由外部工具决定，默认每任务 3 worker 并行，既可能低速单会话，也可能多角度并发，单一阈值不足。
- **关键行为为组合出现：** 同一/少量轮换来源短间隔跨侦察、枚举、参数探测与认证/注入阶段；同端点请求按状态码/长度系统调整；非工作时段长时连续；401/403/429 后仍持续变换尝试。

#### 运营者与取证侧：运行 ARTEX 的主机

用于调查疑似安装或执行 ARTEX 的中转主机。

- **默认 127.0.0.1:8787：** `--addr` 可改；该端口出现仪表盘/任务/资产图 UI 是线索（默认只绑回环，`cmd/artex/main.go`）。
- **记录 MITM 127.0.0.1:8788：** --proxy 默认 loopback，生成 mitmproxy-ca-cert.pem 以解密记录。检查信任 CA 及注入 HTTP_PROXY/CA 的痕迹。worker.go 固定变量名，代理与 mitmproxy CA 同时存在比单端口更特异；[triage](#随仓库发布的检测规则)读取 /proc 或离线环境转储。
- **更新 UA artex-selfupdate：** selfupdate/ 查询 GitHub Release 的出站流量辅助指示二进制存在。
- **SQLite 单文件双图：** 默认与 `config.json` 同目录的 `artex.db` 中，exploration_nodes、assets、companies、activity 及 agent_prompts 种子是数据结构线索。
- **DB 规则与审计：** intercept/ 按优先级匹配 DB 正则；GET /api/audit 中被阻止调用以 `【ARTEX 平台管控·非目标防御】` framing 记录，是运行证据。
- **破坏性命令狩猎：** rm -rf、mkfs、dd of=/dev/、shred/wipe、DROP DATABASE/TABLE、TRUNCATE、MongoDB drop/dropDatabase、Redis FLUSHALL/FLUSHDB、curl/wget -X DELETE 等是通用线索。`curl … | nc …` 属于外流而非破坏；平台因正常逆向连接/传输误报默认关闭此规则，[部署狩猎规则](../detections/sigma/destructive_command_hunting.yml)也仅含破坏范围，不含该管道。外流须单独研判调优，不能直接等同恶意或立即阻断。

> 目标侧以行为为主，artex-enrich/1.0、norma/0.4 为辅助。端口、更新 UA、DB 与审计 framing 主要用于实际运行/中转主机的取证，不能误当目标侧指标。

#### 为什么 IP 阻断只是较弱的第一道防线

事件后常出现社区分享的“攻击 IP 清单”。不建议直接把来源不明、未经验证的非官方清单加入防火墙，尤其面对可轮换来源的自主代理。

- **难以验证来源：** 无可靠采集依据，可能混入无关地址。
- **很快过期：** VPN、云实例、受控中转可改变来源，阻断昨日地址不等于停止今日行为。
- **误封风险：** 共享网段/CDN/正常云 IP 可能伤及客户或内部服务，自动阻断会加速扩大影响。

IP 阻断有用的前提是可信机构/情报来源、有效期审查和误封评估；它仍是追踪轮换起点的临时措施。持续有效的是第 2–4 节行为检测和第 3、5 节攻击面缩减、补丁、MFA。

### 3. 常见入口与加固

自主代理针对与人工相同的弱点，但更持续、更快速重复；以下按防御优先级加固。

#### 3.1 外部暴露面与已知 n-day 漏洞

最稳定入口常是暴露且未修补的已知漏洞，而非复杂 0-day：VPN/防火墙、管理控制台、应用服务器/中间件/框架如 WebLogic、Struts，以及合作、招聘、员工辅助系统。资产枚举与公开 PoC 的自动化匹配可早于补丁覆盖，形成速度不对称。

- **缩减暴露面：** 持续维护互联网资产/控制台/辅助系统清单，不必外露的置于内网、VPN 或允许列表之后。
- **迅速修补：** 优先边界、Web、应用与中间件的已知漏洞，特别是公开 PoC 流行组件。以持续更新的 [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) 与 [CNCERT/CC 公告](https://www.cert.org.cn/) 为优先级输入，交叉查看第 7.1 节官方渠道建议，而非把某个 CVE 写死。
- **限制必要入口：** 不可关闭的管理界面加来源限制、MFA、VPN，减少未认证枚举。
- **同等管理辅助系统：** 合作/招聘/员工渠道保持与主服务相同补丁与监控水平；认证流见 3.2。

已知漏洞 URL/参数的短间隔连续请求是 n-day 扫描线索，结合第 2 节行为与第 4 节同来源多阶段关联更有效。

#### 3.2 辅助认证与身份核验流程

附加、合作、招聘等不同认证路径可能校验较弱。代理可枚举并通过响应差异寻找条件，因此必须全量审查而不只保护主入口。

- 辅助与主服务认证强度一致，审查全部可替代路径。
- 服务器重新验证未登录→登录、普通→特权等状态转换，不信任客户端 cookie/header/参数标记。
- 审查身份 token/一次性码的寿命、重用与可猜测性。

#### 3.3 API 认证与授权（IDOR、权限提升）

- 所有对象访问强制服务器所有权/权限检查，防止仅换 ID 读取他人资源。
- 全面审查横向与纵向权限边界；自动化标识符遍历可能发现单次人工测试遗漏的问题。

#### 3.4 凭据填充（credential stuffing）

泄露账号/密码的重用尝试可能被自主代理的速度与分布放大。

- 登录/核验接口按 IP、账户、设备和行为实施自适应限速。
- 敏感操作强制 MFA，不能只依赖密码。
- 对照可信泄露清单，监控异常登录位置/速度。
- 对失败/成功分布变化，包括低速但广泛尝试，设置告警。

#### 3.5 会话、令牌与秘密管理

- 最小化会话范围、寿命与刷新能力，敏感转换重新认证。
- 不在响应、日志或错误暴露 API key/内部 token；代理会利用错误线索。

### 4. 检测规则与日志模式（实践）

以下为产品无关伪规则，须映射到自身 WAF/IPS/SIEM。源码有依据的静态规则及补全速率/目标数、guard burst、guard 与破坏命令同主机共现等关联见 [Sigma](#随仓库发布的检测规则)。纯 Web 多阶段行为无独有 UA，4.2 提供通用模板。网络 UA 见 [Suricata](#随仓库发布的检测规则)：artex-enrich/1.0 的存在性 sid 1000001、速率 sid 1000002，norma/0.4 的 sid 1000003。

#### 4.1 WAF 与 IPS（行为检测）

- 同来源会话中枚举/参数探测/认证请求高占比、静态资源低占比时增加风险分。
- 按状态码/正文长度系统性调整而非随机的连续请求增加权重。
- 已知自动化 UA 如 artex-enrich/1.0 可标记高风险，但缺失不表示安全。

#### 4.2 SIEM 关联规则

- **同来源多阶段：** 同 IP/ASN/会话在短窗内同时出现端点枚举、参数探测、认证/注入尝试。
- **时间异常：** 单会话长时间连续，偏离正常业务时段分布。
- **失败后持续：** 收到 403/429 仍反复调整请求。

#### 4.3 认证日志

- 账户/IP 失败率突变、低速广泛账户尝试、异常快速失败→成功转换。
- 身份核验/一次性码接口的枚举式访问。

#### 4.4 出站流量与取证

- 内部主机以 artex-selfupdate UA 访问代码仓库。
- 绑定 :8787 管理 UI、127.0.0.1:8788 记录代理的进程。
- artex-enrich/1.0 短时批量查询外部资产的 DNS/HTTP 补全模式。

### 5. 加固检查清单

防御组织可据此逐项审查。

- [ ] 登录/身份核验/敏感 API 自适应限速。
- [ ] 敏感操作强制 MFA。
- [ ] 每个对象访问有服务器所有权/授权检查。
- [ ] 状态转换服务器重验，不信任客户端标记。
- [ ] 辅助/合作/招聘渠道身份验证与主服务一致。
- [ ] 持续检测、对照泄露凭据。
- [ ] WAF 使用行为检测，不仅固定签名。
- [ ] 不直接应用来源不明 IP 清单，可信 IoC 也审查有效期/误封风险。
- [ ] SIEM 同来源多阶段关联。
- [ ] 认证/访问/出站日志充分保留。
- [ ] 维护暴露资产清单、缩减攻击面、迅速修补边界/应用/中间件 n-day。
- [ ] 网络分段限制横向移动与权限提升影响范围。
- [ ] 响应/日志/错误不暴露秘密。
- [ ] 准备经风险评估的自动阻断/隔离，避免全依赖人工批准。

### 6. 事件响应摘要

自主代理可将原本长期的探测与外流压缩到更短时间，响应设计必须考虑这种速度。

- **预备自动处置：** 对高置信信号按既定策略隔离来源、失效会话、降低速率，不把所有动作都置于人工等待；评估误封并留回滚。
- **事先定义日志：** 认证、访问（合规允许的正文范围）、出站、DNS，为事后链路重建保留证据。
- **按资产追踪范围：** 重建入口到横向移动/权限提升的完整路径，不仅修补首次入口。

#### 6.1 疑似主机与流量研判流程

分为“本服务是否被针对”与“某主机是否运行过 ARTEX”。不以单一命中定论，结合多指标与行为；静态指标缺失但行为异常时继续调查。

**目标侧：本服务是否被针对**

1. 查访问/认证日志的 artex-enrich/1.0，是否多资产短间隔、无重定向单 GET。UA 可改，未命中仍继续。
2. 查同一/少量轮换来源的侦察→枚举→探测→认证/注入链，是否按响应调整、401/403/429 后持续。
3. SIEM 部署适用的 [Sigma 关联](#随仓库发布的检测规则)并结合通用 Web 模板；达到本地高置信条件时按响应策略隔离来源/失效会话，不能将主机侧 guard 指标误作目标侧流量。

**主机取证：某主机是否运行过 ARTEX**

依据第 2 节及 [CSV](../detections/indicators/artex_indicators.csv)，先用只读 [triage](../detections/triage/)检查端口、出站/guard 日志、状态/代理存储（triage 的数据库结构检查仍针对上游 PostgreSQL 布局，本分支 SQLite 暂未覆盖，不影响端口/代理/日志类检查）；第五项通用破坏命令不属于独有指纹，需人工对照历史。无 SIEM 时也可执行；所有命中只是线索。

1. **端口：** 本机检查默认 :8787 与 127.0.0.1:8788。
   ```sh
   ss -ltnp | grep -E ':8787|:8788'   # 无 ss 时使用 netstat -ltnp
   ```
   --addr/--proxy 可改，结果为空仍检查全部监听与内部管理 UI。
2. **出站：** selfupdate/ 的 artex-selfupdate 查询 GitHub Release。
3. **审计：** guard/guard.go 的 `【ARTEX 平台管控·非目标防御】`，被阻止工具调用带此 framing。
4. **存储：** SQLite 单文件 `artex.db`（默认与 `config.json` 同目录）中的 exploration_nodes/assets/companies/activity 与 agent_prompts 表；`--data` 默认可执行文件旁数据目录，含 tasks/、transcripts/。server/manager.go 将 traffic/ 用作记录存储，CA 在 traffic/_ca/mitmproxy-ca-cert.pem，索引在 traffic/_index/index.sqlite，正文在 traffic/_blobs/；组合出现较强地支持代理运行。
5. **命令审计：** 对照 rm -rf、DROP DATABASE、FLUSHALL、外流管道等通用狩猎线索，正常管理员也会执行，不单凭此定论。

端口、UA、标记均可修改/清除，缺失不等于安全。结合目标侧行为与主机侧证据才是研判核心。

### 7. 官方通报渠道与报告义务

本节给出中国大陆地区的通报与求助渠道。其他国家和地区请按所在地法律及主管机构规定处理；本节不构成法律意见。

#### 7.1 官方渠道

- **国家互联网应急中心 CNCERT/CC（[cert.org.cn](https://www.cert.org.cn/)）：** 网络安全事件应急处置、威胁情报与安全公告。
- **[12321 网络安全举报中心](https://www.12321.cn/)：** 违法有害信息与网络安全违法举报。
- **[国家互联网应急中心网络安全服务保障中心（12386）](https://www.12386.cn/)：** 互联网网络安全威胁情报共享。
- **[公安部网络安全保卫局](https://www.mps.gov.cn/)：** 涉嫌犯罪的网络安全事件报案渠道。
- **数据与个人信息保护：** 涉及数据泄露时，按《数据安全法》《个人信息保护法》向行业主管部门与网信部门报告。

第 5 节可信 IoC 来源包括这些渠道；即使官方指标也须审查有效期与误封风险，不能跳过第 2 节所述评估。

#### 7.2 金融机构与个人信息泄露的报告义务

事先把报告流程纳入第 6 节响应计划。以下为要点提示，准确适用对象、条件与期限须核对最新官方规定并征询法律意见。

- **个人信息泄露：** 依《个人信息保护法》第五十七条，个人信息处理者发现其处理的个人信息发生或者可能发生泄露、篡改、丢失的，应立即采取补救措施，并通知履行个人信息保护职责的部门和个人；造成严重后果的，还应告知受影响个人。
- **网络安全事件：** 依《网络安全法》第二十五条，网络运营者发生网络安全事件，应立即启动应急预案，采取补救措施，并按规定向有关主管部门报告。
- **数据出境与重要数据：** 依《数据安全法》，重要数据处理者发生安全事件应按规定报告；涉及数据出境的还需符合数据出境安全评估要求。
- **金融机构：** 还应按中国人民银行、国家金融监督管理总局、中国证券监督管理委员会及国家外汇管理局的行业监管要求，在规定时限内单独报告。
- **刑事报案：** 涉嫌非法侵入计算机信息系统、非法获取公民个人信息等犯罪的，应向公安机关报案。

事先记录负责人、联系方式和适用期限。

# 随仓库发布的检测规则

> 本目录将[防御与检测指南](04-防御与检测.md)第 4 节的伪规则转换为厂商中立的 [Sigma](https://sigmahq.io)，可进一步转换为各 SIEM、EDR 的查询语言。所有指标均基于本仓库源码实际存在的字符串或行为，而不是猜测。仅用于防御和检测自有或获得明确书面授权的系统。

### 原子（atomic）规则

- **`sigma/artex_enrich_user_agent.yml`**：资产补全（`enrich/enrich.go`）发送的入站 `artex-enrich/1.0` User-Agent，是目标侧辅助指标。`level: high`。
- **`sigma/artex_selfupdate_egress.yml`**：自更新（`selfupdate/github.go`）发送的出站 `artex-selfupdate` User-Agent，是主机/取证侧 egress 指标。`level: medium`。
- **`sigma/artex_guard_audit_framing.yml`**：工具调用被阻断时，`guard/guard.go` 写入审计日志的平台控制标记，属于主机/取证指标。`level: high`。
- **`sigma/destructive_command_hunting.yml`**：对应 `db/db.go` 种子中的破坏性 Shell/DB 命令 deny 列表，属于通用威胁狩猎线索，不是 ARTEX 专属指纹。`level: medium`。
- **`sigma/artex_recording_proxy_ca.yml`**：记录代理（`traffic/traffic.go`）生成的 `_ca/mitmproxy-ca-cert.pem`。属于主机取证产物，文件名也被独立 mitmproxy 使用，因此只能作为狩猎线索。`level: medium`。

### 关联（correlation）规则：行为检测

静态字符串可以改变，行为更难隐藏。[`sigma/correlation/`](../detections/sigma/correlation/) 将防御指南 4.1–4.2、4.4 节的行为层表达为 Sigma 关联。它们通过 `id` 引用上述原子规则，转换时必须提供整个 `sigma/` 树，不能只提供一个关联文件。

- **`sigma/correlation/artex_enrich_scan_velocity.yml`**：同一来源在短窗口集中发送 `artex-enrich/1.0` 探测。补全并发为 4、无速率限制，可捕获单条存在规则未体现的速度。`event_count`，`level: high`。
- **`sigma/correlation/artex_enrich_fanout.yml`**：同一来源将补全 UA 发送到多个**不同**主机，关注自动遍历资产的广度，不仅是数量。`value_count`，`level: high`。
- **`sigma/correlation/artex_guard_block_burst.yml`**：同一主机重复产生平台控制标记，表示运行中的调用触及自身 guard，而非文档偶然引用。`event_count`，`level: high`。
- **`sigma/correlation/artex_guard_marker_then_destructive.yml`**：同一主机在窗口中先后出现 guard 标记与破坏性命令，将 ARTEX 标记与通用行为组合提高特异性（指南 §4.2）。`temporal`，`level: high`。

阈值、窗口是保守起点，应按环境基线调整。纯 Web 多阶段模式“枚举→探测→认证”不能归结为一个 ARTEX 专属 UA，仍需环境专用基础规则。[防御指南 §4.2](#42-siem-关联规则)提供通用 Sigma 模板；它无法以 ARTEX 源码固定依据，因此没有放进本目录的已测规则树。

### 网络规则（Suricata）

Sigma 关注主机和日志；网络侧可见的两类 UA 在 [`suricata/`](../detections/suricata/) 中由 [Suricata](https://suricata.io) 表达。`enrich/enrich.go` 的 `artex-enrich/1.0` 对应存在与高速枚举规则（sid 1000001、1000002）；norma SDK WebFetch 的 `norma/0.4`（`github.com/Autumn-27/norma/tool/webfetch.go`）对应存在规则（sid 1000003）。Bash 执行的 curl、nmap 等其他工具使用自己的指纹，没有 ARTEX 专属 UA，所以网络规则刻意限制为这两类。TLS 限制、`suricata -T` 与参考 pcap 验证见 [`suricata/README.md`](#随仓库发布的检测规则)。

### ATT&CK 覆盖率

[MITRE ATT&CK](https://attack.mitre.org/) Navigator 层 [`attack/artex_navigator_layer.json`](../detections/attack/)汇总六种战术（侦察、命令与控制、执行、影响、凭据访问、收集）的八种技术。仅依据规则 `attack.*` 标签，按专属指纹或通用狩猎线索的检测强度计分，不添加猜测。用 [Navigator](https://mitre-attack.github.io/attack-navigator/)查看，评分、技术与规则对应及“覆盖不代表完整检测”的说明见 [`attack/README.md`](#随仓库发布的检测规则)。[一致性测试](../detections/tests/attack/run.sh)防止层与规则漂移。

### 机器可读的威胁指标

[`indicators/artex_indicators.csv`](../detections/indicators/)汇总可导入威胁情报平台、SIEM 查询表或 triage 清单的原子指标：补全/自更新 UA、guard 标记、服务/代理默认端点、代理 CA 和 PostgreSQL 探索图 schema。每行注明来源文件及适用规则。

同一指标也提供 [MISP](https://www.misp-project.org/) 事件 [`artex_indicators.misp.json`](../detections/indicators/)，支持直接导入或进一步导出 STIX。规则支持的指纹标为 `to_ids`；主机端口、schema 线索不标。为避免误报，通用破坏性命令及 norma SDK 共享的 `norma/0.4` 不进入导入清单；后者虽被 Suricata sid 1000003 检测，却不是 ARTEX 专属字符串。列、MISP 类型映射、限制与同步测试见 [`indicators/README.md`](#随仓库发布的检测规则)。

### 主机分类（triage）

没有 SIEM、仅获得可疑主机 Shell 的响应人员，可运行只读 [`triage/artex_host_triage.py`](../detections/triage/)检查本地是否有 ARTEX 痕迹。除同类指纹外，还覆盖 CSV 刻意没有 Sigma 规则的三个主机/DB 指标：监听端口、记录代理端点、PostgreSQL 探索 schema；这些必须在主机上确认。

工具也从 `/proc` 或 `--proc-from` 转储检查进程是否同时携带代理与 mitmproxy CA 信任变量，依据 `agent/worker.go` 的注入行为。各发现仅为带有对应指标局限的分类线索，不是归属证明。见 [`triage/README.md`](#随仓库发布的检测规则)，内置 `--self-test` 接入合并门禁。

### 测试

[`tests/`](../detections/tests/)提供仅需 Docker 的可复现规则测试。

- **Suricata**（[`tests/suricata/run.sh`](../detections/tests/suricata/run.sh)）：先以 `suricata -T --init-errors-fatal` 加载完整规则，再由 scapy 确定性合成 pcap，运行 `suricata -r`。存在规则每探测触发一次，速度规则超过阈值触发，正常 UA 告警为零。捕获文件每次生成，不提交二进制。
- **Sigma**（[`tests/sigma/run.sh`](../detections/tests/sigma/run.sh)）：验证 check 零错误、整树编译、原子指标保留到查询、关联规则单独转换失败；最后一项证明其真实依赖被引用原子规则。
- **Sigma 事件匹配**（[`tests/sigma_match/run.sh`](../detections/tests/sigma_match/run.sh)）：原子恶意样本触发、正常样本静默；例如只有 `.mitmproxy/` 的 CA 不满足要求 `_ca/` 的规则。关联在同组、同窗口满足阈值时触发，在阈值不足、过期、组拆分、缺少阶段时静默。pySigma 解析条件，测试遍历编译树与聚合规格，复用原子匹配器。
- **ATT&CK**（[`tests/attack/run.sh`](../detections/tests/attack/run.sh)）：技术、战术与规则 `attack.*` 标签完全一致，各技术指向实际规则；任何单向增删均失败。
- **指标依据**（[`tests/indicators/run.sh`](../detections/tests/indicators/run.sh)）：固定 UA、guard 标记、破坏 token 与真实源码一致，CSV 每行仍有源码/规则依据；所有固定的非 detections 来源都在 CI push/PR paths 中。捕获“规则仍编译触发，但上游已经改指纹”的漂移。
- **MISP 同步**（[`tests/misp/run.sh`](../detections/tests/misp/run.sh)）：pymisp 实际加载有效事件，拒绝不存在的属性类型；值、预期类型/类别、`to_ids`、`disable_correlation` 与 CSV 逐行一致。可检测指标 `to_ids` 开启，主机端口分类提示关闭且禁关联。事件另有说明、UUID、标签，手工维护，CSV 增删或改类型时必须同提交同步。
- **Sigma 后端可移植性**（[`tests/sigma_backends/run.sh`](../detections/tests/sigma_backends/run.sh)）：整树编译为 Splunk、Elasticsearch eql、Grafana Loki；五条原子规则也在不支持关联的 lucene、Microsoft kusto 编译，复现下面支持矩阵。
- **SigmaHQ lint**（[`tests/sigma_lint/run.sh`](../detections/tests/sigma_lint/run.sh)）：加载全部 `pySigma-validators-sigmahq` 验证器，不是普通 check；按 [`validators.yml`](../detections/tests/sigma_lint/validators.yml)基线零问题，并确认仅有四项已说明的不适用检查排除。新标题、字段或分类问题会使构建失败。

八类规则测试之外，还有三个非规则门禁由同一 CI 与 [`tests/run-all.sh`](../detections/tests/run-all.sh)运行：harness 同步检查 runner、CI、目录的套件与顺序一致；[`triage-selftest.sh`](../detections/tests/triage-selftest.sh)验证合成主机命中、干净主机零发现；[`check-defense-template.sh`](../detections/tests/check-defense-template.sh)复现指南内联模板的 check、splunk/eql/loki 转换、lucene/kusto 关联拒绝和中英文规则主体字节一致。模板位于规则树之外，工具升级造成文档承诺过期时其他套件不会发现。

任何断言失败均返回非零。详情见 [`tests/README.md`](#随仓库发布的检测规则)。

### 正确理解规则与局限

- **静态指标可改变。** 缺少 `artex-enrich/1.0` 或 `artex-selfupdate` 不代表安全。更持久的信号是同源侦察、枚举、探测、认证/注入随响应持续调整；速度、fanout、guard 突发和多阶段关联已表达于规则，纯 Web 多阶段仍需环境基础检测，见指南 1、2、4.1–4.2 节。
- **破坏性命令是通用狩猎。** 合法管理员也可能运行同样命令，应结合允许列表与上下文，不能仅凭命中认定 ARTEX。
- **端口是主机取证指标。** 默认服务 `:8787`、代理 `127.0.0.1:8788` 适合在可疑主机用 ss/netstat 确认，不作为高噪声 Sigma 网络规则。CSV 将其标为分类线索，[triage](../detections/triage/)为没有 SIEM 的响应人员检查端口、代理产物、日志标记与 PostgreSQL schema。

### 验证与转换

原资料使用 [sigma-cli](https://github.com/SigmaHQ/sigma-cli)（pySigma）验证这些规则。复现方法：

```sh
python3 -m venv .venv && . .venv/bin/activate
pip install sigma-cli

## 结构与最佳实践检查，预期零错误、零问题
sigma check detections/sigma/

## 加载 SigmaHQ 全部约定验证器，使用独立规则集的已记录基线
## 普通 sigma check 不加载这些验证器
pip install pySigma-validators-sigmahq
sigma check --validation-config detections/tests/sigma_lint/validators.yml detections/sigma/

## 编译为目标查询语言，例如 Splunk
sigma plugin install splunk
sigma convert -t splunk --without-pipeline detections/sigma/artex_enrich_user_agent.yml

## 转换整树，以解析关联规则通过 id 引用的原子规则
sigma convert -t splunk --without-pipeline detections/sigma/
```

基线启用 SigmaHQ 全部约定，仅排除四项针对其 monorepo 文件布局和分类体系、而不适用本独立规则集的检查。理由见 [`validators.yml`](../detections/tests/sigma_lint/validators.yml)，由 lint 测试机械验证。

#### Sigma 后端可移植性

关联规则引用原子 `id`，只有支持 Sigma 关联转换的后端可以编译整树。`-t` 选择很重要。以下为原资料固定基线（sigma-cli 3.1.0 与兼容后端）记录的支持情况，由 [`sigma_backends`](../detections/tests/sigma_backends/run.sh)复现。

- **整树（原子与关联）：** Splunk（`-t splunk`）、Elasticsearch EQL（`-t eql`）、Grafana Loki（`-t loki`）。
- **仅原子规则：** Elasticsearch Lucene（`-t lucene`）、OpenSearch（`-t opensearch_lucene`）、Microsoft kusto（Sentinel/Defender XDR，`-t kusto`）。转换五条原子，在产品内原生表达窗口，如 Sentinel 的 `summarize ... by bin(TimeGenerated, 30m)`；传整树会报 `Backend does not support correlation rules`。

```sh
## 仅转换原子规则，例如 Microsoft Sentinel / Defender
sigma plugin install kusto
sigma convert -t kusto --without-pipeline \
  detections/sigma/artex_enrich_user_agent.yml \
  detections/sigma/artex_selfupdate_egress.yml \
  detections/sigma/artex_guard_audit_framing.yml \
  detections/sigma/artex_recording_proxy_ca.yml \
  detections/sigma/destructive_command_hunting.yml
```

固定版本的原记录说明：ES|QL（`-t esql`）拒绝 guard 标记规则，报 `String value expressions are not supported`，当时建议转换其余三条原子；新增规则需另核实支持。IBM QRadar 插件 `ibm-qradar-aql` 与固定 pySigma 不兼容、需 `--force-install`，故不在测试矩阵。用 `sigma list targets` 查看已安装目标。

例子用 `--without-pipeline` 保留 `cs-user-agent`、`cs-host`、`CommandLine` 等通用字段。实际部署应移除该参数，使用 `-p` 处理管线映射产品 schema（`sigma list pipelines`）。管线还可能要求通用 logsource 没有指定的目标表，如 sentinel_asim 在设置正确 `query_table` 前会报 `Unable to determine table name`；必须按环境映射字段和表。
