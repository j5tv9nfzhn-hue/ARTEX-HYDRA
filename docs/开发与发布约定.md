# 开发与发布约定（长期生效 · 最高优先级）

> 本文件是本仓库的**最高优先级作业约定**，优先级高于 `CONTRIBUTING.md` 与 `MAINTAINING.md` 中的通用开发说明；
> 两者冲突时以本文件为准。修改本文件需要与改动 `ci.yml` / `release.yml` 同等审慎，且应在同一个提交内同步更新。
>
> 最后更新：2026-10-21

- **第 1～6 节**约束的是 **AI 助手 / MCP 客户端在本机工作副本上作业时的行为**：
  本机 `C:\Users\Administrator\Desktop\ARTEX-REA` 只做"读、写、提交、推送"，不做构建。
- **第 7～9 节**（门禁分层、代理、发布）是**仓库级**约定，对任何执行 `git push` / 打 tag 的人与自动化都成立。

人类开发者在其他机器上正常开发，仍按 `CONTRIBUTING.md` 的"开发环境"执行本地构建与测试，不受第 2 节限制。

## 2. 本机不做任何测试 / 编译 / 构建 / 打包

在本机（含通过 MCP shell 间接调用、含写 `.bat` / `.ps1` / `.cmd` 去跑、含用 `docker run` 跑等价命令）：

**禁止**

```text
go build / go vet / go test / go run / gofmt / golangci-lint
npm ci|install|test|run build|run build:static、npx tsc、npx biome、next build
build.sh、dev.sh、任何打包 / 压缩 / 出 zip 的脚本
```

**允许**

```text
读文件、写文件（源码 / 配置 / 脚本 / 文档）、列目录
git status / diff / log / show / ls-files 等只读查看
git add / commit / push / tag（按第 5、6 节的网络与时机规则）
gh 只读查询（run list / release list / api GET）
```

理由：本机是用户的生产机，跑构建会污染工作树、占用 CPU 与磁盘、且与云端环境不一致；
云端 Actions 才是唯一的权威构建环境，本机的"跑一下看看"既慢又不能证明发版可用。

**替代手段**：写完回读文件，静态核对 import / 符号名 / 类型签名 / 调用点参数 / 结构体字段 / i18n 键是否存在
（见第 9 节）。宁可写得保守，也不在用户机器上跑命令兜底。

## 3. 验证由云端承担

本机的结论只能是"静态看是对的"，不能是"跑通了"。

## 4. 用静态自检替代编译

提交前逐项核对：

1. 新用的符号是否真实存在（`grep` 定义处，不凭记忆）。
2. 函数签名 / 返回类型 / 错误处理是否与调用点一致。
3. 结构体字段名、JSON tag 是否与前端类型、golden 文件一致。
4. 新增的 `import` 是否齐全，删除代码后是否留下未使用的 import。
5. 新增界面文案是否同时写进 `web/messages/zh.json`，键名一致。
6. 改了 `capability` 相关能力项时，同步 `mcp_tools.golden.json` 与计数断言。

## 5. 网络：访问 GitHub 必须走本地代理 7897

裸直连会稳定超时（约 20 秒后 `Failed to connect to github.com:443`），
而 `gh api` 走另一条链路可能仍然可用——**不要**因此误判为"仓库坏了"。

```bat
:: git（按次传参，不写全局 config）
git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 push origin main
git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 ls-remote origin refs/heads/main

:: gh
set HTTPS_PROXY=http://127.0.0.1:7897&& set HTTP_PROXY=http://127.0.0.1:7897&& gh run list --limit 6
```

```bash
# 同一条链路的 Linux / macOS 写法
git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 push origin main
```

故障处理顺序：

1. 先探测：`curl -x http://127.0.0.1:7897 -sS -o /dev/null -w "%{http_code}" https://github.com`，得 `200` 再 push。
2. 单次 20 秒无响应即判不可达；最多重试 2 次（合计 3 次）。
3. 3 次仍失败 → **停止并如实报告**。不裸直连硬刷、不无限重试、不改端口乱试。
4. **禁止**用 `gh api POST /git/refs` 绕过 push：commit 不在远端时必然 `422 Object does not exist`，
   还会让远端出现悬空引用。

## 6. 推送 / 打 tag / CI：发起即返回

- 不阻塞等待、不轮询日志、不盯 Actions 进度、不为"确认成功"反复查询。
- 唯一必须串行的动作：**tag 必须在新 commit 已到远端之后创建**。因此允许
  `push → ls-remote 校验 → push tag` 一次性完成，校验通过立即结束。
- 失败信息由用户转述，或按需再改源码；不靠本机复现失败。

## 7. 门禁分层：编译失败必拦，测试失败不拦

这是本项目对 CI 的核心口径。**产物健康**与**代码健康**是两件事，不能互相绑架。

| 类别 | 判定 | 典型内容 | 失败时的行为 |
|---|---|---|---|
| **编译 / 静态检查** | 确定性 | `go build ./...`、`go vet ./...`、`go vet -tags embedui`、`gofmt`、`golangci-lint`、前端 `build:static`（含 TS 类型检查） | **硬门禁：必须拦住，不得出包** |
| **测试** | 概率性 / 环境相关 | `go test ./...`、`node --test`、`detections/tests` | **信号灯：只报告健康度，不得阻塞打包与发版** |
| **发布流程** | 确定性 | 资产缺失、zip 数量不符、sha256 不匹配、上传失败、草稿未转正 | **硬门禁：必须失败并清理，不留半成品** |

三条红线：

1. **"测试不拦" ≠ "什么都不拦"。** 编译类、类型类的确定性失败必须拦死；不得把这条口径当作放松门禁的理由。
2. **测试红了要显著标注**（PR / Release 说明里写清楚哪几个包红），不得静默放过；更不得为了让测试变绿而删测试或改断言。
3. **发布失败必须原子回退**：`release.yml` 的 `if: failure()` 会删除草稿、保留 tag，下一次可原地重跑。

当前落地方式：

```text
ci.yml
├── go-build   前端静态导出 → go build / go vet / go vet -tags embedui
│              → gofmt → golangci-lint → build.sh --release → 头校验 → 上传 3 个 artifact
│              （不跑测试；编译失败 = 无产物）
└── go-test    独立 checkout + go test ./...（红了只影响自身，不影响 artifact）

release.yml
gate       tag 格式校验 + go build ./... + go vet ./...   ← 只有这三件，不等 CI 全绿
frontend   npm ci + build:static
binaries   6 目标交叉编译 + 打包
release    校验 6 个 zip → sha256sum → gh release create --draft → 上传 → latest.json → 转正
           if: failure() → 删除草稿，保留 tag
```

**为什么 gate 不等 CI 全绿**：CI 里的测试失败不代表二进制坏掉；把测试挂在发版链路上，
会让一次 flaky 测试挡住整个版本。编译与静态检查才是"产物能不能用"的必要条件。

## 8. 版本与发布

- **每版必须发 GitHub Release**，tag 与 Release 同名（`vX.Y.Z`），二者缺一视为该版未发布。
- 版本被删除后**重发沿用同一版本号**，不递增；前提是新 commit 已经成功推到远端。
- 更新源白名单只有 `j5tv9nfzhn-hue/ARTEX`：
  `selfupdate` 只接受该仓库的 Release，且保留**白名单 + SHA256 双闸门**。
  `jiwoochris/*`、`Autumn-27/artex` 已彻底移除，不得再进入检测或下载链路。
- 自动更新（安装）**默认关**；自动检测默认开；两者都要有开关，且状态可持久化。
- **发布说明必须写全量变更**：由 `scripts/gen-release-notes.py` 从 git 历史按类型分组生成，
  不再使用 `gh release create --generate-notes`（它只汇总 PR 标题，直接提交的改动会全部丢失）。
  正文上限 8 KB——它会进 `latest.json`，客户端每次检测都要下载。
- 一次 tag 推送只应产生 **1 个**发布 run：
  `ci.yml` 靠 `branches: [main]` 天然不在 tag 上跑；`detections.yml` 用 `tags-ignore: ["v*"]` 排除 tag。

## 9. 提交粒度

- 一次语义完整的改动合成**单个提交**，提交信息用中文，写清"改了什么 / 为什么 / 影响面"。
- 不提交构建产物（`dist/`、`server/webui/dist/`、`web/out/`）、不提交本地配置与密钥。
- 提交前默认执行 `git status` 与 `git diff --stat` 复核，确认没有夹带无关文件。

## 10. 常见误判对照表

| 现象 | 真实原因 | 正确做法 |
|---|---|---|
| `git push` 20 秒后 `Failed to connect to github.com:443` | 没走代理 | 按第 5 节加 `-c http.proxy=...:7897` |
| `git push` 返回 `Empty reply from server` | 代理链路抖动 | 换代理参数重试一次；仍失败则报告 |
| `gh api POST /git/refs` 返回 `422 Object does not exist` | commit 还没推到远端 | 先 push，校验 `ls-remote` 后再建 tag |
| 首页 404 | 构建没带 `-tags embedui` | 那是构建参数问题，不是代码问题（见 `docs/构建与产物.md`） |
| CI 红但 Release 正常出包 | 红的是 `go-test`（测试信号） | 属预期行为，按第 7 节处理 |
| CI `go-build` 红、无 artifact | 编译或静态检查失败 | 硬门禁生效，必须修代码 |
