# 上下文压缩黄金比例（80%）——落地说明（2026-10-21）

> 需求：**单窗口上下文总量，按用户在 Provider 里设置的模型窗口（`context_window_k`）计，达到 80% 左右就压缩。**
> 结论：已按此口径改代码，四条执行路径（planner / worker / main / chat）+ 实验性的 noa 路径全部生效，
> 128K 及以上的窗口触发点精确落在 80.0%，小窗口按"宁可早压、绝不晚压"封顶。

## 2. 源码事实（norma v0.4.3，只读核对）

模块缓存：`E:\Go\gopath\pkg\mod\github.com\!autumn-27\norma@v0.4.3\`。

### 2.1 内置 compaction：**没有比例旋钮**

`compaction/compaction.go` 的 `Config` 只有三个字段：

```go
type Config struct {
    ContextWindow   int // 默认 200000
    MaxOutputTokens int // 摘要预留 = min(MaxOutputTokens, 20000)，默认 8000
    KeepRecent      int // 默认 8
}
```

阈值全部是从 `ContextWindow` 派生出来的，写死在代码里：

```
effectiveWindow  = ContextWindow − reservedForSummary()          // 预留默认 8000
buffer(effective)= 50000 (≥800K) / 30000 (≥400K) / 13000 (其余)
autoThreshold    = effectiveWindow − buffer                      // 硬触发线
predictiveOver(t)= t + maxTurnGrowth > effectiveWindow           // 预测线，maxTurnGrowth = 预留 + 15000
microThreshold   = effectiveWindow × 6 / 10                       // 工具结果清退线
```

`Pre()` 里两条触发线是**或**的关系：

```go
if tok >= c.autoThreshold() || c.predictiveOver(tok) { autoCompact(...) }
```

→ 实际触发点 = `min(autoThreshold, effectiveWindow − 23000)`。

**所以"传 80%"这件事在 SDK 层面并不存在**：同一套默认值在不同窗口上算出来的比例不一样
（128K → 75.8%、200K → 84.5%、400K → 92.3%、1M → 94.2%），窗口越大压得越晚。

### 2.2 noa 路径：**有完整比例旋钮，但 ARTEX 一直没传窗口**

`noa/config.go: DefaultConfig(limit)` 里有：

```
Nudge.MaxContextLimitPct     = 0.75   // 压力带下沿：到这里开始提示模型压缩
Nudge.MinContextLimitPct     = 0.45
Nudge.EmergencyThresholdPct  = 0.95
Truncate.Threshold           = 0.95
```

`noaadapter/noa.go: newSession()` 的取值顺序是 `DefaultConfig(o.ModelContextLimit)`，`o.Config != nil` 时整体覆盖；
`ModelContextLimit == 0 && Config == nil` 才回落到 200000。

**改前的 `agent/noa.go: enableNoa` 只传了 `ArchiveBaseDir` / `SessionID` / `OnWarn`**，
于是：

- 用户把 `context_window_k` 设成 1M，noa 仍按 200K 算压力带 → 20 万 token 就开始催压缩，早了 5 倍；
- 用户把窗口设成 128K，noa 仍按 200K 算 → 压缩线跑到窗口外面，等于不压。

这条属于隐蔽 bug，本次一并修掉。

## 3. 方案选择：为什么"反解等效窗口"而不是改 SDK

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 反解等效窗口（**采纳**） | 先按 `ratio × 真实窗口` 定触发点，再倒推出一个让 SDK 恰好在此刻触发的 `ContextWindow` 传进去 | 不改 SDK、不动 go.mod、四条路径统一；等效窗口最多比真实窗口小 3%（1M 时 85.8 万），压缩时仍有充足余量 |
| B. norma 加 `AutoThresholdRatio` 字段 | 上游加一个显式比例字段，宿主直接传 0.80 | 语义最干净，但要改第三方 SDK（module 直依赖，无 vendor）→ 走 fork / replace，成本与升级风险都高。已作为**上游补丁建议**记入 `docs/norma-SDK优化补丁清单.md` #7 |
| C. 直接把 `0.8 × 窗口` 当 `ContextWindow` 传 | 最省事 | **否决**：micro 清退线（60%）与预测线会一起等比缩水，语义从"80% 触发压缩"漂成"所有阈值整体提前 20%"，小窗口会被压死 |

反解的做法（`agent/provider.go: compactionTriggerWindow`）：

```
目标触发点 target = ratio × 真实窗口
触发点 = x − 预留 − max(buffer, 15000)
∴ x = target + 8000 + max(buffer(x − 8000), 15000)
```

`x` 出现在 `buffer` 的分档里，取不动点即可（只有三档，四轮内收敛）。
若解出来比真实窗口还大（小窗口，固定开销占比过高），按真实窗口封顶——
**宁可早压，不能虚报窗口**：虚报会让"预估下一轮会不会超"永远算绿，直到 API 返 413。

## 4. 代码改动

### 4.1 `agent/provider.go`

| 符号 | 作用 |
|---|---|
| `defaultCompactRatio = 0.80` | 黄金比例常量（`[0.5, 0.95]` 夹逼） |
| `compactionSummaryReserve = 8000` | 与 SDK `reservedForSummary` 对齐，写入 `MaxOutputTokens` 钉死，避免默认值漂移 |
| `compactionTurnGrowth = 15000` | 与 SDK `toolResultGrowthGuess` 对齐 |
| `CompactionRatio()` | 读 `ARTEX_COMPACT_RATIO`（`0.8` 与 `80` 都认，越界夹逼，非法回落默认） |
| `compactionBuffer()` / `autoCompactThreshold()` / `predictiveCompactThreshold()` / `compactionTrigger()` | 把 SDK 的阈值算法抄一份，用于自检与反解，不参与实际决策 |
| `compactionTriggerWindow()` | 反解等效窗口，含封顶保护 |
| `compactionConfig()` | 改为传等效窗口 + 钉死摘要预留；四个 Agent 都经这里注入 |

### 4.2 `agent/noa.go`

- `enableNoa(...)` 新增 `window int` 参数：把用户窗口传进 `noaadapter.Options.ModelContextLimit`；
- 同时构造 `noa.DefaultConfig(window)` 并覆盖 `Config`，把 `Nudge.MaxContextLimitPct` 对齐 `CompactionRatio()`；
- 比例调高时按 `ValidateConfig` 的约束联动 `MinContextLimitPct`（`ratio × 0.6`）与 `EmergencyThresholdPct`（`ratio + 0.15`，上限 0.99），避免只告警不生效。

### 4.3 四个调用点

| 文件 | 位置 | 传入的窗口 |
|---|---|---|
| `agent/chat.go` | `:176` | `c.window`（控制台聊天） |
| `agent/mainagent.go` | `:220` | `m.compactionWindow()`（主 Agent） |
| `agent/planner.go` | `:511` | `p.compactionWindow()`（规划器） |
| `agent/worker.go` | `:627` | `w.compactionWindow()`（工作 Agent） |

`compactionWindow()` 的 resolver 由各 Agent 在 `SetCompactionWindowResolver` 里注入，
读的始终是**当前 Provider** 的 `ContextWindowK` → 满足口径①。

## 5. 验证矩阵（按 SDK 真实算法手算，改动后与 `agent/provider_compaction_test.go` 对齐）

| 用户窗口 | 改前实际触发点 | 改前比例 | 改后触发点 | 改后比例 |
|---|---|---|---|---|
| 32K | 9,000 | 28.1% | 9,000 | 28.1%（封顶，SDK 原生行为） |
| 64K | 41,000 | 64.1% | 41,000 | 64.1%（封顶） |
| 100K | 77,000 | 77.0% | 77,000 | 77.0%（封顶） |
| 128K | 97,000 | 75.8% | 102,400 | **80.0%** |
| 200K | 169,000 | 84.5% | 160,000 | **80.0%** |
| 400K | 369,000 | 92.3% | 320,000 | **80.0%** |
| 1M | 942,000 | 94.2% | 800,000 | **80.0%** |

可精确命中 80% 的最小窗口是 155K（`0.8W + 31000 ≤ W`）；低于它时反解撞上限，
触发点提前但**绝不会晚于 80%**，这是刻意选择的安全方向。

单位测试（`agent/provider_compaction_test.go`）锁三件事：

1. 160K / 200K / 400K / 1M 四条窗口的触发点 == `80% × 窗口`（精确相等）；
2. 32K / 64K / 100K / 128K 不晚于 80%，且不早于窗口的 25%；
3. `ARTEX_COMPACT_RATIO` 的解析与夹逼。

## 7. 已知边界与上游建议

1. **等效窗口比真实窗口小**：1M 时传 858,000。SDK 的"剩余空间"判断会比真实略紧，
   属于安全方向；压缩发生后仍有 ≥14% 真实余量承载摘要输出。
2. **noa 是"提示模型压缩"**，不是立即压缩：压力带下沿设在 80%，
   模型实际提交压缩的时机通常在 80%~85%，符合"80% 左右"的容差。
3. **摘要预留钉死 8000 token**：若上游改 `reservedForSummary` 的分档，`provider.go` 里的两个常量需同步，
   单测会先红。
4. **上游补丁建议（新增 #7）**：给 `compaction.Config` 增加 `AutoThresholdRatio float64`（0 = 维持现状），
   LR 侧就不用再做反解；在此之前反解是成本最低且不改依赖的做法。
5. 本机不编译、不测试（项目约定），验证由云端 `release.yml` 的 `go build` / `go vet` / `golangci-lint` / `go test` 承担。
