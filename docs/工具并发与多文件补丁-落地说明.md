# 工具并发与多文件补丁：落地说明（2026-10-22）

> 现象：Agent 读写文件、打补丁时「像是一次只能动一个文件」，多文件任务来回很多轮，效率低。
> 结论：**不是模型不肯并行，是四层保守默认值叠加**；其中最大的一层是「除只读工具外，全部工具都被当成不安全＝独占」，任何一个系统工具进场都会把后面所有工具一起挡住。本次在**宿主侧**（不动 norma SDK）把四层逐层解开。

- **核验版本：** norma `v0.4.3`，本地模块缓存 `E:\Go\gopath\pkg\mod\github.com\!autumn-27\norma@v0.4.3`（只读核对）。
- **相关文档：** SDK 侧仍需上游改的部分见 [norma SDK 优化补丁清单](norma-SDK优化补丁清单.md) 第 8 条。

## 1. 诊断：四层叠加

### L1 提示词层：从来没有一句话让模型批量取文件

全仓检索：agent 侧提示词里 `并行`／`batch`／`multi_tool` **零命中**。模型于是按「读一个 → 看一眼 → 再要下一个」走，6 个文件就是 6 次完整模型往返。
每次往返都要重发整段上下文——**这是多文件任务慢的主因**（本地并行只省墙钟，省不掉往返）。

对照 Codex 的官方指引（[Prompting Guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)）是硬要求：
"Think first — decide ALL files/resources you will need"、"Batch everything"、"Never read files one-by-one unless logically unavoidable"。

### L2 调度层：不安全工具会挡住排在它后面的所有工具

SDK 的 `harness/streaming.go`（`streamExec`）是「FIFO + 独占」：

- `canStartLocked(safe)`：只要有一个正在执行的工具不安全，**任何**工具（包括后面的安全工具）都不能开始；
- `processQueue`：遇到一个起不来的不安全工具就 `break`，**队尾全部被挡住**；
- `drain`：结果按到达顺序放行，遇到第一个未完成的不安全工具就停。

并发上限本身不是瓶颈（`MaxConcurrency` 默认 10，`harness/query.go`）。

### L3 工具层：整个「写侧」都是独占，且没有多文件入口

本仓工具面按构造器分成两半（`agent/tools.go`）：

| 构造器 | 声明 | 覆盖 |
|---|---|---|
| `readTool` / `readExpTool` | `ReadOnly: true` + `Concurrent: true` | 已是并发安全：`list_*`、`graph_overview`、`node_detail`、`tactical_kb`、`human_verification_*` … |
| `writeTool` / `writeExpTool` | **什么都没声明** → fail-closed 独占 | `insert_assets`、`record_fact`、`report_finding`、`set_goals`、`set_constraints`、`add_intent`、`add_hint`、`prove_goal`、`goal_met`、`expand_digest`、`add_company_scope`、`add_task_scope`、`steer_work`、`kill_work`、`restart_work` |
| 直接 `actool.Build` 的探测/工具 | 只设 `ReadOnly: noStoreRo`，**没声明 `Concurrent`** → 独占 | `http_request`、`http_sequence`、`http_fuzz`、`web_recon`、`net_probe`、`dns_probe`、`codec_crypto`、`extract_data`、`binary_inspect`、`binary_lab`、`human_verification_flow` |
| SDK 默认工具 | `Read` 安全；`Write/Edit/MultiEdit` 未声明 | 写文件也独占 |

也就是说：**「记录一条事实」会把后面所有读写一起挡住，「改一个文件」会把一次 HTTP 探测一起挡住。** 这是「一次只能动一个文件」这个体感的最大来源。

### L4 正确性层：独占其实在防一个真 bug

同批两次改同一文件时，两边都读同一份底本、都报成功，后写静默覆盖先写。业界同族事故：
[opencode #53512](https://github.com/anomalyco/opencode/issues/53512)、
[deepagents #6297](https://github.com/langchain-ai/deepagents/issues/6297)、
[zcode-my-go #78](https://github.com/skeleton1231/zcode-my-go/issues/78)（10/10 静默丢失）。

所以改法不是「把独占去掉」，而是**把独占从「全局」收窄到「真正冲突的资源」**。

## 2. 业界对照

| 做法 | 代表 | 要点 | 本次采用 |
|---|---|---|---|
| 批次分区 | Claude Code `partitionToolCalls` | 安全性是**每次调用**的属性；连续安全调用合批，不安全单独成批；上限默认 10 | 部分（保留 SDK 调度，只改每个工具的安全声明） |
| 路径/资源分组 | ZCode `scheduler.ts`、zcode-my-go `PathGroupable` | 按资源解析；**同组内顺序、异组并行**；解析失败保守串行；破坏性工具永不并行 | **采用**（`tools_concurrency.go`） |
| 单次多文件补丁 | Codex `apply_patch`（V4A） | 一次调用内含 Add/Update/Delete/Move 多个 FileOp，按上下文锚点匹配并逐级降级 | **采用**（`tools_patch.go`，改用 JSON 入参以走 schema 校验） |
| 原子写 + 版本闸 | gemini-cli #29499、Zoo-Code #1375 | 临时文件 + `rename`；Windows 对 `EBUSY/EPERM/EACCES` 重试；读时记 hash、写时校验 | **采用原子写**；hash 闸留作后续 |

## 3. 本次落地

### 3.1 `agent/tools_concurrency.go`：把「独占」收窄成「资源键」

一套进程内按键分片的读写锁 + 一张声明表，键只有四个命名空间：

| 键 | 语义 | 归属 |
|---|---|---|
| `""`（全局） | 写锁独占一切 | `Bash`、`shell_*`、`ExecuteExtraTool`、以及**所有未登记的新工具**（fail-closed） |
| `graph` | 任务内探索图 + 资产图 + 目标/意图（读共享、写独占） | `record_fact`、`insert_assets`、`report_finding`、`set_goals`、`add_intent`、`steer_work`… 与其读侧 `list_*`、`graph_overview`… |
| `file:规范化路径` | 单文件（读共享、写独占） | `Read` / `Write` / `Edit` / `MultiEdit` / `apply_patch` |
| `mcp:服务名` | 一个 MCP 服务（同服务串行、跨服务并行） | `mcp__<服务>__<工具>` |

另有一档**无键**（与谁都不冲突）：所有只读工具，外加显式登记的「不碰进程内共享状态」的工具——
`http_request`、`http_sequence`、`http_fuzz`、`web_recon`、`net_probe`、`dns_probe`、`codec_crypto`、
`extract_data`、`binary_inspect`、`binary_lab`、`human_verification*`、`tactical_kb`、`Sleep`。
判据：每次调用自带 HTTP 客户端或纯计算；唯一共享落点是流量库，而流量库本来就是并发安全的（MITM 代理长期多协程写它）。

**覆盖方式**：`agent/assembly.go` 的 `AugmentTools` 是**所有**工具的必经之路（内置 + 领域 + 技能 + MCP + 宿主 + 自定义），在那里统一套一层 `lockResources`：

```go
out[i] = guardPanicWithBreaker(lockResources(t), lb)
```

于是 78 个系统工具、SDK 工具、MCP 工具一次性全部获得并发语义，**不需要逐个改构造器**；将来新加的工具默认落在「全局独占」这一档（fail-closed），要并行必须显式登记——这也是 registry 里 `concurrentSafe` 元数据的同一套思路（ZCode）。

锁本身：`map[键] → *RWMutex`（引用计数归零回收）+ 一把 `global` 兜底；非全局调用一律先取 `global` 读锁，因此只被全局独占的工具挡住；多键（`apply_patch`）按字典序获取，不会死锁。

冲突矩阵（改造前 → 改造后）：

| 组合 | 改造前 | 改造后 |
|---|---|---|
| `Edit a` ‖ `Read b` | 串行 | **并行** |
| `Edit a` ‖ `Edit b` | 串行 | **并行** |
| `Edit a` ‖ `Edit a` | 串行 | 串行（同 file 键） |
| `record_fact` ‖ `Edit a` | 串行 | **并行** |
| `record_fact` ‖ `http_request` | 串行 | **并行** |
| `record_fact` ‖ `report_finding` | 串行 | 串行（同 graph 键，共享图状态） |
| `http_request` × N | 串行 | **全并行** |
| `Bash` ‖ 任何工具 | 串行 | 串行（全局键，作用面无法解析） |
| `mcp__A__x` ‖ `mcp__B__y` | 串行 | **并行**（跨服务） |

### 3.2 `agent/tools_patch.go`：`apply_patch` 多文件原子补丁

入参：`{"patches":[{"file_path":"...","edits":[{"old_string":"...","new_string":"...","replace_all":false}]}]}`。

执行分两阶段，**全有或全无**：

1. **校验 + 内存应用**：按出现顺序读入目标文件、逐处应用精确替换。任一处 `old_string` 找不到 / 不唯一 / 与原串相同 → 直接返回错误并**一个文件都不写**。
2. **落盘**：逐文件原子写；中途失败则回滚已写文件，错误信息说明回滚了几个。

细节：同一 `file_path` 出现多次会按顺序合并编辑；只改已存在的文件（新建请用 `Write`）；上限 40 文件 / 200 处编辑；结果只回「哪个文件几处」，不回正文。
加锁由装配层按 `patches[].file_path` 统一施加（工具内部不再自己加锁——同一把 `sync.RWMutex` 不可重入）。

### 3.3 段 [D] 工具调用批量规约（提示词层）

`toolBatchSpec()` 作为**代码持有的尾段**追加到 mainagent / planner / worker / chat（含三套软逆变体）的系统提示，位置在 `langDirective` 之前，因此和 `artifactSpec` 一样**改 DB 正文也丢不掉**。四条：动手前把这一轮要碰的东西想齐、独立读取放同一条消息、跨文件改动一次 `apply_patch`、只有依赖关系才拆多轮。

### 3.4 接入面

| 位置 | 改动 |
|---|---|
| `agent/assembly.go` | `AugmentTools` 末层套 `lockResources`（全部工具的唯一漏斗） |
| `agent/mainagent.go`、`planner.go`、`worker.go`、`chat.go`、`tool_lean.go` | `actool.DefaultTools()` → `SDKDefaultTools()`；系统提示追加段 [D] |
| `agent/worker.go` | 非软逆 worker 的 `trimSDK` 一并裁掉 `apply_patch`（与 `Write/Edit` 同等对待，软逆 worker 保留） |
| `intercept/intercept.go` | `apply_patch` 进 `defaultEnabledTools`——写类工具不能有拦截规则体系的后门 |
| `guard/guard.go` | 审计记录 `apply_patch` 的目标文件列表（否则审计里会出现「改了东西但 command 为空」） |
| `web/messages/zh.json`、`web/src/app/(main)/system/intercept/page.tsx` | 拦截页工具说明与写类工具清单补 `apply_patch` |

`apply_patch` 不进 `tools` 表（与其它 SDK 通用工具一致）：无 DB 行 → `ToolResolve` 原样放行，不受「按 agent 绑定」过滤。

## 4. 语义边界与残留窗口（必须知道）

1. **同资源 FIFO 不保证**：调度器按队列顺序**启动** goroutine，锁的**获取**是竞态的。同批次里 `[Edit a, Read a]` 有小概率让 Read 先拿到共享锁、读到改前内容。跨批次（模型看到结果后再读）不受影响。要绝对顺序需要 SDK 按队列序号派发（补丁清单第 8 条）。
2. **graph 键是保守合并**：探索图/资产图/目标意图/worker 控制共用一把读写锁，因此 `record_fact` 与 `report_finding` 仍然互斥。这是刻意的——它们改的是同一批进程内图对象，而本仓的工具 handler 没有细粒度锁。要再拆细需要逐个工具证明它只碰哪个子结构。
3. **未登记的工具 = 全局独占**：新加工具若忘了登记，行为与改造前一致（不给并发，也不出错）。这是 fail-closed 的另一面。
4. **`Grep/Glob/LS` 不参与文件键**：它们的作用面是目录或模式，锁不到具体文件；而 SDK 的 `Write/Edit/MultiEdit` 仍是 `os.WriteFile`（非原子），所以「同一文件的写进行中」并发执行 `Grep` 理论上可能看到半截内容。`Read` 已被文件键保护。收口办法是把三个写工具也换成宿主实现、统一走 `writeFileAtomic`（P3）。
5. **等等锁会占并发槽**：等待锁的调用已经进入 SDK 的并发信号量（默认 10 个槽），同批 10 个以上冲突调用时，后面的非冲突调用要等槽释放。极端批次下比改造前稍差，正常任务感知不到。
6. **结果配对不变**：并行只改执行时序，每个 `tool_use` 仍对应唯一 `tool_result`。

## 5. 验收

CI 门禁（本仓约定：不在本地 build/test/lint）：

- `gofmt` 门禁（`release.yml`）：新增/改动文件必须零 diff。本次为此刻意规避「多行嵌套 map 字面量的列对齐」与「const 组对齐」——schema 用单行字面量 + 辅助闭包，工具名集合用 `nameSet(...)` 变参函数，常量拆成独立声明。
- `go vet ./...`、`golangci-lint run`（仅 govet）。
- `go test ./agent/...`：`prompt_test.go` 断言的是「正文前缀 + 尾段包含 + langDirective 在最后」，段 [D] 插在 `langDirective` 之前不破坏任何断言。
- 需盯一眼：`TestToolSchemaSlimmingMeetsBudget` 要求三套工具面省 ≥40%，`apply_patch` 进入工具面后分子分母同时变化，理论上比例不变，但这是唯一一个「数值型」既有断言。

人工验收：

1. 「改 5 个文件、每个 2 处」：改造前约 5 轮工具往返，改造后应为 1 轮（一次 `apply_patch`）。
2. 「读 6 个文件再总结」：应为 1 轮 6 个 `Read` 并行。
3. `apply_patch` 里一处的 `old_string` 不匹配：应返回「本次调用未修改任何文件」+ 定位到文件与第几处，磁盘无任何改动。
4. 同一文件并行两次 `Edit`（同批）：两处改动都生效。
5. `record_fact` 与 `http_request` 同批：墙上应看到 HTTP 探测不再等写库。
6. 连续 `Bash`：应仍然串行（全局键）。

量化指标（建议进面板，本次未接）：

| 指标 | 采集点 | 目标 |
|---|---|---|
| 单轮工具调用数 | harness 事件流 | 读密集任务从 ~1.0 提到 ≥3 |
| 任务内模型往返次数 | `activity` 表 | 同任务下降 ≥40% |
| 工具墙钟利用率 | `Σ工具耗时 / 墙钟` | 从 ~1.0 提到 ≥2.0 |
| 键冲突等待时长 p95 | 锁埋点（未接） | < 200ms |
| 丢失更新事件 | 同 file 键冲突计数 | 恒为 0 |
