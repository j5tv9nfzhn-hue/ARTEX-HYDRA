# ARTEX-REA 自动更新流程 · 全面分析

> 分析基线：`main` @ `7b06ba7`（v2.2.2 + 项目总结提交）
> 方法：**只读源码 + git/CI 元数据**；遵守 `AGENTS.md`，未在本机执行任何编译/测试/构建，本文不含运行期结论。
> 覆盖范围：`selfupdate/`（4 文件）+ `server/update.go` + `cmd/artex/main.go` + `start.sh`/`start.bat` + `web` 更新卡片/红点 + `.github/workflows/release.yml` + `scripts/gen-update-manifest.py`

## 0. 结论摘要

这套自更新是**「下载/校验在 Go、换装靠退出码、稳定靠标记文件」**的三方协作设计，核心取舍非常明确：

| 设计决定 | 代价 | 收益 |
|---|---|---|
| 换装逻辑全部放在 Go（脚本只管拉起） | 需要跨次进程的握手协议（退出码 75 + marker 文件） | 只需维护一份 sha256/冒烟逻辑，sh 与 bat 各自保持 20 行量级 |
| 进程不自我重启，用 `exit 75` 交给守护脚本 | 必须有 `start.sh`/`start.bat`；双击 exe 时能力退化 | 避免「进程 fork 自己」在各平台的坑；重启策略集中在一处 |
| 下载走完整 zip 而不是裸二进制 | 多下载几百 KB 的 skills | 复用既有的 `SHA256SUMS`（只覆盖 zip），**不改 CI**，兼容已发布的历史版本 |
| 检测优先走 `latest.json`（网页别名） | 多发一个资产、多一次请求 | 不消耗未认证 API 的 60 次/小时/IP 配额 |
| 自动更新只「暂存」不「切换」 | 需要用户下次重启才生效 | 绝不在渗透任务跑到一半时重启进程 |
| 换装后连续失败自动回滚 | 实现复杂度 + 3 次崩溃窗口 | 避免"更新完打不开、只能上机器救"的死局 |

**一句话**：这是一条**双闸门（域名白名单 + SHA256）+ 可回滚 + 可观测（SSE 进度）**的成熟更新链路，工程完成度高于绝大多数同类项目；主要短板集中在**信任锚（无签名）**和**几个入口缺少能力位校验（非守护部署、容器内、旧暂存件无版本护栏）**，见第 8 节。

## 1. 全景时序（一次成功升级跨 3 次进程启动）

```
[浏览器]                [旧版进程]                      [守护脚本]            [新版进程]
   │  POST /api/update/apply                                 │                    │
   │──────────────────────►│ ① 取 Release（缓存优先）        │                    │
   │                       │ ② checkWritable 预检            │                    │
   │                       │ ③ 取 SHA256SUMS → 下载 zip      │                    │
   │                       │ ④ 边下边算 sha256，比对清单      │                    │
   │                       │ ⑤ 解压出 artex-rea → .new.part  │                    │
   │                       │ ⑥ 冒烟：.new -h（30s 超时）      │                    │
   │                       │ ⑦ 写 .new.sha256 → rename .new   │                    │
   │                       │ ⑧ 写 marker{from,to,attempts:0}  │                    │
   │◄── SSE staged ────────│ ⑨ 等 1.5s → requestRestart      │                    │
   │                       │ ⑩ 优雅关闭 → 退出码 75           │                    │
   │                       │────────────────────────────────►│ 见到 75 → 立即重拉  │
   │                       │                                 │───────────────────►│
   │                       │                                 │      Bootstrap()   │
   │                       │                                 │  a. 有 .new → 重算 sha256
   │                       │                                 │  b. 再冒烟一次
   │                       │                                 │  c. swap: 当前→.old，.new→当前
   │                       │                                 │  d. Restart → 退 75 │
   │                       │                                 │◄───────────────────│
   │                       │                                 │ 见到 75 → 立即重拉  │
   │                       │                                 │───────────────────►│
   │                       │                                 │   （本次跑的就是新版）
   │                       │                                 │      Bootstrap()   │
   │                       │                                 │  e. 只剩 marker → attempts=1
   │                       │                                 │  f. 正常启动（开库/绑端口）
   │                       │                                 │  g. 30s 后 Settle() → 删 marker
   │  GET /api/health 轮询  │                                 │                    │
   │──────────────────────────────────────────────────────────────────────────────►│
   │◄── version 变化 → 整页刷新 ───────────────────────────────────────────────────│
```

**关键点**：`Bootstrap()` 在 `main.go` 里排在**开库与绑端口之前**（`cmd/artex/main.go#run`），因此换装失败不会留下半开的数据库或占着的端口；`Settle()` 用 `time.AfterFunc(selfupdate.SettleDelay=30s)` 注册，晚于 HTTP 监听启动，用来判定"新版活下来了"。

## 3. 七个阶段逐一拆解

### 阶段 1｜检测（Detection）

**两条通道，先清单后 API**（`selfupdate/github.go#FetchLatestWithFallback`）：

| 通道 | URL | 配额 | 用途 |
|---|---|---|---|
| 主 | `https://github.com/<Repo>/releases/latest/download/latest.json` | **0**（网页别名，不计 API 配额） | 日常检测默认走它 |
| 备 | `https://api.github.com/repos/<Repo>/releases/latest` | 未认证 **60 次/小时/IP** | 清单缺失/异常时回落；403/429 会返回明确的中文限流提示 |

**缓存策略**（`server/update.go#releaseCache`）：

- 成功结果 TTL **30 分钟**；失败结果 TTL **2 分钟**（网络恢复后能自愈，又不至于每次页面加载都干等超时）
- 取数期间**一直持锁**：多个标签页同时来查会排队等同一次结果，而不是各自去打 GitHub
- 显式点「检查更新」带 `force=1` 绕过 TTL；请求被取消（关标签页）不写缓存，避免污染
- 顶栏红点走 `/api/update/status`，**只读快照、绝不发网络请求**（自动检测关掉时它永远不亮）

**自动检测**（`startUpdateWatcher` / `updateTick`）：

```
启动后 90s 首查（避开首屏抢带宽） → 每 6h 一拍
每拍现读 update_auto_check 开关（关掉后下一拍就不再出网，无需重启）
comparable?  → 开发构建（dev / git describe 带后缀）直接跳过
已有对应平台 asset? → 没有则跳过（避免"提示有新版却装不了"）
InDocker?      → 跳过（换装只改容器可写层）
已暂存同版本?  → 跳过
update_auto_apply 开且 updHub 空闲 → stageUpdate(restart=false)
```

### 阶段 2｜下载与校验（Stage）

`selfupdate/stage.go#Stage` 的**严格顺序**（顺序本身就是安全设计）：

1. `checkWritable(dir)`：在目标目录建临时探测文件再删。**提前**发现"装在 `C:\Program Files` 但非管理员"这类问题，而不是下完几十 MB 才失败。
2. `AssetName(tag, GOOS, GOARCH)` → 在 Release 资产里精确查找（`artex-rea-<ver>-<os>-<arch>.zip`，版本号去 `v` 前缀，与 `build.sh` 的 `package_binary` 对齐，有单测 `TestAssetNameMatchesBuildScript` 守着）。
3. `fetchSums`：先取 `SHA256SUMS`。**若清单里没有该资产条目，按固定命名拼 URL 再试一次**，仍失败则**拒绝更新**（"拒绝安装未验证的二进制"）。
4. `download`：写入 `<exe>.new.zip.part`，`io.MultiWriter(file, sha256, progressWriter)` 边写边算，进度 **300ms 限频**；结束后校验 `Content-Length` 一致（不完整即失败）。
5. 摘要比对：`SHA256SUMS` 里该 zip 的期望值 vs 实算值，大小写不敏感；不匹配直接失败并提示"下载内容损坏或被篡改"。
6. `extractBinary`：zip 内**按基名**匹配 `artex-rea(.exe)`（兼容旧名 `artex`），限 **512 MiB**，写 `<exe>.new.part`，权限 `0755`。
7. `extractSkills`：顺带把 zip 里的 `skills/` **增量补齐**（只补缺失文件，不覆盖用户修改，跳过含 `..` 的路径）。
8. `smokeTest`：`chmod 0755` 后执行 `<exe>.new -h`，**30s 超时**，子进程环境带 `ARTEX_SELFUPDATE_SMOKE=1` 让它跳过 Bootstrap（显式短路，不依赖"路径带 .new 所以碰不到"这种巧合）。挡掉：下载截断、架构选错（exec format error）、动态链接缺失。
9. 二次校验和：把 `.new` 自身的 sha256 写进 `<exe>.new.sha256`（**供下次启动换装前再校验一次**，防止暂存后到重启前文件被改动/写坏）。
10. `rename .new.part → .new`，写 `marker{from,to,attempts:0,staged_at}`；marker 写失败只告警（失去自动回滚能力，但暂存件已就位，不中断升级）。
11. 回调 `PhaseStaged` → 调用方决定是否 `requestRestart()`。

> **为什么临时文件都落在目标目录**：保证最后一次 `rename` 是同文件系统内的原子操作（`/tmp` 常是独立挂载点，跨设备 rename 会失败）。

### 阶段 3｜暂存生效（Swap，下一次启动）

`selfupdate/bootstrap.go#Bootstrap` 三种局面：

| 磁盘状态 | 函数 | 行为 |
|---|---|---|
| 存在 `<exe>.new` | `applyStaged` | `verifyStaged`（重算 sha256 比对 `.new.sha256` + 再冒烟）→ 失败则 `cleanStaged` 删暂存件与 marker，**继续跑旧版**；成功则 `swap` → 返回 `Restart` |
| 只有 marker | `confirmOrRollback` | `attempts++`；`> maxAttempts(3)` → `rollback`；否则继续启动并等待 `Settle` |
| 都没有 | — | 正常启动 |

`swap`（唯一会覆盖可执行文件的地方）：

```
删 .old（Windows rename 不覆盖已存在目标，必须清） → 当前 → .old → .new → 当前
第二步失败则把 .old 原样 rename 回当前（否则下次启动没有可执行文件）→ 删 .new.sha256
```

> 之所以不分平台：Unix 和 Windows **都允许 rename 一个正在运行的可执行文件**（Windows 禁止的是删除与覆盖，rename 不在其列），所以不需要先停掉自己。

### 阶段 4｜稳定确认（Settle）

`main.go` 在 `NewManager` 与 HTTP 服务就绪后注册 `time.AfterFunc(30s, selfupdate.Settle)`；`Settle` 发现 marker 存在就删掉，日志打印"新版本运行稳定，升级完成（上一版本保留为 .old）"。

- 计数器**只在 Go 代码跑起来后才递增**，所以它覆盖的是"能执行但初始化时崩溃"（配置不兼容、端口被占、DB 迁移炸了）；
- "根本无法 exec" 由换装前的冒烟测试挡住。两者合起来才完整。
- 副作用：`Settle` 只看"进程活过 30 秒"，**不校验 HTTP 就绪/业务可用**——监听成功但功能坏掉的情况会被判为升级成功。

### 阶段 5｜失败与回滚

| 触发 | 行为 |
|---|---|
| 暂存校验/冒烟失败 | 删 `.new`/`.sha256`/marker，继续跑旧版，`State.FailedStage=true`，前端显示"上次升级提示" |
| 换装后连续 3 次启动未活到 Settle | `rollback`：当前（坏版）→ `.failed` 留作排查，`.old` → 当前，删 marker，`exit 75` 回到旧版 |
| 回滚本身失败 | 删 marker 并按当前状态启动（不再重启，避免无限循环），日志给出原因 |
| 手动回滚 `POST /api/update/rollback` | 无 `.old` → 400；先对 `.old` 冒烟（起不来就拒绝回滚）；三文件轮换（当前→`.swap`，`.old`→当前，`.swap`→`.old`）→ 删 marker → 500ms 后 `requestRestart` |
| 崩溃退出（非 0/非 75） | 守护脚本 **1→2→4…60s** 指数退避重启；每次启动 marker 计数 +1 |

### 阶段 6｜进度与前端呈现

- `POST /api/update/apply` **立即返回 202**，真正下载在后台 goroutine 上跑（挂在请求上会被反代超时掐断）。
- 进度走 `GET /api/update/stream`（SSE）：订阅时**先补一条当前状态**（刷新页面也能立刻看到进行中的升级）、20s 心跳 `: ping`、每订阅者 64 缓冲，**满了就丢**（进度是可丢弃信息，绝不能让卡住的连接阻塞升级）。
- `updateHub.running` 同时充当**互斥**：升级中再次 apply → `409 已有更新正在进行`；升级中回滚 → `409 正在更新，无法回滚`。
- 前端 `update-card.tsx`：只有点了「立即更新」才建立 SSE（平时不占长连接）→ 收到 `staged` 后进入 `restarting` → 每 **2s** 轮询 `/api/health`，发现 `version` 变了就整页刷新。

### 阶段 7｜部署前提

| 前提 | 不满足时的后果 |
|---|---|
| 用 `start.sh` / `start.bat` 启动（`ARTEX_SUPERVISED=1`） | 换装后 `exit 75` 没人拉起 → **服务停止**，需手动启动（下次启动才应用新版）；`auto_apply` 开关会被禁用，但「立即更新」按钮**当前不受此限制**（见 8.1） |
| 程序目录可写 | `checkWritable` 提前失败并给出中文原因 |
| 服务器能访问 GitHub | 检测/下载失败；错误会如实回传（"浏览器能连不等于服务器能连"，所以**以服务端结果为准**） |
| 代理配置 | 复用 `Manager.GlobalProxy()`（`global_proxy` 设置，即"目标流量出口代理"），空则直连 |
| 非容器 | `InDocker()` 为真时：`updateTick` 跳过、UI 禁用自动下载并提示"请拉取新镜像" |

## 4. HTTP / SSE 契约

| 端点 | 语义 | 关键返回 |
|---|---|---|
| `GET /api/update/check?force=1` | 查最新正式版并与当前比较 | `current/latest/notes/html_url/published_at/asset/size/asset_available/comparable/has_update` + `mode(binary|docker)/os/arch/has_backup/repo/boot_notice/rolled_back/supervised/staged_version/auto_check/auto_apply` + 可选 `reason/error` |
| `POST /api/update/apply` | 暂存并退出换装 | `202 {ok,target[,staged]}`；`400` 不可比较/已最新；`409` 进行中；`502` 取版本失败 |
| `POST /api/update/rollback` | 手动回滚 | `202`；`400` 无备份/旧版无法执行；`409` 升级中 |
| `GET /api/update/stream` | SSE 进度 | `{phase,percent,message,version?,error?}`，phase ∈ `idle/downloading/verifying/extracting/staged/failed` |
| `GET /api/update/status` | 只读缓存快照 | `checked/checked_at/latest/has_update/staged_version`，**绝不发网络请求** |

**鉴权**：`server.go` 里 `api := cors(s.requireAuth(mux))`，仅 `/api/auth/*` 与 `/api/health` 豁免 → 上述 5 个端点都在 JWT 之后（单管理员模型，即管理员本人）。

**两个开关**（存 `settings` 表而非 localStorage，多浏览器/多客户端一致）：

| 键 | 默认 | 语义 |
|---|---|---|
| `update_auto_check` | **开** | 每 6h 只读版本清单，不下载不改动 |
| `update_auto_apply` | **关** | 查到后**自动下载并校验**，下次启动生效（不重启、不打断任务） |

## 5. 状态与文件模型

| 文件（同目录，`ResolvePaths`） | 含义 | 生命周期 |
|---|---|---|
| `artex-rea(.exe)` | 当前运行的二进制 | 被 swap 替换 |
| `artex-rea.new(.exe)` | 已下载校验的暂存件 | 换装成功即消失 |
| `artex-rea.new(.exe).sha256` | 暂存件摘要（防落地后被改） | 换装后删除 |
| `artex-rea.new.zip.part` | 下载临时件 | `defer` 保证清理 |
| `artex-rea.old(.exe)` | 上一版本，回滚目标 | **常驻**（这是"能回滚"的代价，约一个二进制大小） |
| `artex-rea(.exe).failed` | 自动回滚时留存的坏版本 | 常驻（便于排查） |
| `artex-rea.upgrade.json` | `{from,to,attempts,staged_at}` | `Settle` 后删除 |

| 退出码 | 含义 | 脚本行为 |
|---|---|---|
| `0` | 正常停止 | 退出循环（不再拉起） |
| `75`（`EX_TEMPFAIL`） | "请重新拉起我"，用于换装/回滚 | **立即**重跑，不计入崩溃退避 |
| 其它 | 崩溃 | 指数退避重启，上限 60s |

窗口侧额外保护：`main.go` 在 Bootstrap 之前调用 `guardProcessTree()`，把进程放进 kill-on-close 的 Job Object，换装重启时不会留下跑到一半的 `powershell`/`python` 孤儿。

## 6. 安全闸门清单（共 8 道）

| # | 闸门 | 实现 | 拦住的攻击/故障 |
|---|---|---|---|
| 1 | 更新源**构建期固定** | `Repo` 由 `-ldflags -X ...selfupdate.Repo` 注入；`init()` 用 `^[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+$` 校验，非法直接 panic；注释明确"不回落上游、不在运行时改" | 换源 = 远程代码执行通道；上游仓库 404 导致更新链路静默全断（历史事故） |
| 2 | **仅 HTTPS** | `checkURL` 强制 `Scheme == https` | 明文降级 |
| 3 | **域名白名单 5 个** + 每一跳重定向校验 + 最多 10 跳 | `allowedHosts`（`api.github.com` / `github.com` / `objects.githubusercontent.com` / `release-assets.githubusercontent.com` / `raw.githubusercontent.com`） | DNS 污染、中间人把资产换掉 |
| 4 | 独立 `http.Transport` | 不复用默认 Transport，杜绝别处设置的 `InsecureSkipVerify` 影响升级链路 | 全局降级 TLS 校验 |
| 5 | **SHA256SUMS 先取后下**，缺条目即拒绝 | `fetchSums` + `parseSums`（首字段必须是 64 位 hex，防止把说明文字当条目） | 篡改/损坏的 zip |
| 6 | 暂存件**二次校验** | `.new.sha256` 在换装前重算比对 | 暂存 → 重启之间的落盘改动/写坏 |
| 7 | **冒烟测试** | `<exe>.new -h`，30s 超时 | 下载截断、架构选错、缺动态库 |
| 8 | **版本可比较才放行** | `parseVersion` 只认纯净三段式；`dev`/`git describe` 后缀一律 `comparable=false`，`updateCheck` 与 `updateTick` 双向拒绝 | 用正式版覆盖本地调试构建、覆盖未提交改动 |

**发布侧配套**（保证上面这些真的成立）：

- `gen-update-manifest.py` 用 `TAG_RE=^v\d+\.\d+\.\d+$` **拒绝带后缀的 tag**（否则所有客户端判定不可比较、一键更新静默全禁用）；
- `SHA256SUMS` 由 `sha256sum -- *.zip` 生成，`latest.json` 里**同时列出 zip 与 SHA256SUMS**（这是 v2.2.1 的修复：清单只列 zip 会导致升级在校验阶段报"缺少 SHA256SUMS"而拒绝更新）；
- 发布用**草稿**：先建 draft（外部不可见）→ 传全部资产 → `diff` 断言"6 zip + SHA256SUMS + latest.json"齐全 → 才 `--draft=false`；任一步失败 `if: failure()` **删草稿、保 tag**，可原地重跑。

## 8. 问题清单（按严重度）

### 8.1 P1｜「立即更新」缺少 `supervised` 校验 → 非守护部署会把自己关掉

**现状（2026-10-22 已修）**：双击 `artex-rea.exe`、没有脚本时，旧代码会走到 `400 不支持一键更新`，
或者更糟：按钮能点、装完 `exit 75` 却没人拉起，进程当场停机。

**处置**：
- 后端不再要求 `selfupdate.Supervised()`。进程自己会拉起新进程重开（`ExitForRestart` → 写意图 →
  `Relaunch`），`Supervised()` 只影响"是不是自己拉"还是"交给脚本"这条路径选择。
- 唯一保留的硬条件仍是容器内不能一键换装（换完没人拉起），那条由 `InDocker()` 单独判断，
  并且在拿安装锁**之前**判断，不会占着锁不放。
- `GET /api/update/check` 的 `supervised` 字段语义改为"当前环境能否自动重启"（即 `CanRestartSelf()`），
  前端 `update-card.tsx` 的风控文案同步改成"装好后会自动重启生效"，不再提示需手动重启。
- `canApply` 保持原样：docker 已被 `mode === "docker"` 排除，其余情况都能点。

### 8.2 P1｜容器内 `apply` 未被后端拦截

`updateTick` 有 `if selfupdate.InDocker() { return }`，UI 也把 `canApply` 排除了 docker，但 **`updateApply` 本身没有容器判断**。容器里若直接调用 API（或 UI 判断被绕过），会在容器可写层暂存并 `exit 75`；若 ENTRYPOINT 不是循环脚本，容器直接退出，是否回来取决于编排的 restart policy。修法同上：`updateApply` 增加 `400`。

### 8.3 P2｜信任锚只有 SHA256，没有签名

`SHA256SUMS` 与 `latest.json` 都发布在**同一个 Release**、由同一个 `GH_TOKEN` 产生，客户端只做 `https + 域名白名单 + sha256 比对`。也就是说：**信任锚 = GitHub 账号 + TLS**。仓库被接管（或 CI 令牌泄露）时，攻击者可以同时替换二进制与摘要，这套链路会"正确地"装上一个恶意版本。

**已存在但未用上的加固点**：`gen-update-manifest.py` 已经在 `assets[].sha256` 里写了每个 zip 的摘要，但 Go 侧 `selfupdate.Asset` 结构体只有 `Name/URL/Size`，**这个字段被丢弃了**。零成本改进：把 `latest.json` 内嵌的 `sha256` 与 `SHA256SUMS` 做**双源交叉校验**（不一致即拒绝）。

**更彻底**：Release 附 `SHA256SUMS.sig`（minisign/cosign keyless）或在 `latest.json` 里放签名，客户端内置公钥验签；这会把信任锚从"GitHub 账号"挪到"私钥持有者"。

### 8.4 P2｜暂存件无版本护栏：可能被"降级安装"

`Bootstrap → applyStaged` 只校验摘要与可执行性，**不比较 marker.To 与当前版本**。场景：用户在 v2.3.0 时自动暂存了 v2.4.0（未重启），随后手动换成了 v2.5.0 的包；下次启动时 `.new`（v2.4.0）仍会被装上 —— **等于静默降级**。`marker.staged_at` 字段也没有任何过期判定，几个月不重启的实例会在某天突然应用一个很旧的暂存版本。

**修法**：`Bootstrap` 接收当前版本号（`main` 里的 `version` 变量），在 `applyStaged` 里用 `CompareVersions(marker.To, current)`，`<= 0` 或 `staged_at` 超过 N 天（如 30）则 `cleanStaged` 丢弃。

### 8.5 P2｜内置技能的内容修复无法通过升级下发

`skills/embed.go#EnsureBundled` 与 `selfupdate/stage.go#extractSkills` 都遵循"**磁盘已存在则不覆盖**"（为保护用户在 Web UI 里的修改）。后果是：随版本发布的内置技能（`api-recon`、`rea-mcp`、`wpe64-mcp` …）一旦落盘，后续版本对**同名文件**的修正**永远不会到达已有安装**——只有全新安装或用户手动删文件才会更新（唯一例外是 `retiredSkills` 白名单里的下线目录会被主动删除）。

**建议**：给内置技能加版本戳（每个技能包一个 `version` 或 `manifest.json` 里的 hash），启动时比对：**内置版本更新且用户未修改（hash 与上次落盘一致）→ 覆盖**；用户改过 → 保留并在 UI 提示"内置技能有更新，是否覆盖"。这既保住用户修改，又让技能修复能真正下发。

### 8.6 P2｜回滚后再"回滚"会回到坏版本

手动回滚的实现是**三文件轮换**（当前→`.swap`，`.old`→当前，`.swap`→`.old`），注释写明"回滚之后还能再滚回来"。这在"误回滚"时是优点，但在"新版确实坏了"的场景里，用户在 UI 上再点一次「回滚到上一版本」，会**把刚回滚掉的坏版本装回来**。而 UI 只按 `has_backup` 显示按钮，不区分 `.old` 是"上一稳定版"还是"上次回滚留下的坏版"。

**建议**：把 `.failed` 的存在（或 marker 里的回滚记录）纳入 `/api/update/check`，UI 对"回滚目标疑似坏版本"加二次确认与明确文案。

### 8.7 P3｜若干工程细节

| 项 | 说明 | 建议 |
|---|---|---|
| 下载无断点续传/重试 | 几十 MB 的中断要从头再来；`Client.Timeout` 30 分钟内无进展也会整体失败 | 加 `Range` 续传或 2 次指数退避重试 |
| 无磁盘空间预检 | 只在 `checkWritable` 里验证可写，不验证剩余空间是否够 zip + 解压 | 用 `asset.Size` 估算并预检（`fsutil` 已有原子写模块） |
| `updateCheck` 直接回传 `err.Error()` | 内部错误细节（含 URL/状态码）会展示给前端 | 分类成"网络不可达/限流/仓库无发布"三类友好文案 |
| `Settle` 只看存活 30s | 监听成功但业务坏掉会被判成功 | 可选：Settle 前做一次 `/api/health` 自检 |
| `auto_check` 默认开 | 对一个渗透平台来说，默认出网是 opsec/隐私考量点（虽然只读清单） | 保持默认开（合规要求已在文档写明），但首次启动时在 UI 明示 + 一键关闭 |
| 更新代理复用 `GlobalProxy` | 用户把"目标流量代理"设成一个不通 GitHub 的内网代理，更新链路会整体失败且难以归因 | 设置页文案区分，或提供独立的"更新/出网代理" |
| `.old` 与 `.failed` 常驻 | 每个约一个二进制的磁盘占用 | 文档写明；或加"清理旧备份"按钮 |

## 10. 总体评价

**做得好的地方（值得保留的设计）**

1. **错误处理的方向是对的**：所有失败路径都回落到"继续跑旧版"，而不是留下半装状态；`swap` 第二步失败会把 `.old` rename 回原位，`rollback` 失败会删 marker 保证不再无限重启。
2. **安全闸门分层清楚**：源固定 → https → 域名白名单 → 独立 Transport → 摘要 → 二次摘要 → 冒烟 → 版本可比性，每一层都能单独解释"为什么需要它"，且注释里写明了历史事故（上游仓库 404、清单缺 SHA256SUMS）。
3. **额度友好**：`latest.json` + 网页别名 + 30 分钟缓存 + 顶栏只读快照，把 GitHub 未认证配额的压力降到几乎为零——这是很多项目踩过的坑。
4. **不打断业务**：自动更新只暂存，绝不擅自重启；进度用 SSE 且可丢弃，不阻塞升级本身。
5. **可观测性**：`boot_notice`/`rolled_back`/`failed`/`supervised`/`staged_version` 都回传给前端，用户能看懂"上次升级发生了什么"。

**最该补的三件事**

1. ~~补三道闸门校验~~（第 23 条已完成，见第 9 节）：门禁从"有没有监护脚本"换成"当前环境能否自动重启"，`updateApply`/`updateRollback` 都加了跨进程安装锁。
2. **暂存件版本护栏**（8.4）：避免静默降级 / 过期暂存意外生效。
3. **信任锚升级**（8.3）：先用 `latest.json` 内嵌 sha256 做双源校验（零成本），再考虑签名。

> 本文所有判断均来自源码与 CI 配置的静态阅读；其中"服务会停止""会降级"等结论是**代码路径推导**，不是运行期实测——按仓库约定，确定性验证交给云端 `release.yml` 与真机。

## 9. 实施记录（2026-10-22，对应第 23 条）

目标：**不冲突**（双开不互杀、并发更新只有一个生效）且**不依赖 BAT**（双击 exe 就能完成一次更新），Windows / Linux / macOS 三端同时落地。

### 9.1 四件事与落点

| 事 | 落点 | 要点 |
|---|---|---|
| A. 重启意图 + 入口自监护 | `selfupdate/restart.go`、`selfupdate/relaunch_{windows,unix}.go`、`selfupdate/layout.go#Handoff` | 退出前写 `updates/restart.request`（原子、一次性、读后即删）；`Handoff` 由"单次转交"改成 `for` 监护循环，每轮重读 `pointer.json`，只在**有意图**时才拉起；无意图的正常退出/Ctrl-C 绝不自动重开。`relaunch_windows.go` 用 `CREATE_BREAKAWAY_FROM_JOB`（配合 `JOB_OBJECT_LIMIT_BREAKAWAY_OK`，否则 kill-on-close 会把新进程一起带走），`relaunch_unix.go` 用 `Setsid`。自拉窗口 5 次 / 5 分钟，超了不再拉，避免新版起崩把日志刷爆。 |
| B. 单实例锁 | `selfupdate/instance.go`、`instance_windows.go`、`instance_unix.go`、`cmd/artex/main.go` | Windows 命名互斥量 `Local\ARTEX-REA-instance-<sha1(安装根前 8 字节)>`，Unix `updates/instance-<hash>.lock` + `flock(LOCK_EX|LOCK_NB)`。**先拿锁再绑端口**，锁是唯一仲裁者。`WAIT_ABANDONED` = 上一任异常死亡 → 接管；拿不到就是 `LockBusy` → 只打印地址并 `exit 0`，**不再 terminateProcess**。自拉起来的新进程等 20s（`RelaunchLockWait`），普通双击只等 3s。 |
| C. 关机序列 | `cmd/artex/main.go` | 收到重启信号后：停止接受新请求 → grace（重启 20s / Ctrl-C 5s）→ `cancel()` → 关库（`defer`）→ 重启则 `return selfupdate.ExitForRestart("apply")`，普通停止 `return 0`。Ctrl-C 永远返回 0，**不会被自动拉起**。 |
| D. 跨进程安装锁 | `server/update.go#lockInstall`、`stageUpdate`、`updateTick`、`updateRollback` | `updates/install-<hash>.lock`（Windows `LockFileEx` 由命名互斥量同一套 `acquireNamedLock` 提供，Unix `flock`）。手动 apply 在版本校验通过、`updHub.begin` 之前取锁，拿不到直接 **409**；锁随 `stageUpdate` 的 `defer` 释放，进程崩了由内核回收。自动暂存同样先取锁，拿不到只记日志跳过。 |

### 9.2 六条验收怎么验

| # | 验收 | 怎么看 |
|---|---|---|
| ① | 双击 exe 无脚本也能更新 | 任务管理器只有 `artex-rea.exe`（无 `cmd.exe` 跑 `start.bat`）；点"立即更新"后 `/api/health` 的 `version` 变了、`pointer.json.current` 变了、`updates/journal.json` 是 `confirmed`、`logs/update.log` 有 `reason=apply` 的记录 |
| ② | 双开不互杀 | 第二次双击 → 第二个进程只打印"已在运行：http://127.0.0.1:8787"并退出，第一个进程 PID 不变、正在跑的会话不中断 |
| ③ | Ctrl-C 不被拉起 | 控制台 Ctrl-C → 进程消失后 **不会** 再出现新进程（没有 `restart.request`，`Handoff` 只拉有意图的） |
| ④ | 新版起崩自动回滚 | `updates/journal.json` 的 `attempts` 累加到阈值 → 指针切回旧版本 → `state: rolled-back`，`/api/update/check` 的 `rolled_back=true`，全过程重启次数 ≤ 5 |
| ⑤ | 断电自愈 | 安装到一半 `taskkill /f`（或拔电）→ 下次启动 `Bootstrap` 看到 `applying/swapped` 未确认 → `Settle` 失败即回滚；锁由内核回收，不会卡住 |
| ⑥ | 并发 apply 只有一个进入 | 两个控制台同时 POST `/api/update/apply` → 一个 202，另一个 **409 已有更新正在进行**（跨进程锁，不是只在同一个进程内拦） |

### 9.3 仍然保留的边界

- 容器内（`InDocker()`）依然不支持一键换装：换完没人拉起，只能重建容器。这是刻意保留的唯一"硬拒绝"。
- 旧版遗留的 `swap()`（`.old-<ts>` 覆盖式自更新）没有删，但版本化路径（`versions/<ver>/` + 指针）已经是唯一会被 `ApplyNow`/`Bootstrap` 走到的路径。
- 依赖 `-takeover` 的抢占行为还在，但默认关闭：端口被同目录实例占用时只报错退出，说明该怎么处理。
