# 多模态图片链路：接口调研 + 根因 + 整改

> 现象：在「系统 → LLM 设置」里给配置勾上了 `image` 输入模态，模型却依然"看不见"图片。
> 结论：**不是模型的问题，也不是配置没生效——图片从来没有被当作图片发出去过。**

---

## 一、调研：图片到底怎么传给视觉模型

三家主流协议块结构互不兼容，**形状写错就静默失效**（很多网关不报错，直接把图丢掉）。

### 1. OpenAI Chat Completions

```json
{"role":"user","content":[
  {"type":"text","text":"..."},
  {"type":"image_url","image_url":{"url":"data:image/png;base64,<B64>","detail":"high"}}
]}
```

- `url` 支持公网 URL 或 **data URI**（必须带 `data:<mime>;base64,` 前缀）
- `detail`：`low` / `high` / `auto` / `original`；缺省 `auto`
- 省略 `detail` 可能按高精度处理，**token 多花 2–3 倍**

### 2. OpenAI Responses API

```json
{"input":[{"role":"user","content":[
  {"type":"input_text","text":"..."},
  {"type":"input_image","image_url":"data:image/png;base64,<B64>"}
]}]}
```

注意：这里是 `input_image`，**不是** `image_url` 类型，且 `image_url` 是字符串而非对象。

### 3. Anthropic Messages

```json
{"content":[
  {"type":"image","source":{"type":"base64","media_type":"image/png","data":"<裸 B64>"}},
  {"type":"text","text":"..."}
]}
```

三处最容易错的地方：

1. `data` 是**裸 base64**，带 `data:` 前缀直接 400；
2. `media_type` 必须与真实字节一致（把 PNG 标成 `image/jpeg` 会 400）；
3. 支持的 `media_type` 只有 `image/jpeg|png|gif|webp`；单图 base64 ≤10MB（Bedrock ≤5MB）。

### 4. 业界高频故障（都被真实 issue 记录过）

| 故障 | 表现 | 来源 |
|---|---|---|
| 网关把 `data:image/...;base64,...` 丢弃 | 上游只收到文本 | llm-gateway #2170 |
| 把 Anthropic 的 `input_image` 发给 OpenAI 兼容端点 | 模型回"我没看到图片" | openclaw #46255 |
| 图片塞进 `tool_result` 的文本字段 | token 暴涨数十万，且模型看不到图 | maka #5277 |
| 能力判定只看模型名 | 自定义配置声明了图片也被剥掉 | 9router #4301 |
| 部分网关不支持 URL source | 必须内联 base64 | neuralwatt |
| `detail` 被某些模型忽略 | 计费高于预期 | OpenAI community |

## 二、根因：本仓库的图片从来没到过模型

### 2.1 现状链路

```
前端选择文件 → POST /api/chat/upload?scope=session|task|staging
             → 落盘到 <workDir>/sessions/conv-<id>/uploads/x.png
             → 返回 {attachments:[{name,path,size,abs}]}
用户发送消息 → POST /api/conversations/{id}/messages {message, attachments}
             → 模态闸门 checkTurnAttachments(...)
             → composeAgentMessage() 把附件拼成一段文本：
                 【用户上传的附件】(绝对路径，需要时用 Read/Bash 查看)：
                 - C:\...\uploads\x.png（120 KB）
             → ca.Chat(ctx, agentKey, sessionID, <这段文本>, ...)
```

也就是说：**图片以"一行路径字符串"的形式进入模型上下文**。模型唯一能做的是一次 `Read`，而
`Read` 读的是二进制——它永远看不到像素。

### 2.2 为什么不能"直接塞一个 image 块"

上游 SDK `github.com/Autumn-27/norma v0.4.3` 的消息模型定义了内容块类型：

```go
const (
    BlockText       BlockType = "text"
    BlockThinking   BlockType = "thinking"
    BlockToolUse    BlockType = "tool_use"
    BlockToolResult BlockType = "tool_result"
)
```

**没有 image 块**，`ContentBlock` 里也没有 `Source`/`Data` 字段。`grep -r "image" llm/` 零命中。
所以只要不动 SDK，就不可能构造出真正的多模态请求。

### 2.3 于是「勾了 image」的实际含义

`input_modalities` 只被用于**闸门**（`server/modalities.go`）：勾了 → 允许上传；没勾 → 400 拒绝。
它不改变消息如何发给模型。这就是"设置生效了但依然看不见"的完整解释。

## 三、方案：视觉桥（vision bridge）

在 artex 这一层补一次**真正的多模态请求**，把图片变成文本再交给 agent：

```
用户附件 ──┬─ 非图片 ──────────────→ 原路径清单（不变）
           └─ 图片 ──→ DescribeImage() ──→ 文本转写 ──→ 注入用户消息
                        （按 openai / openai-responses / anthropic 三种线格式构造）
```

### 3.1 为什么选这条路

| 方案 | 可行性 | 代价 |
|---|---|---|
| 改 SDK 加 image 块 | 需 fork norma | 上游一升级就冲突，且我们无权改 |
| 自己实现 provider | 要重写三种协议 | 与现有重试/限流/记账体系脱节 |
| **视觉桥（本方案）** | 只加两个文件 | 多一次模型调用（有缓存） |

取舍写清楚：**这是"转写"不是"原生多模态"**。好处是三种协议、所有入口一次覆盖，
不改 SDK、不动既有链路；代价是模型看到的是转写文本，不是像素本身——所以提示词要求
"逐字转录 + 结构描述"，并保留原图路径供后续 `Read` 复核。

### 3.2 协议实现要点（逐一对照第一节）

| 协议 | 端点 | 关键差异 |
|---|---|---|
| openai | `{base}/chat/completions` | `image_url.url` 带 `data:` 前缀，`detail:"high"` |
| openai-responses | `{base}/responses` | `input_image` + 字符串 `image_url` |
| anthropic | `{base}/v1/messages` | 裸 base64、`media_type` 与字节一致、图在文前 |

端点拼接与 SDK `provider.go` **完全一致**（`BaseURL+"..."`），所以既有配置写法无需改动。

### 3.3 尺寸与成本

- 单边 > 2048 或 > 4MiB → 本地盒式缩放后重编码 JPEG(82)；WebP 无法解码时不缩放，超限直接报错（绝不截断字节）。
- 转写结果缓存到 `<原图>.vision.txt`，键 = `sha256(实际发送字节) + model + format`。
  **同一张图同一模型只花一次钱**；换模型会重转（不同模型侧重点不同，不混用）。
- 一轮多图并发 4 路，整轮总时限 90s；超时/失败按失败处理并**明确告知**。

### 3.4 上下文成本（重要）

转写会进入对话历史，**之后每一轮都会随上下文重发**。所以：

| 位置 | 上限 | 理由 |
|---|---|---|
| 注入消息 | **4000 字符** | ≈1K token/图/轮；超出部分截断并指向全文 |
| 磁盘全文 | 12000 字符 | `<原图>.vision.txt`，模型需要细看时可 `Read` |

不这么做的话，一张图的完整 OCR 会在每一次后续请求里重复计费。

## 五、用户可见行为

| 场景 | 之前 | 现在 |
|---|---|---|
| 勾了 image + 视觉模型 | 模型收到一行路径，看不到图 | 模型收到逐字转写（含界面元素/错误信息/URL） |
| 勾了 image + 其实不支持图片的模型 | 静默无视 | 时间线出现红色错误卡：「图片未转写：xxx（HTTP 400 …）」 |
| 没勾 image | 上传即 400（闸门） | 不变 |
| 同一张图再次发送 | — | 命中缓存，零成本 |
| 粘贴截图 | 只能先存文件再点回形针 | Ctrl+V 直接进候选附件 |

**可见性设计**（延续"不静默"原则）：
- 转写开始 → 打一条系统记录「正在把图片转写成文本（视觉模型：X）…」，避免秒级停顿像卡死；
- 转写失败 → 打一条 `IsError` 记录，并在消息里告诉模型"这些图内容未知，不要根据文件名猜"。

## 六、开关与回滚

| 设置键 | 值 | 说明 |
|---|---|---|
| `vision_bridge_mode` | `auto`（默认）/ `off` | `off` 回到旧行为：只发路径清单 |

## 七、未做与下一步

| 项 | 原因 |
|---|---|
| 原生 image 块 | 需上游 norma 支持 `BlockImage`；届时可删掉视觉桥，只保留注入逻辑 |
| `describe_image` 工具 | 让 agent 自己决定何时看某张图（尤其是它自己截的图）。需要把 LLM 配置传进 `ChatAgent`（当前它只持有 provider 与 model，不持有 key/format），改动面比预想大，故留作 P1 |
| PDF / 音频模态 | 闸门已支持声明，但转写通路只做了图片；PDF 建议走工具解析而不是视觉 |
| 图片理解结果回填附件卡片 | 目前转写只进模型上下文；若要给用户看，需在附件卡片上加"查看转写"入口 |
