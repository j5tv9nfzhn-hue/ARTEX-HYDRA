# 数据保留策略（#197，前后端源码阶段）

## 状态与边界

初始阶段新增后端源码、元数据表定义、人工维护 API 和待运行的测试源码；后续按用户确认，补充了保留策略管理界面源码。**没有运行数据库迁移、清理数据、启动服务、编译或测试；当前运行程序不会因源码修改自动获得这些接口。**

自动清理始终关闭：没有注册定时任务或后台 worker，也没有向 Agent 暴露清理工具。`enabled` 仅表示允许登录操作者进行人工执行，不表示自动清理。默认值为 false。

## 默认策略

| 字段 | 默认 | 范围 |
|---|---:|---|
| enabled | false | 仅人工执行开关 |
| usage_days | 90 | 0 为永久保留，否则 30–3650 天 |
| log_days | 30 | 0 为永久保留，否则 7–3650 天 |
| notification_days | 90 | 0 为永久保留，否则 30–3650 天 |
| max_rows_per_table | 100 | 1–500；四张候选表总上限为每表上限的四倍 |

未配置时使用默认值；配置错误直接返回错误，不以空策略掩盖。保存策略会使尚未使用的旧预览全部失效，包括保存为相同值的情况。

## 第一版可以清理什么

1. `llm_usage`：仅超期且没有 task_id、没有 exploration_id 的独立记录。任何已有任务/探索身份都保护，**不减少任务预算、历史任务 Token 总账**。
2. `server_logs`：仅超期的 debug/info 日志；保留 warn/error 和 auth、audit、security、intercept、approval、retention 相关标签。
3. `notification_deliveries`：仅超期终态记录，而且必须有超期的 sent_at；缺少终态时间的 skipped 记录保留。关联事件已 fan-out，且已不存在相关任务、漏洞、资产、审批和会话。事件或 digest 批次仍有 pending/sending/failed/未知状态记录时保留。
4. `notification_events`：仅已 fan-out、超期、无投递子记录、无上述业务引用的事件。删除投递后父事件不会在同一预览中自动追加，必须重新预览。

所有目标还根据真实数据库外键元数据检查入向引用；即使外键声明 CASCADE 或 SET NULL，也不主动删除仍被引用的父行。遇到未知目标列时保守保留。通知快照无效或身份格式无法识别时保留。

这不是针对任意自定义表、非结构化文本引用或未来新增 JSON 关系的全自动证明。新增引用类型必须先扩展策略。任务、漏洞、资产、审批、会话、RE 样本/证据/实体、流量和原始 LLM 请求正文不在删除白名单内。

## 两阶段人工操作

以下是未来获准构建和验收后的接口说明，**本轮没有调用**。

- `GET /api/retention/policy`：读取策略与边界。
- `PUT /api/retention/policy`：保存策略；初始 enabled=false。
- `POST /api/retention/preview`，JSON `{}`：持久化有上限的候选 ID 快照，返回每表 selected、more_candidates、15 分钟有效的 confirmation_token。预览不删除业务记录，但会写计划和审计元数据。
- `POST /api/retention/execute`：要求明确的 `confirmation: "DELETE_PREVIEWED_ROWS"` 和对应 `confirmation_token`。
- `GET /api/retention/audit`：返回最近 100 条记录。

这些路由继承现有 JWT 鉴权。修改接口要求 JSON 对象、4 KiB 请求上限，并拒绝携带非同主机 Origin 的浏览器请求。命令行请求可以不带 Origin，但仍需通过既有鉴权。

### 执行语义

- 预览令牌使用随机 256 bit，只存 SHA-256，不把原令牌放入 URL、普通日志或审计。
- enabled=false 时拒绝执行；旧策略、超时、已使用令牌拒绝执行。
- 只允许计划中的四张白名单表、有限数量的正整数 ID。
- 同事务先获取 SQLite 写保留，再检查策略、令牌、年龄与引用。
- 每个候选 ID 执行前重新检查条件；新插入的行不加入旧计划，新产生的引用会保护对应行。
- 删除、令牌消费和成功审计同事务提交；失败回滚，不返回虚假成功。返回 deleted 与 skipped，不把预览计数冒充实际删除数。
- 真正提交成功后令牌不可复用。调用超时或提交结果不明时，先查审计，不盲目重复提交。

## 管理界面（后续源码阶段）

入口为「系统 → 数据保留」，路由 `/system/retention`。复用现有鉴权请求、UI 控件、导航和中文词条；不修改共享 API 客户端、不增加依赖，不进入独立官网。

- 页面进入只读取策略和最近审计，不自动保存、预览或执行。预览必须点击按钮，并明确说明会写入计划/审计元数据；业务记录不在预览时删除。
- 未读到有效策略时停用编辑和维护；不使用默认配置或虚构零计数掩盖旧后端、HTTP/协议错误。Mock 模式在发送维护请求前拒绝。
- 表单只接受边界内整数；未保存、正在请求、结果待核对时不开放相关危险步骤。策略开关明确标注为「允许人工执行」，不是自动清理。
- 预览仅显示四张白名单表的固定候选数量与是否还有更多，不冒充全量统计，不输出原始业务正文或行样本。
- 执行前必须看到有效候选、已保存且允许人工执行的相同策略，输入 `DELETE_PREVIEWED_ROWS` 并勾选不可撤销确认。回调内再次检查门禁，不能只依赖按钮 disabled。
- 同页用 ref 防止快速重复提交；令牌在发送前从本地权限状态消费。仅内存保存预览令牌，不放入 URL、DOM、日志或存储；重新加载不恢复令牌。
- 编辑、重载、后台切换、重新聚焦或到期均弃用预览。过期同时受墙上时间与单调时钟约束，并扣除请求等待及少量传输余量；服务端仍为最终判定。
- 异常/超时/响应无法验证时不重试、不声称回滚；保留「结果待核对」提示。sessionStorage 只存一位非敏感待核对标志，以便路由切换后提示操作者；存储被禁用时只能在当前页面保留此标志。
- 操作者需读取最新审计、人工核对后才能解除本地待核对状态；这不是自动关联请求或证明数据库结果。若仍不清楚，必须停止维护并核对服务端日志。
- 成功结果要求 `committed=true`，且返回的表、候选数和删除/跳过计数与原预览一致；只显示已知字段，不把未知响应当作成功。
- 审计显示最近 100 条，只做白名单字段摘要，不原样渲染未知 JSON，不提供修改或删除审计入口。进入页面和操作完成后读取，也可手动刷新；无轮询。

开发反向代理必须验证 Host/Origin 的部署关系。后端目前要求浏览器 Origin 主机与请求 Host 一致；本轮未放宽 Origin 校验、未盲目信任 X-Forwarded-Host，也未从浏览器剥离 Origin 绕过检查。现有 Next 开发重写是否保留对应 Host 尚待实际验收，不能因 403 就降低该边界。

完整未来验收项见[数据保留界面-实现与验收清单](数据保留界面-实现与验收清单.md)。当前仍未编译、启动或调用这些 API。

## 审计

`retention_audit` 有普通 SQL 层面的禁止 UPDATE/DELETE 触发器。它记录策略保存、预览、提交结果等，不记录业务正文和密钥。数据库操作失败在回滚之后尝试写独立失败审计；数据库不可写时明确写日志。HTTP 参数校验拒绝不触发业务数据库操作。

actor 目前为单用户系统的 authenticated_operator 标签，不是多用户实名归属。追加限制不是对本机高权限人员、手工改库或移除触发器的密码学防篡改保证。
