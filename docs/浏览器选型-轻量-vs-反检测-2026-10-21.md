# 浏览器选型：几十 MB 存储 × 高等反检测，能同时要吗？

> 结论先给：**内置引擎做不到「几十 MB」。** 唯一能同时满足「几十 MB 存储」和「高等反检测」的组合是
> **不内置引擎、驱动系统已安装的 Chrome / Edge**，应用侧只带几 MB 的驱动胶水；
> Camoufox 从「内置」改成「按需下载的高级档」。

## 一、先把体积账算清（2026 实测区间）

| 方案 | 磁盘占用 | 反检测强度 | 备注 |
|---|---|---|---|
| Chromium / Chrome for Testing（随 Playwright 分发） | 400–600MB（headless shell 150–200MB） | 中：JS 层可打补丁，但「Chromium 不是 Chrome」——Widevine/编解码/版本戳对不上 | Playwright 1.57 起默认改发 Chrome for Testing |
| Playwright Firefox 自带包 | ~187MB | 中 | 只能跑 Playwright 的补丁版 |
| **Camoufox**（补丁 Firefox） | 官方口径 <200MB，**实际 fetch 300–400MB**；macOS 解包 639MB、Linux 解包 1.2GB | **高**：C++ 层注入，页面看不到 JS 覆写 | 内存每实例 ~200MB（空闲 ~40MB） |
| fingerprint-chromium / CloakBrowser 等补丁 Chromium | 300MB+ | 中高 | 需跟随上游重打补丁 |
| Lightpanda | 188MB 单文件 | 低：无渲染器，行为与真实浏览器差异大 | 不适合反检测场景 |
| **系统已装 Chrome / Edge + CDP** | **0（用户机器本来就有）**，应用侧胶水 ~3MB | **高**：真二进制 = 真 TLS/JA4、真编解码、真 Widevine | 需要用户机器上有浏览器（Windows 必带 Edge） |
| 系统 Firefox + 加固配置（RFP） | 0 + ~1MB 配置 | 中：RFP 是「统一化」，本身就是可识别签名（时区强制 UTC、canvas 弹窗） | 不建议做主路径 |

体积那一栏已经把话说死了：**任何自带引擎的方案都在 150MB 起步**，`几十 MB` 这个量级只有「用系统浏览器」能达标。

## 二、反检测这一侧，内置反而不占优

三条 2026 年的共识：

1. **传输层看的是真实二进制。** 真实 Chrome 的 JA3/JA4、HTTP/2 帧序、扩展顺序都是真的；补丁 Chromium 一旦版本戳、编解码或 DRM 能力对不上，就是最显眼的矛盾。（Chrome 110 起每次连接随机化 TLS 扩展顺序，JA3 已不稳定，JA4 才是当前口径。）
2. **JS 层补丁的边际收益在下降。** Runtime.enable / Target.setAutoAttach 这类 CDP 泄漏可以用 Patchright 之流关掉，且它支持 `channel=chrome` 直接驱动系统 Chrome——这正是「轻量 + 强反检测」的现成路径。
3. **C++ 层注入（Camoufox）确实更强**，但代价就是 300MB+ 的磁盘与每次 fetch 的维护成本；它适合「必须过指纹检测」的高风险目标，不适合当默认态。

## 三、推荐路线（三档，按目标风险切换）

| 档 | 引擎 | 磁盘成本 | 适用 |
|---|---|---|---|
| **L1 默认** | 系统 Chrome / Edge（CDP，`channel=chrome` / `msedge`） | **0 额外**，胶水 ~3MB | 绝大多数任务：真实指纹、真实 TLS，最难被「版本矛盾」抓到 |
| L2 备选 | 系统 Firefox + 加固 profile（关 WebRTC、固定时区/语言与代理出口一致；**不开 RFP**） | 0 + ~1MB | 目标对 Chrome 有特殊策略时 |
| **L3 高级档** | Camoufox（按需下载，~300MB，用户显式点「安装」） | 300MB+（用户自选） | 明确知道对方跑指纹检测（Cloudflare/DataDome 高级档） |

L1 要做的加固（应用侧，全部在启动参数与 CDP 层，不打补丁二进制）：
- 持久化 profile 目录（每任务一个），禁用 `--enable-automation` 的可见痕迹、`--no-first-run`、`--disable-blink-features=AutomationControlled`；
- UA-CH 与 UA 字符串、时区（`Emulation.setTimezoneOverride`）、语言、地理坐标与代理出口保持一致；
- headline 级 JS 面：`navigator.webdriver`、`plugins/mimeTypes`、`Notification.permission`、`chrome.runtime` 的存在性；
- 关闭 CDP 的 `Runtime.enable` 早期暴露（走 Patchright 同款思路，或自建 CDP 会话时缓用）；
- 每个 profile 固定一套「屏幕/DPR/字体」参数，避免同一目标前后不一致。

## 四、代价与风险（要接受的三件事）

1. **依赖用户机器上的浏览器**：没有 Chrome 就用 Edge（Windows 必带）；两者都没有的环境只能引导装一个，或落到 L3。
2. **版本不可固定**：系统浏览器会自己升级，行为可能漂移；换来的是「版本真实」。
3. **L1 的 JS 层不如 Camoufox 深**：遇到明确检测 `navigator.hardwareConcurrency`、WebGL renderer、AudioContext 指纹的站点，仍然只能上 L3。

## 五、落地顺序（如果按推荐走）

1. **P1**：`browser` 能力抽象成 `Launcher` 接口，新增 `system-chrome` 实现（找 exe → 启持久化 profile → CDP 连接）；Camoufox 降级为可选实现。
2. **P2**：加固层（启动参数 + Emulation + 一致性校验：时区/语言/UA/代理出口四项必须自洽，不自洽直接拒绝启动）。
3. **P3**：设置页给「浏览器引擎」三选一 + L3 的「下载 Camoufox（约 300MB）」按钮与进度、体积提示。

> **状态（2026-10-21）**：P1 已落地——`camoufox-cli --engine=auto|chrome|edge|camoufox`，系统 Chrome/Edge 走 CDP，零额外磁盘、零新依赖（playwright 已在）。L3 仍是按需安装，未做设置页下载按钮。
