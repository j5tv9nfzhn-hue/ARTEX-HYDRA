# 架构整改方案：内置反指纹浏览器 + 框架五个断层的改法（2026-10-21）

> 本文回应两件事：
> ① 你指出 SQLite 是**为了旧设备、轻量、低占用**特意选的——这一点我接受，并撤回上一稿里
>   「建议换回 PostgreSQL」的说法。错不在选型，**错在把它当 PostgreSQL 那样用**。
> ② 反指纹浏览器目前**没有内置**：要用户自己 `pip install camoufox` + `camoufox fetch`，
>   还要有系统 Python。这确实是个架构缺口。下面给出内置方案与实测数据。

---

## 0. 先把成本算清楚：那 4GB 是怎么没的

你的观感（31GB → 27GB）大概率是**内存**，也可能是**磁盘**；两者都由同一条链路造成。逐项拆：

| 层 | 磁盘 | 常驻内存 | 依据 |
|---|---|---|---|
| Playwright 的 Node 驱动（`playwright-core`） | ~50MB | **~144MB PSS**（另有一份 85MB 是 import 即占） | FreeClaw PR #15 实测：Node driver 144MB / 整浏览器 354MB |
| Chromium（`ms-playwright/chromium-*`） | **281MB 解压 / 167MB zip** | **~270MB**（1 个页面），复杂页 400–600MB | Playwright 官方安装文档；GoLogin 云浏览器实测 270MB/实例 |
| Chromium headless shell | 111MB zip | 略低 | Playwright CDN 实测 |
| Firefox（Playwright 版） | 187MB | ~250–400MB | Playwright 文档 |
| Camoufox | **~300MB 下载**；`camoufox version` 报的安装目录 **1.2GB**（含多版本 + GeoIP 40MB） | 250–450MB | Camoufox 官方安装页 / camofox-browser README |
| `npx` 缓存 + node_modules | 数百 MB | — | — |
| Python（系统解释器 + pip 缓存） | ~100MB+ | 每个 CLI 进程 ~40–80MB | 本项目现状 |

对照你现在的方式：**每条浏览器命令起一个 Python 进程**（`camoufox_cli.py open/click/...`），
进程退出后浏览器也退出（或靠会话文件重连）。所以「3 个 worker 同时用浏览器」≈
3 ×（Python 40–80MB + Camoufox 300–450MB）≈ **1.0–1.6GB**，再叠上 `pip`/`npx` 缓存与
浏览器的 renderer 子进程，落到 4GB 完全解释得通。

**结论：这 4GB 里没有多少是 ARTEX 自己（Go 单进程 ~100–200MB），大头是"解释器 + 浏览器实例"的重复起停。**

## 1. 内置方案的候选与实测数据

| 方案 | 体积（单平台） | 常驻内存 | 反检测强度 | 驱动方式 | Windows | 结论 |
|---|---|---|---|---|---|---|
| **Camoufox**（Firefox 分支） | ~300MB | 250–450MB / 实例 | **强**：C++ 引擎层改指纹，TLS 就是真 Firefox | Juggler（只有 Playwright 会讲） | ✅ x64 | **保留，做内置包** |
| Playwright Chromium | 281MB 解压 | 270–600MB + Node 144MB | 弱（`HeadlessChrome`、CDP 泄露） | Node | ✅ | 淘汰（你已移除） |
| fingerprint-chromium（adryfish） | ~150–280MB | 200–400MB | 中：JS 层伪装完整，但 **TLS/JA3 与真 Chrome 不同** | **CDP（Go 可直连）** | ✅ | 备选，见 §2.3 |
| 系统 Edge/Chrome + CDP | **0** | 200–400MB | 中：指纹是真的，但 CDP 自动化痕迹在 | CDP（Go 可直连） | ✅ 系统自带 | 备选（零下载） |
| Lightpanda | 188MB 二进制 | **27–123MB** | **不适用**：无渲染器、全新引擎、指纹独一份 | CDP | ❌ 无原生 Windows | 只适合纯取 DOM，不适合反检测 |
| Camoufox（现状：pip 安装） | 1.2GB 安装目录 | 同上 + Python | 强 | Python CLI | 需系统 Python | **要改的就是这个** |

数据出处：Playwright 官方安装文档（281M/187M/180M）、Playwright CDN 实测（Chrome for Testing 167.3MiB /
headless shell 110.9MiB）、GoLogin 实测（270MB/实例）、FreeClaw PR #15（Node driver 144MB）、
Camoufox 官方安装页（安装目录 1.2GB、GeoIP 40.7MB）、camofox-browser README（~300MB 下载、空闲 40MB）、
Lightpanda 官方基准（25 并发 123MB vs Chrome 2.0GB）。

### 1.1 一个绕不开的技术约束

**Camoufox 只讲 Juggler，而 Juggler 只有 Playwright 有实现。** 想在 Go 里直接驱动它，
要么自己实现 Juggler 协议（不现实，版本随 Playwright 走），要么换成
**WebDriver BiDi / 经典 WebDriver + geckodriver**（Firefox 156 支持，但功能面比 Juggler 窄）。

所以「内置 Camoufox」有三条路：

| 路线 | 做法 | 代价 |
|---|---|---|
| **L1（推荐）** | 随包分发 **嵌入式 Python 运行时 + 预装 camoufox 包 + 浏览器二进制**，用户零安装 | +15MB 运行时；仍保留 Python 进程（但改为常驻） |
| L2 | 用 `playwright-go`（自带 Node 驱动） | +50MB 磁盘、+144MB 常驻，比 Python 更重 |
| L3 | Go 自写 WebDriver/geckodriver 客户端 | 最轻（geckodriver ~9MB），但要重做页面交互层，且丢掉 Juggler 的隔离世界 |

**推荐 L1**：它把「用户要装 Python + pip + 下载 300MB」变成「解压即用」，
同时不牺牲你最看重的反检测强度，改动量也最小（CLI 保留，换的是运行环境与进程模型）。

## 2. 推荐架构：一个内置浏览器包 + 一个常驻进程 + 一个进程内 MCP

```
┌──────────────────────────── ARTEX (Go) ────────────────────────────┐
│  agent 工具层                                                       │
│    browser_navigate / browser_click / browser_type /                │
│    browser_eval / browser_snapshot / browser_screenshot            │
│              │                                                      │
│         browserMgr（Go，单例）                                       │
│    · 懒启动、空闲 60s 回收、崩溃自愈                                 │
│    · 单浏览器进程 + N 个 context（不是 N 个浏览器）                   │
│    · 请求排队 + 超时 + 取消                                          │
└──────────────┬──────────────────────────────────────────────────────┘
               │ 本机 IPC（stdin/stdout JSON，或 unix socket / named pipe）
┌──────────────▼──────────────────────────────────────────────────────┐
│  browser-pack/<platform>/                                           │
│    python-embed/        嵌入式 Python（15MB）                        │
│    site-packages/       camoufox[geoip]、playwright、依赖（预装）     │
│    camoufox/            Camoufox 浏览器（~300MB，单版本，剔除多余）   │
│    bridge.py            极薄的常驻桥：一行 JSON 进、一行 JSON 出      │
└──────────────────────────────────────────────────────────────────────┘
```

**关键设计点**

1. **常驻而不是每次起进程**：`open` 之后浏览器活着，后续命令复用同一个 context/page。
   现状「每条命令一个 Python 进程」既慢（冷启动 1–2s）又抖（内存反复申请释放）。
2. **一个浏览器、多个 context**：3 个 worker 用 3 个 context（各 +80–120MB），
   而不是 3 个浏览器（各 300–450MB）。粗算：3 context ≈ 500–700MB，比现在省一半以上。
3. **进程内 MCP，不再多一层**：工具直接注册进 agent 的 ToolSet，
   不经过 stdio MCP 握手、不多一个 Node/Python MCP server 常驻。
4. **按平台拆包**：release 里放 `browser-pack-windows-amd64.zip` 等独立资产，
   主程序 14MB 不变；首次使用浏览器时下载（SHA256 + 断点续传），或提供「离线完整包」。
5. **可替换后端**：`browserMgr` 后面是接口，Camoufox 是一个实现，
   将来要加 Chromium 档（见 §2.3）不改工具面。

### 2.1 体积与内存预算（验收口径）

| 指标 | 现状（pip + 每命令一进程） | 方案 L1 |
|---|---|---|
| 用户需手工安装 | Python + pip + `camoufox fetch` | **无**（解压即用） |
| 磁盘占用 | 1.2GB（多版本 + GeoIP） | **~320MB**（单版本 + 精简资源） |
| 3 并发浏览器内存 | 1.0–1.6GB | **~600–800MB** |
| 冷启动 | 1–2s / 每条命令 | 首次 2–3s，之后 ~10ms |
| 空闲回收 | 无（进程随命令退出） | 60s 无操作回收，常驻内存回到 ~50MB |

### 2.2 分发方式（不必让主包变大）

- Release 增加 6 个资产：`browser-pack-<os>-<arch>.zip`（约 300–330MB/个）。
  只下当前平台的那一个。
- 首次调用浏览器工具时：提示一次 → 后台下载（进度走 SSE）→ SHA256 校验 → 解压到
  `<dataDir>/browser-pack/` → 复用。
- 断网/内网：提供 `artex-browser-pack-offline-<os>.zip`，手动放进去即可，校验同路径。
- 老设备：Windows 10+ 才支持新版 Firefox 内核，Win7/8 需明确写进兼容性说明。

### 2.3 备选档（需要你拍板，因为与现有硬规则冲突）

`skills/camoufox/SKILL.md` 里有一条硬规则：「任何回退到 Chromium 系浏览器的做法都属于违规」。
如果将来想要一个**更轻、更快、能纯 Go 驱动**的档位，可以考虑
**fingerprint-chromium（Ungoogled + `--fingerprint=<seed>`）**：
磁盘 ~150MB zip、内存 200–400MB、CDP 直连（Go 的 rod/chromedp），零解释器。

代价必须写清楚：**它的 TLS/JA3 指纹与真 Chrome 不同**，这在 Cloudflare 这类
传输层检测面前是硬伤；而 Camoufox 的 TLS 就是真 Firefox。
所以它是**"快查"档**，不能替代**"隐身"档**。默认关闭，等你自己决定要不要。

## 3. 框架到底错在哪：五个断层 + 具体改法

### 3.1 承载层：SQLite 选型没错，错在「当 PostgreSQL 用」

**选型是对的**：PostgreSQL 要额外 300MB+ 安装、常驻服务、Windows 老设备上折腾；
SQLite 单文件、零安装、易备份，完全符合你的目标。问题出在下面四件事：

| 错在哪 | 证据 | 怎么改 |
|---|---|---|
| **写放大**：每一步 activity 都单独一条 insert，一个意图 10 步就是 10 次写事务 | `activity` 是热表；worker 越多写得越碎 | 写**合并**：单写协程 + 批量提交（50ms 或 200 行先到者为准） |
| **多 goroutine 直写**：planner / N worker / HTTP handler / 流量代理全在写同一个库 | `db/dialect_locking.go` 用 `_txlock=immediate` + `busy_timeout` 模拟行锁 | **单写者**：所有写走一个 channel，读走 WAL 只读连接池 |
| **高频只写数据与核心状态同库竞争** | 同上 | **分库**：`artex.db`（状态）+ `activity.db`（只写）+ `traffic.db`（流量），各自 WAL |
| **长事务/逐行提交** | 意图写回、资产去重都是逐条 | 一次写回一个事务；批量 upsert；去重交给唯一索引 |

**SQLite 的正确打开方式（照抄即可）**：

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous  = NORMAL;     -- 崩溃最多丢最后一个事务，换来 10 倍写入
PRAGMA busy_timeout = 5000;
PRAGMA foreign_keys = ON;
PRAGMA temp_store   = MEMORY;
PRAGMA cache_size   = -64000;     -- 64MB
PRAGMA mmap_size    = 268435456;  -- 256MB
```

- 连接池：**1 个写连接**（串行）+ **N 个只读连接**（WAL 下可并发读）；
  读连接加 `PRAGMA query_only=ON`。
- 备份：`VACUUM INTO 'backup.db'`（在线、不锁库）。
- 不支持的：多实例同时写。单进程就是单进程，写进文档。

**验收指标**：worker=8 连跑 30 分钟 —— `SQLITE_BUSY` 计数 **0**；写事务 p99 **< 20ms**；
planner 单轮 p95 **< 3s**；DB 文件增长 < 200MB/小时。

### 3.2 上下文层：把「静默截断」改成「显式缺口 + 可查回」

**错在哪**：`agent/prompt_slim.go: marshalOverviewCapped` 超预算时按 key 逐个丢弃，
只留一行「已截断」；planner 16KB、worker 12KB 两套预算还不一样。模型不知道自己少了什么，
下一轮可能基于不同摘要做出相反判断。

**怎么改**：

1. 注入块改成**清单式**：`{ "included": [...], "omitted": [{"key":"cold_digests","reason":"budget"}] }`；
2. 给一个 **`get_overview_slice(key, filter)` 工具**，模型缺哪块自己取（按需拉取，而不是每轮全塞）；
3. planner/worker 共用同一份序列化逻辑，只是预算不同——避免两边对同一事实的颗粒度打架；
4. 给「关键字段」设**保底额度**（例如 `task`/`open_intents` 至少各 2KB），不被长尾挤掉。

**验收**：同一任务连续 20 轮，`omitted` 清单稳定（不抖动）；planner 判「0 意图」后
人工复核覆盖率，误判率下降。

### 3.3 编排层：planner 单点 + worker 无连续性

**错在哪**：planner 是唯一意图源，判 0 条全队停摆；worker 领一条、做完即停，
跨意图没有记忆，只能靠共享 todolist 打补丁。

**怎么改**：

1. **终止契约**：planner 输出「0 条意图」时，必须同时给出
   `{ "coverage_gaps": [...], "why_done": "..." }`，引擎校验通过才允许收尾；
   不通过就强制再来一轮（或升级给 main agent 决策）。这一步直接打 MAST 的
   「不知道何时终止 12.4% + 过早终止 6.2%」。
2. **意图内多步**：允许一条意图最多执行 K 步（K=5），而不是一步一停；
   减少 planner 轮次（省 token）也减少冷启动丢上下文。
3. **意图带验收标准**：创建时写 `expected_evidence`（例如「该 endpoint 存在 401/200 差异」），
   worker 完成时必须附证据，否则意图不算 done。

### 3.4 验证层：把复核从旁路挪进主链路

**错在哪**：finding 由执行者自己写回；`db/finding_retests.go` 有复核能力但不在主链路。

**怎么改**：

1. finding 增加状态机：`unverified → verified | refuted`；
2. 只有 `verified` 才计入资产真值与报告；
3. 复核用**独立 prompt + 只读工具**（同一条链路，但角色不同），避免自己验证自己；
4. 成本控制：只对「高危/影响面大」的 finding 强制复核，低危按采样。

**验收**：随机抽 20 条 finding，`verified` 覆盖率 100%；误报率对比基线下降。

### 3.5 审批层：无状态裁判

**错在哪**：`intercept/review_context.go` 的 `ReviewInput` 明确不含执行历史，
裁判只能对单条命令做语法级判断。

**怎么改（不必泄露完整转录）**：

1. 追加一个**最小历史包**：最近 N=5 条同类工具调用（只留名字 + 一行摘要 + 结果码）、
   当前任务阶段（recon/exploit/post）、已授权的 scope；
2. **规则优先**：能由确定性规则判定的（目标在 scope 外、命令含破坏性动词）直接拦，
   不烧模型；
3. 模型只判「灰区」，且输出结构化 `{decision, reason, confidence}`，
   低置信度一律走人工。

**验收**：抽样 20 次 `ask`，人工判断「给了最小历史后结论是否不同」——目标是把
「明显该拦的」全部拦住，把「明显可放」的自动放掉，人工只处理真灰区。

### 3.6 工具面：按阶段裁剪

**错在哪**：MCP + skills + 内置工具全量暴露，schema 每轮都进请求；工具越多越容易选错。

**怎么改**：

1. 工具分三组：`recon` / `verify` / `exploit`，按任务阶段只注入当前组（+ 常驻的几个）；
2. 工具描述瘦身到「一句话 + 关键参数」，细节靠 `--help` 式工具按需查；
3. 大输出工具统一「落盘 + 指针」，只回摘要（你们已有 12k 字符截断，可再加指针化）。

## 5. 明确「不做」的事

- **不换回 PostgreSQL**（你的约束成立：300MB+ 安装、老设备不友好）；
- **不引入 Docker 作为默认部署**（同上，增加不可控依赖）；
- **不做 Lightpanda**：无渲染器、无 Windows 原生包、指纹独一份——与「反检测」目标相反；
- **不把 Camoufox 换成 Chromium**（除非你自己拍板启用 §2.3 的"快查档"）。
