# 架构框架问题诊断（2026-10-21）

> 起因：有用户说「ARTEX 的架构框架有很多问题」，但没指明是哪一些。
> 本文做两件事：**① 联网看外部到底在骂什么**（含多 agent 系统的公开失败统计）；**② 对着本机源码逐个定位**，
> 并回答一个具体问题——这些底层问题，是官方（norma / 上游 ARTEX）带来的，还是本仓库改造引入的。

---

## 0. 结论先行

用户说的「很多问题」不是玄学，可以收敛成 **5 个结构性断层**。归属是混合的，不能全推给上游：

| # | 断层 | 一句话 | 归属 | 严重度 |
|---|---|---|---|---|
| A | 上下文断层 | 真值在库里，但**判断靠每轮重建**：注入有 16KB/12KB 硬预算，超了按 key 优先级**静默降配** | 上游 ARTEX 设计 + norma 压缩策略 | 高 |
| B | 编排断层 | **planner 是唯一意图生成者**，worker 领一条就停；planner 判「0 条」= 全队停摆 | 上游 ARTEX | 高 |
| C | 验证断层 | finding 由 worker 自己写、自己算数；复核（retest）在旁路，不在主链路 | 上游 ARTEX | 高 |
| D | 审批断层 | 审批模型是**无状态裁判**：只看到这一次工具调用，看不到前因后果 | 上游 ARTEX | 高（安全产品里最致命） |
| E | 承载断层 | **数据库被当消息总线用**：SQLite 选型合理（旧设备/轻量），但用法照搬了 PG 时代的并发模型 | 本仓库（选型对、用法待改） | 高 |

**关于「跟我的改动无关」这个假设：大约 70% 成立。** A–D 确实是官方框架自带的；
E 则是本仓库把底座从 PostgreSQL 换成了 SQLite（`47aaab2`，2026-10-14）。

> **2026-10-21 修正**：换 SQLite 是**有意的产品决策**（旧设备、免安装；PG 要 300MB+ 安装与常驻服务），
> 这一条**不构成选型错误**。真正的问题是**并发模型没跟着换**——仍按「多写者 + 行锁」的 PG 心智在用。
> 具体改法见[架构整改方案](架构整改方案-2026-10-21.md) §3.1。

## 1. 外部声音：别人到底在骂什么

### 1.1 多 agent 系统的公开失败统计（最硬的证据）

UC Berkeley 主导的 **MAST（Multi-Agent System Failure Taxonomy，NeurIPS 2025）** 分析了 7 个主流
多 agent 框架、1600+ 条真实执行 trace，人工标注一致性 κ=0.88。结论非常不客气：

- 这些框架的失败率区间是 **41% – 86.7%**（与用哪个模型关系不大）；
- 14 种失败模式，归成三类，占比大致是：
  - **系统设计类 41.8%–44.2%**：不遵守任务规格 11.8%、**步骤重复 15.7%**、**不知道什么时候该停 12.4%**、会话历史丢失 2.8%；
  - **agent 间错位 32.3%–36.9%**：推理与行动不一致 13.2%、任务跑偏 7.4%、不澄清就瞎猜 6.8%；
  - **任务验证类 21.3%**：过早终止 6.2%、**验证不充分 8.2%、验证错误 9.1%**。
- 论文的核心判断：**这 79% 的问题出在规格与协作，不在模型能力**；靠换更强的模型解决不了。

把这张表和 ARTEX 对上，几乎是一一命中的：

| MAST 失败模式 | ARTEX 里对应的结构 |
|---|---|
| 步骤重复 / 不知道何时终止 | planner 每轮重读「摘要态势」，冷启动判断边界靠 prompt 约束而非状态机 |
| 会话历史丢失 | 注入 16KB/12KB 硬预算 + 按 key 静默降配 + 冷图 digest + SDK compaction |
| 任务跑偏 / 推理-行动不一致 | worker 只领一条意图、执行完即停，没有「做一半回头看」的回路 |
| 验证不充分/错误 | finding 由执行者自己写回，复核不在主链路 |

### 1.2 中文社区的直观吐槽（不是 ARTEX 专属，但同构）

- V2EX「5X 的 Codex 一天半烧完了，晒晒我的智障多 agent 工作流」：多个 agent 互相评审，
  评审意见一个比一个能说，「最后基本都得我自己动手改」——**多 agent 把返工变成了新的工作**。
- V2EX「感叹 Codex 的过度设计」：让 agent 连续跑 15 小时、写 2 万行，「我是真不敢合并」——
  **产出量与可验收性脱钩**。

这两条对应的正是 B/C 两个断层：**执行者多、验收者少**。

### 1.3 第三方对 ARTEX 本身的具体批评

- **Hysen Labs 的评测**指出：审批层的 review model **拿不到历史**——README 明确写了
  它只收到 v4 JSON（工作目录、简短背景、工具名、参数），**不含历史命令、历史结果、历史审批理由**，
  也不含调用关联标记。「它不推理 agent 的历史」这一句，是对 D 断层的外部佐证。
- **note.com 的拆解**：审批闸门「设计存在，但默认值松」——技术上有拦截层，策略上默认放行。
- **cn-sec 的两篇拆解**：夸了双图、CAS 抢单、共享 todolist；同时也点了一句关键——
  「**护栏要在设计期做，不能只写在文档里**」，以及「文档不构成技术约束」。
- **ASEC 的威胁报告**（非架构，但影响口碑）：开箱即用 + 全球 ~600 个 IP 出现活动，
  说明这套东西的**默认自治度**高到超出使用者的判断能力——这也是「框架问题」的一部分。

**小结**：外部没有人给 ARTEX 列过「架构缺陷清单」，骂点集中在三类——
**跑不稳（重复、不收敛）、烧钱（多 agent 放大）、拦不住也看不清（审批与可观测）**。
下面用源码把这些骂点落到具体位置。

## 2. 源码里的五个断层

### A. 上下文断层：真值在库里，判断靠「每轮重建成一份摘要」

**机制**（源码）：

- `agent/prompt_slim.go: marshalOverviewCapped` —— 把态势 map 序列化后按 **固定字节预算** 装填，
  超预算就「先砍半列表、再整键省略」，末尾补一行截断说明。代码注释自己承认：
  *"截尾会把 task/running_intents 这类规划关键字段整段丢掉"*，所以按优先级逐键装填，
  让位顺序是 `related_tasks / cold_digests` 这些「按需可查」的块先走。
- README 里写死的注入预算：**planner ≤16KB、worker ≤12KB**；再叠上 norma 的 compaction
  （我们这轮刚把触发点改成窗口的 80%）与冷图 digest。

**问题在哪**：

1. **模型不知道自己少看了什么**。截断只留一行「已截断」提示，模型无法判断丢的是无关噪声还是
   关键前提；下一轮它可能基于不同的摘要做出相反的判断 → 对应 MAST 的「步骤重复 / 任务跑偏」。
2. **两份摘要不一致**。planner 看的是 16KB 版本、worker 看的是 12KB 版本，同一事实在两边
   颗粒度不同，交接必然有缝。
3. **每轮重建 = 每轮重新理解**。状态在库里是对的（比塞长上下文强），但「读库 → 摘要 → 注入」
   这条链把确定性丢在了中间层。

**归属**：注入预算是上游 ARTEX 的选择；压缩阈值是 norma 的（本仓库已把 80% 口径修好）。

---

### B. 编排断层：单点意图生成 + 无状态执行者

**机制**：

- `server/engine.go:568` —— 引擎 `debounce: 800ms`，图一变就唤醒 planner；
- `server/engine.go:claimNext` —— 取 `Frontier(20)`，逐条 `ClaimIntent` 做 CAS 抢单；
- planner 是**唯一**的意图生成者，worker 领**一条**意图、执行、写回、**即停**。

**问题在哪**：

1. **单点**：planner 一轮判 0 条，全队停摆。它判断「没有新方向」的依据是那份被裁剪过的摘要
   （见 A），于是「漏看到 → 误判完成 → 提前终止」是一条完全闭合的失败路径
   （MAST：不知道终止条件 12.4% + 过早终止 6.2%）。
2. **无状态执行**：worker 没有「先试探、再回来」的两段式，也没有跨意图的记忆——
   它每次从系统提示 + 库里的原始资产重新理解任务。这解释了为什么需要「共享 todolist」
   这种补丁：**用外部便签弥补执行者没有连续性**。
3. **抢单是乐观锁**：SQLite 上每次 CAS 都是一次写事务，20 条一轮就是最多 20 次写尝试；
   worker 越多，冲突越多（与 E 联动）。

**归属**：上游 ARTEX 的编排设计。

---

### C. 验证断层：发现即事实

**机制**：worker 执行后直接 `insert_findings` 写回；`db/finding_retests.go` 提供了复核能力，
但它是一条旁路，不在「写回 → 触发 planner」的主链路上。

**问题在哪**：LLM 误报是常态，而这里**执行者=记录者=证人**。没有独立 verifier、没有
「未验证不得进真值库」的闸门。MAST 里任务验证类占 21.3%，其中「验证错误」9.1%——
这一类错误在渗透场景里直接等于**误报**或**假阴性**。

**归属**：上游 ARTEX（有工具，但没进主链路）。

---

### D. 审批断层：无状态裁判

**机制**（`intercept/review_context.go`）：

```go
// ReviewInput contains only the current call and explicitly selected background.
// Execution history and call correlation belong to the separate audit record.
type ReviewInput struct {
    Version    int
    WorkingDir string
    Background *ReviewBackground // 仅当来源是「用户原话」时才填，且截到 4000 字符
    Tool       string
    Arguments  json.RawMessage
}
```

注释写得很清楚：**有意不把执行历史喂给评审模型**，理由是「审计记录另有其处」。

**问题在哪**：这是一条**正确的隐私/成本取舍**，但做成了一个**错误的安全判断**。
「`curl` 内网地址」在侦察阶段合理、在拿到立足点之后就是横向移动；「`cat /etc/passwd`」
在本地靶场无害、在客户生产机上致命。裁判看不到前因，只能对**单条命令**做语法级判断——
于是它要么很松（默认放行），要么很吵（误拦），两种都会让人把它关掉。

**归属**：上游 ARTEX 的设计取舍（外部评测也点了这一条）。

---

### E. 承载断层：数据库当总线，SQLite 扛着 PG 时代的并发模型（**本仓库**）

**证据链**：

| 事实 | 位置 |
|---|---|
| 上游是 PostgreSQL（多篇拆解文章均如此描述，schema 997 行、9 个条件唯一索引） | 外部资料 |
| 本仓库 `go.mod` **没有 pgx**，只有 `modernc.org/sqlite` | `go.mod`（require 块） |
| 配置文件明写 | `config/config.go:17` — *"ARTEX runs on SQLite only"* |
| 手写锁模拟 | `db/dialect_locking.go` — 用 `_txlock=immediate` + `busy_timeout` 模拟 `SELECT … FOR UPDATE [SKIP LOCKED]` |
| 写串行化兜底 | `server/sqlite_write.go`、`config.SQLiteBusyTimeout` |
| 残留的双栈假设 | `db/dialect_companies.go`（41 处 postgres 字样）、`dialect_arrays.go`、`dialect_dml.go` |
| **迁移就是这一支做的** | `47aaab2`（2026-10-14）*feat(db): 引入 SQLite 迁移层*；三天后 `cf4b265`（2026-10-17）*fix(sqlite): 修复写锁竞争导致的 BUSY/超时风暴* |

**问题在哪**：

1. **SQLite 是单写者**。而这里的负载模型是：N 个 worker 抢单 + planner 写意图 + HTTP handler
   写设置/审批 + 流量代理写记录，**全在写同一个库**。上游选 PostgreSQL 不是随便选的，
   正是为了 `FOR UPDATE SKIP LOCKED` 这种「多消费者队列」语义。
2. **锁是模拟出来的**。`dialect_locking.go` 用「立即事务 + 忙等」替代行锁，语义上能跑通，
   但把「排队」变成了「抢锁重试」：worker 数一调高，`SQLITE_BUSY` 与长尾延迟就上来。
3. **方言层是死复杂度**。产品只跑 SQLite，`dialect_*` 里还留着一整套 PG 分支——
   读代码的人会以为有两套部署形态，排障时会照着不存在的路径找问题。
4. **这不是推测，已经发生过**：`47aaab2`（10-14）引入 SQLite 迁移层，`cf4b265`（10-17）
   就在修「写锁竞争导致的 BUSY/超时风暴」——中间只隔了三天。一个需要 3 天打补丁的底座，
   说明它不是「实现没写好」，而是**选型与负载模型不匹配**。

**归属**：**本仓库**，但要分两层看——**选型没问题**（SQLite 换 PG 正是为了旧设备/轻量），
**用法有问题**（多写者直写、写放大、锁模拟）。改法不是换回 PG，而是在 SQLite 上把
「单写者 + 批量提交 + 分库」做对，详见[架构整改方案](架构整改方案-2026-10-21.md) §3.1。
这也是最该先解决的一条，因为 A/B/C 的所有写路径都压在它上面。

---

### F（附带）. 工具面断层：schema 常驻、按阶段不分层

MCP + skills + 内置工具全量暴露，工具定义每轮都要进请求（这是缓存断点之外最贵的固定成本）。
工具越多，选错的概率越高（MAST：推理-行动不一致 13.2%）。目前没有按任务阶段
（侦察 / 验证 / 利用）裁剪工具面的机制。

## 3. 哪些和你的改动无关：把账分清楚

### 3.1 上游 norma（SDK）的已知欠账

这些**不是**你改出来的，仓库里早有清单（`docs/norma-SDK优化补丁清单.md`），本次核对仍然成立：

| # | 问题 | 影响 |
|---|---|---|
| 1 | 缓存断点只打在 system，tools 与消息序列没有 | 每轮工具 schema 全价计费 |
| 2 | MicroCompact 的白名单硬编码 8 个工具 | ARTEX 的大输出工具不参与清退，只能等更晚更贵的 AutoCompact |
| 3 | 内建压缩固定用主会话 Provider 做摘要 | 摘要也在烧最贵的模型 |
| 4 | 截断恢复次数写死 3 次 | 高成本路径不可控 |
| 5 | 没有 `prompt_cache_key` | OpenAI 兼容网关的前缀缓存命中率上不去 |
| 6 | `TokenBudget` 是「续跑激励」不是硬上限 | 当成本闸用会反向烧钱 |
| 7 | 压缩触发比例不可配（本轮已用反解绕过，并提了上游补丁 #7） | 各窗口触发点漂移 |

### 3.2 上游 ARTEX（框架层）的欠账

A（注入预算是它的选择）、B（单点编排）、C（验证不在主链路）、D（无状态审批）、F（工具面）。

### 3.3 本仓库改造引入的

E（SQLite 承载）。**它不制造新失败模式，但把上游「数据库即总线」的设计推到了最不利的底座上。**

> 一句话回答你的假设：**底层原因确实大多是官方的，但你现在踩到的「卡、慢、抢锁」那部分，
> 是 PG→SQLite 这一步放大出来的，不能算在上游头上。**

## 4. 优先级建议（按 ROI 排，不按「重构爽感」排）

| 优先级 | 动作 | 打掉哪个断层 | 成本 |
|---|---|---|---|
| P0 | **写路径收敛**：所有写走单协程/队列，或把 DB 换回 PostgreSQL（Docker 版保留 PG） | E | 中 |
| P0 | **planner 的终止契约**：0 条意图时必须输出「覆盖度缺口清单」，而不是默默结束 | B | 低 |
| P1 | **审批输入补最小历史**：最近 N 条同类调用 + 当前任务阶段（不含完整转录） | D | 低 |
| P1 | **注入截断显式化**：告诉模型「缺了哪块」并给一个取回工具，而不是一行「已截断」 | A | 低 |
| P2 | **verifier 入主链路**：finding 未复核前标 `unverified`，不进资产真值 | C | 中 |
| P2 | **工具按阶段裁剪**：侦察/验证/利用三套工具面 | F | 中 |
| P3 | 清掉 `db/dialect_*` 的 PG 死分支，统一心智模型 | E | 低 |

## 5. 怎么验证（可复现，不用信我）

1. **抢锁**：把 worker 数调到 8，跑 30 分钟，统计 `SQLITE_BUSY` 与 `ClaimIntent` 失败率；
   对照 worker=2 的基线。
2. **注入截断**：统计 planner prompt 里 `overviewTruncatedNote` 出现的轮次占比——
   这就是「模型没看全」的比例。
3. **验证覆盖**：随机抽 20 条 finding，看有多少条有 retest 记录。
4. **审批有效性**：抽 20 次 `ask` 审批，人工回答「如果给它最近 5 条同类调用，结论会不会不同」。
5. **终止质量**：统计「planner 判 0 条后任务状态」——是 prove_goal 成功，还是被判死。
