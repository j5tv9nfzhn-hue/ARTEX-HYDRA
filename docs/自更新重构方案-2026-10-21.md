# 自更新落地重构方案：静默失败归因 + 业界通用范式（2026-10-21）

> 触发问题：检查、下载、SHA256 校验都正常，**重启换装阶段静默失败**，且现场出现一个名为
> `artex-rea.new.exe` 的**常驻进程**。
> 方法：源码只读分析（遵守 `AGENTS.md`，未编译未测试）+ 联网调研业界实现。
> 结论提前说：**这不是一个 bug，是一类结构性缺陷**——「暂存件本身就是可执行程序、且换装由被替换的进程自己做、且失败不留任何持久痕迹」。本文给出归因、业界范式对比与分阶段落地路径。

---

## 0. 一页结论

| 维度 | 现状 | 问题 |
|---|---|---|
| 谁执行换装 | **被替换的那个进程自己**（下次启动时的旧版） | 只要有一次没被守护脚本拉起，换装就永远不发生；且失败只写控制台 |
| 暂存件形态 | `artex-rea.new.exe`，**就在安装目录、可双击运行、名字像正式程序** | 一旦被启动，它就是一个"第二个安装"：`ResolvePaths()` 以 `os.Executable()` 为锚，于是它的 marker 叫 `artex-rea.new.upgrade.json`、它的暂存件叫 `artex-rea.new.new.exe` —— **分裂脑** |
| 同族进程判定 | `bootBeforeStart` 认为「同目录 `artex*.exe`」都是自己人，可以强杀 | `artex-rea.new.exe` 正好命中 → 新版预览进程与旧版互相抢 8787，谁后启动谁杀掉对方 → **看起来"更新没生效"** |
| 回滚备份名 | 固定 `artex-rea.old.exe`，`swap` 里 `os.Remove(.old)` 失败即 `return err` | 上一轮的 `.old` 仍被运行中的旧进程锁定（Windows 允许重命名、**不允许删除正在运行的镜像**）→ **之后每一次升级都失败**，且报错只进控制台 |
| 换装成功判定 | `Settle()` 只看"进程活过 30 秒" | 端口抢到了、业务坏了也算成功；没有版本匹配、没有健康探测 |
| 失败的可观测性 | 进度走 SSE（进程一退出就断），`bootState` 只在**内存**里 | 重启后上一个进程知道的一切全丢；前端"正在重启"**没有超时分支**，可以无限转圈 |
| 并发保护 | `updateHub.running` 是**进程内**互斥 | 两个实例（分裂脑、或用户开两份）可同时改同一批文件 |

**一句话**：现在的链路把「可执行文件的身份」和「目录里的文件名」绑在了一起，又没有为"换装"这个动作指定唯一、独立、有台账的执行者。

## 1. 本次事故的代码级归因

### 1.1 `artex-rea.new.exe` 是怎么跑起来的？——唯一会 exec 它的地方是冒烟测试

全仓只有一处执行暂存件：`selfupdate/bootstrap.go#smokeTest`

```go
cmd := exec.CommandContext(ctx, bin, "-h")   // bin 可能是 artex-rea.new.exe.part / artex-rea.new.exe
cmd.Env = append(os.Environ(), smokeEnv+"=1")
```

它被调用两次：`stage.go#Stage`（下载后）与 `bootstrap.go#verifyStaged`（换装前）。设计意图是靠 `-h` 让子进程**立刻退出**（Go 的 `flag` 包对未定义的 `-h/-help` 走 `ErrHelp` → `os.Exit(0)`）。

**这条路径有三个脆弱点，任何一个被触发都会留下一个"活着的 `.new.exe`"：**

1. **它执行的是完整程序**，只靠"参数让它退"这一条约束。将来若把 `-h` 改成别的、或加子命令/交互式初始化、或 `flag.Parse` 之前新增了会阻塞的逻辑，子进程就会**继续往下跑成一台真正的服务器**。
2. **它继承了父进程的完整环境**（只额外加了 `ARTEX_SELFUPDATE_SMOKE=1`），包括 `ARTEX_SUPERVISED=1`、`ARTEX_CONFIG`、代理变量等；一旦它跑起来，行为和正式实例几乎一模一样。
3. **超时杀进程只杀直接子进程**。`exec.CommandContext` 在超时后 `Kill()` 的是它拉起的那个 PID；如果新版本将来会再派生进程（本仓库的 Bash 工具就会），会留下孤儿。

而一旦 `.new.exe` 真的作为服务器跑起来，**它不会被现有逻辑"认领"**：

```go
// selfupdate/selfupdate.go#ResolvePaths —— 一切路径都锚定 os.Executable()
stem = "artex-rea.new"        // ← 因为它就是 artex-rea.new.exe
New  = "artex-rea.new.new.exe"
Marker = "artex-rea.new.upgrade.json"
```

于是它**永远不会应用真正的暂存件**，也不会读真正的 marker。它只是安静地占着 8787 端口，把界面服务起来——用户看到"程序是好的、版本没变"。

### 1.2 为什么"静默"？——五条独立原因叠加

| # | 原因 | 证据 |
|---|---|---|
| S1 | 换装发生在**下一次启动**（`Bootstrap`），若那时没被守护脚本拉起，换装就无限期挂起 | `cmd/artex/main.go#run` → `Bootstrap()` 只在启动时调用一次 |
| S2 | 失败原因只写 `log.Printf`（控制台），没有落盘文件 | `applyStaged` / `confirmOrRollback` / `swap` 全部只 `log.Printf` |
| S3 | 换装结论 `bootState` 是**进程内变量**，重启即丢 | `server/update.go#bootState` + `SetBootUpdateState` |
| S4 | 进度走 SSE，**进程一退出流就断**；断流后前端只做一件事：轮询 `/api/health` 等版本号变化，**没有超时、没有失败分支** | `update-card.tsx` 的 `restarting` effect：`setInterval(2000)` 无限轮询 |
| S5 | `swap` 里清理 `.old` 失败会让**整个升级**返回错误，但错误只到 `updateHub.finish(err)` → 一条 SSE → 页面已刷新就看不到了 | `bootstrap.go#swap` 第一段 `os.Remove(p.Old)` 失败即 `return` |

S4 就是用户主观感受"点了更新 → 一直转圈 → 没下文"的直接来源。

### 1.3 为什么 `.old` 会成为"一次失败、永久失败"

Windows 的语义边界（多份资料一致，且有硬件实测）：

- 正在运行的 `.exe` / 已加载的 `.dll`：**可以重命名**，**不能删除、不能原地覆盖**（`ERROR_ACCESS_DENIED`）。
- 被锁定的是**目录项的内容**，不是目录项本身。

现在的 `swap` 用的是**固定名字**：

```go
_ = os.Remove(p.Old)              // 若上一轮的 .old 还被某个进程锁定 → 失败
if err := os.Rename(p.Current, p.Old); err != nil { ... }   // .old 存在且不可删 → 也失败
```

只要历史上有一次"旧进程没退干净"或"用户双击过 `.old.exe`"，`.old` 就被锁住，**此后每一次升级都卡在第一行**。这正是社区反复踩的坑：*"a locked ghost.exe.old blocks every later upgrade on Windows"*，正确修法是**不复用固定备用名**（用 `<ver>-<时间戳>`），并对清理失败**只告警不阻断**。

### 1.4 为什么"两个进程会互相杀掉"

`cmd/artex/boot_windows.go#isOwnedProcess` 的判定是：

```go
if filepath.Dir(target) == dir && strings.HasPrefix(base, "artex") && strings.HasSuffix(base, ".exe") {
    return path, true   // 同目录的 artex*.exe 都算"自己人"，可以强杀
}
```

`artex-rea.new.exe`、`artex-rea.old.exe`、`artex-rea.exe.failed` 全部命中。于是：

- 分裂脑的 `.new.exe` 占着 8787；
- 守护脚本拉起 `artex-rea.exe` → `ensurePortFree` 发现占用者"是自己人" → **`terminateProcess` 杀掉 `.new.exe`** → 旧版继续跑。

结果：**新版本被自己的兄弟进程杀掉了，而且没有任何一处会报告这件事**。用户看到"更新完还是老版本"，日志里也不一定有人看。

### 1.5 现场两分钟判定（在目标机上跑，只读命令）

```bat
:: 1) 谁在跑、路径是什么（重点看映像名与目录）
tasklist /FI "IMAGENAME eq artex*" /V
wmic process where "name like 'artex%'" get ProcessId,ExecutablePath,CommandLine
:: 2) 谁占着 8787 / 8788
netstat -ano | findstr ":8787 :8788"
:: 3) 安装目录里的残留（关键：.new.exe 是否还在、.old 是否被锁）
dir /a "C:\path\to\artex"
:: 4) 升级台账是否存在、内容是什么
type "C:\path\to\artex\artex-rea.upgrade.json"
:: 5) 「最新一次」到底走到哪一步：看控制台/日志里 [update] 前缀
```

判定表：

| 观察到 | 结论 |
|---|---|
| `.new.exe` 有进程、`artex-rea.exe` 没进程 | 分裂脑：暂存件被当过正式程序启动（1.1） |
| `.new.exe` 无进程但文件在、marker 的 `to` 是目标版本 | 换装从未执行（守护脚本没拉起过，S1） |
| 有 `.old.exe` 且 `swap` 日志报"清理旧备份失败" | 固定备用名被锁（1.3） |
| 8787 被 `artex-rea.new.exe` 占用 | 新版预览抢端口 → 旧版被杀（1.4） |
| 界面停在"正在重启" | S4，前端无看门狗 |

## 2. 业界怎么做（调研结论）

### 2.1 Windows 换装的三条硬约束（全行业共识）

| 约束 | 说明 | 出处 |
|---|---|---|
| 可以**重命名**正在运行的 exe | 目录项被允许改名，进程继续用旧 inode / 旧映射 | [5](https://github.com/jdolan/quetoo/issues/1033)（含 Win11 26200 硬件实测 11/11 通过）、[12](https://stackoverflow.com/questions/55247194/how-to-self-update-application-while-running)、[9](https://github.com/kunchenguid/no-mistakes/issues/373) |
| **不能删除、不能原地覆盖**运行中的 exe | `ERROR_ACCESS_DENIED` / `WinError 32` | 同上；[2](https://github.com/NousResearch/hermes-agent/issues/89599) |
| **不能重命名"含有正在运行 exe 的目录"** | 想整体替换整个安装目录会失败 | [8](https://github.com/NousResearch/hermes-agent/issues/93032) |

推论：只能"**改名让位 → 写入新文件 → 旧文件等进程退出后再删**"，并且删除必须**容忍失败**。

### 2.2 五个反复出现的失败模式（我们踩了其中三个）

| 失败模式 | 现象 | 正确做法 | 出处 |
|---|---|---|---|
| 固定名 `.old` 被锁死 | 一次失败后**永久**无法再升级 | 备用名带版本/时间戳；清理失败只告警；下次启动再扫 | [14](https://github.com/wcatz/ghost/issues/1351) |
| 两次 rename 之间的**空窗** | 中途被杀 → 目标路径上没有可执行文件 → 彻底坏掉 | 同目录暂存 + `fsync` + 尽量单次原子 `rename`；Windows 上至少保证"失败即回滚" | [17](https://github.com/giantswarm/mcp-debug/pull/180)、[8](https://github.com/redcarbon-dev/redcarbon-agent/pull/28) |
| **并发**升级共享同一组 `.new/.old` | 一个截断另一个的下载，或把对方刚装好的删掉 | 跨进程文件锁 + 随机化临时名 | [10](https://github.com/inconshreveable/go-update/issues/53)、[17](https://github.com/giantswarm/mcp-debug/pull/180) |
| **update 替换自己**（self-lock） | 更新程序本身就是被替换的那个 exe | 用**独立 helper / 分离进程**执行换装 | [1](https://github.com/WodenJay/GitScry/issues/110)、[11](https://github.com/NousResearch/hermes-agent/issues/49428)、[7](https://github.com/kunchenguid/treehouse/issues/73) |
| **杀毒/索引器的瞬时锁** | 同一个更新"有时成功有时 Access Denied" | 200ms→1s 退避重试 3–5 次；不要把瞬时失败当永久失败 | [16](https://github.com/Cliftonz/jarvy/issues/63)、[20](https://forum.cursor.com/t/cursor-updater-blocks-with-access-is-denied-error-on-windows/172151) |

另外两条容易被忽略的：

- `MoveFileEx(..., MOVEFILE_DELAY_UNTIL_REBOOT)` **需要管理员权限**，普通用户会拿到 `ERROR_ACCESS_DENIED`，不能当兜底方案用（[1](https://github.com/WodenJay/GitScry/issues/110)）。
- 集成测试**必须用"真的在运行的 exe"**去替换；用普通文件测，Windows 的锁语义完全测不到（[1](https://github.com/WodenJay/GitScry/issues/110)、[7](https://github.com/kunchenguid/treehouse/issues/73)）。

### 2.3 Go 生态的主流实现对比

| 方案 | 换装策略 | 优点 | 局限 |
|---|---|---|---|
| `minio/selfupdate#CommitBinary` / `inconshreveable/go-update` | 目标→`.old`，`.new`→目标，最后**尝试**删 `.old`；Windows 删不掉就**隐藏** | 事实标准，很多库照抄 | 固定 `.old` 名；两次 rename 有空窗；不再维护（[1](https://pkg.go.dev/github.com/minio/selfupdate)、[3](https://pkg.go.dev/github.com/koron/hk/Godeps/_workspace/src/github.com/inconshreveable/go-update)） |
| `joshuavidthomas/go-selfupdate` | Unix 单次原子 rename；Windows 改名让位 + 失败回滚 + `CleanupPending` | **区分平台语义**、跨进程锁、校验指纹、结果可为"已提交但有残留" | 作者明确承认"Windows 上没有进程内操作能补住崩溃窗口"（[7](https://pkg.go.dev/github.com/joshuavidthomas/go-selfupdate)） |
| `phlipse/go-selfupdate` | **临时 helper 进程**负责换装与重启 | 彻底避开 self-lock | 多一个可执行体/进程（[25](https://pkg.go.dev/github.com/phlipse/go-selfupdate)） |
| `datapointchris/goselfupdate` | 同目录暂存 + `CleanupOldBinary()` 在下次启动清残留 | 简单可靠 | 无健康门控（[9](https://github.com/datapointchris/goselfupdate)） |
| `viniciusbuscacio/go-updates` | staging → `app.exe.old` → 就位 → 失败回滚 → 下次启动 `CleanupOld()` | 明确"Windows 上 rollback 只有一次机会" | 无 helper（[5](https://pkg.go.dev/github.com/viniciusbuscacio/go-updates)） |

**没有人**在客户端层面解决"信任锚"（摘要与产物同源）——这一点我们要靠自己（见 P1-4）。

### 2.4 系统级能力：Windows 官方的两件"外挂"

| API | 作用 | 适用 | 出处 |
|---|---|---|---|
| `RegisterApplicationRestart` + Restart Manager（`RmStartSession/RmShutdown/RmRestart`） | 安装器可以把应用**优雅关掉、换文件、再拉起来**；被重启的进程需事先注册 | 有安装器的场景；**进程运行不足 60 秒不会被重启**（防循环）；提权进程不参与自动重启 | [9](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-registerapplicationrestart)、[7](https://learn.microsoft.com/en-us/windows/win32/rstmgr/about-restart-manager)、[1](https://learn.microsoft.com/en-us/windows/win32/api/restartmanager/nf-restartmanager-rmrestart) |
| `ARR`（Application Recovery & Restart） | 崩溃/挂起/系统更新后恢复并带参数重启 | 提升韧性，不解决换装本身 | [2](https://blogs.windows.com/windowsdeveloper/2023/07/20/help-users-resume-your-app-seamlessly-after-a-windows-update/) |

注意"**60 秒最小运行时长**"这条：如果新版本一启动就崩，系统不会帮你循环拉起——所以**必须**有自己的计数与回滚（我们已有 `maxAttempts=3`，但计数存活期依赖 marker，且 `Settle` 只看存活）。

### 2.5 更进一步的范式：版本化目录 + 原子指针切换

服务端部署十几年的成熟做法（Capistrano / Deployer / 蓝绿）：

```
app/
├── releases/
│   ├── 20261020-1200/   ← 上一版（保留，用于回滚）
│   └── 20261021-0930/   ← 新版（先构建/校验完）
└── current -> releases/20261021-0930    ← 只改这一根指针
```

- **切换 = 一次 `rename`**，读者要么看到旧树要么看到新树，没有半成品状态；
- **回滚 = 把指针指回去**，秒级，不需要复制文件；
- 保留最近 N 个版本即可（[1](https://www.deployhq.com/blog/zero-downtime-deployments-keeping-your-application-running-smoothly)、[6](https://deployer.org/blog/atomic-symlinks)、[7](https://oxmgr.empellio.com/blog/instant-rollback-deployment)）。

两个必须知道的坑：

1. `ln -sfn` **不是原子的**（它是 `unlink` + `symlink`，中间有空窗）；必须是"在新名字建好 → `mv -T` 覆盖"（[16](https://github.com/mojoatomic/atomic-deployments)、[14](https://dev.to/nasrulhazim/a-symlink-swap-is-not-a-zero-downtime-deploy-4bb2)）。
2. **Windows 上创建符号链接需要权限（管理员 / 开发者模式）**；目录 **junction** 不需要管理员但只对本地卷目录有效。对"用户机型上的单二进制"来说，最稳的等价物是**一个永不替换的小 launcher + 一个指针文件**（见 3.3 B 方案）。

## 3. 推荐架构

核心原则四条：

1. **进程身份与文件身份解耦**：谁是"当前版本"由**台账/指针**说了算，不由"哪个文件名在跑"说了算。
2. **换装者必须是独立执行体**：要么守护脚本，要么专门的 helper 进程，**永远不是那个要被替换的进程**。
3. **暂存区与执行区物理隔离**：`updates/` 子目录里的文件**不是可双击的程序**、不匹配 `artex*.exe`。
4. **每一步都留痕**：跨进程的 journal（不是内存），失败必须能被下一个进程、下一个页面、下一个人读懂。

### 3.1 目标状态机（跨进程持久）

```
                 ┌──────────┐  check   ┌───────────┐ download+verify  ┌───────────┐
   用户点更新 →  │ detached │ ───────► │  checking │ ────────────────► │  staged   │
                 └──────────┘          └───────────┘                   └─────┬─────┘
                                                                            │ 写 pending（含 sha256、目标版本）
                                                                            ▼
                                            ┌──────────────────────────────────────┐
                                            │  apply-requested（等待换装者接手）   │
                                            └──────────────┬───────────────────────┘
                                                           │ helper / supervisor 接手
                                        ┌──────────────────┼──────────────────┐
                                        ▼                  ▼                  ▼
                                 ┌────────────┐   ┌──────────────┐   ┌──────────────┐
                                 │ swapping   │──►│ health-check │──►│  confirmed   │
                                 └─────┬──────┘   └──────┬───────┘   └──────────────┘
                                       │ retry(N)        │ version 不匹配 / 探活失败
                                       ▼                 ▼
                                 ┌────────────┐   ┌──────────────┐
                                 │ failed     │   │  rolling-back│──► rolled-back
                                 └────────────┘   └──────────────┘
```

- 状态写进 `<dir>/update-journal.json`（**原子写**：temp + `fsync` + `rename`，项目已有 `fsutil` 可复用），字段至少：
  `state / from / to / staged / sha256 / attempts / requested_at / swapped_at / confirmed_at / last_error / by(pid)`。
- **SSE 只用于"下载进度"**（短生命周期）；**换装与重启后的真相从 journal 读**（长生命周期）。新增 `GET /api/update/journal`。

### 3.2 A 方案（P0，低风险，直接消灭本次事故）：把换装交给"独立执行体"

```
artex-rea.exe (旧版)
   ├─ 检测/下载/校验 → updates/staging/<ver>/artex-rea.staged（后缀不是 .exe）
   ├─ 校验 sha256 + 冒烟（子进程带 --self-test，一次性、无网络无端口）
   ├─ 写 journal: apply-requested（含目标版本、staged 路径、sha256）
   └─ 拉起 helper：artex-rea.exe --apply-update <journal>  （detached，独立控制台）
        然后旧版自己优雅退出（exit 75）

helper (artex-rea.exe --apply-update)
   ├─ 等旧版 PID 结束（轮询 + 超时）
   ├─ 锁 journal（跨进程文件锁）→ 加锁成功才动手
   ├─ 重试循环（3~5 次，200ms/500ms/1s）：
   │    rename 当前 → versions/<旧版本>/artex-rea.exe 或 <当前>.old-<ts>   （改名允许）
   │    rename staging → 当前                                              （目标路径已空）
   │    失败 → 回滚 rename
   ├─ 健康门控：起子进程 `当前 -version` 或探 /api/health，**校验版本号 == 目标**
   ├─ journal: swapped / failed(+原因)
   └─ 重新拉起正式进程（或交给 supervisor）
```

为什么这样就"不静默"了：

- helper 是**独立进程**，可以写日志到 `<dir>/logs/update.log`（追加式），旧版退出也不影响它写完；
- journal 是**持久**的，下一个进程（无论新版旧版）都能读到"上次做到哪、为什么失败"，直接喂给 `/api/update/check` 的 `boot_notice`；
- 前端加**看门狗**：`restarting` 状态超过 60s 就轮询 `/api/update/journal`，读到 `failed/rolled-back` 立即显示原因 + 排障指引，不再无限转圈。

### 3.3 B 方案（P2，目标形态）：launcher + 版本目录，换装变成"改一行指针"

```
artex-rea/                        ← 安装根（用户快捷方式/服务指向这里，永不改变）
├── artex-rea.exe                 ← 40 行 launcher：读 pointer → exec 目标版本 → 透传参数/退出码
├── pointer.json                  ← {"current":"2.3.0","previous":"2.2.2"}  原子写
├── versions/
│   ├── 2.2.2/artex-rea-core.exe
│   └── 2.3.0/artex-rea-core.exe  ← 新版本先落盘、冒烟通过再切
├── updates/                      ← 暂存区：只放 .staged/.zip，永不放可直接运行的名字
└── logs/update.log
```

- **升级 = 写 `pointer.json`**（temp+rename）：瞬时、原子、**从不替换正在运行的文件**→ self-lock 问题整体消失；
- **回滚 = 把 pointer 改回上一个版本**，不需要任何文件搬运；
- 旧版本目录保留 N=3 个，磁盘成本可预期；
- launcher 极小、几乎不变（改了它才需要一次传统换装），可以被杀毒软件"记住"；
- 对 Windows 不需要符号链接权限，纯文件指针 + `exec` 即可。

> 代价：多一次进程 exec（几十毫秒）；需要一次性的迁移（把现有 `artex-rea.exe` 变成 launcher 并引入 `versions/`）。所以排在 P2。

## 4. 落地清单（按优先级，全部可静态自检）

### P0-1｜消灭分裂脑：暂存件不可执行、不参与"同族"判定

| 改动 | 位置 | 要点 |
|---|---|---|
| 暂存目录改为 `updates/staging/<ver>/`，文件名 `artex-rea.staged`（**不叫 `.exe`**） | `selfupdate/selfupdate.go#ResolvePaths`、`stage.go#Stage`、`extractBinary` | 双击不会运行；`artex*.exe` 不匹配 |
| **启动守卫**：若 `os.Executable()` 基名含 `.new/.old/.failed/.swap/.staged/.part`，拒绝启动 | `cmd/artex/main.go` 最前面（`Bootstrap` 之前） | 打印明确中文指引 + 写 journal + 非 0 退出；这一条直接封死本次事故 |
| `isOwnedProcess` 收紧为"**恰好是** `artex-rea.exe` / `artex-rea-core.exe`"（白名单，不用前缀通配） | `cmd/artex/boot_windows.go` | 顺带避免误杀 `.old`/`.new`/用户自己的副本 |

### P0-2｜消灭"一次失败永久失败"：备用名唯一 + 清理容忍 + 重试

```go
// 备用名带时间戳，永不复用；清理失败只告警
aside := fmt.Sprintf("%s.old-%d", p.Current, time.Now().Unix())
if err := os.Remove(p.Old); err != nil && !errors.Is(err, os.ErrNotExist) {
    log.Printf("[update] 旧备份仍被占用，跳过清理（不阻断本次升级）：%v", err)   // ← 不再 return
}
if err := renameWithRetry(p.Current, aside); err != nil { return err }        // 3~5 次退避
if err := renameWithRetry(p.Staged, p.Current); err != nil {                  // 失败即回滚
    _ = renameWithRetry(aside, p.Current)
    return fmt.Errorf("安装新版本失败：%w", err)
}
cleanupLater(aside)   // 下次启动扫 *.old-* ，删不掉的留到再下次
```

### P0-3｜消灭"静默"：journal + 落盘日志 + 前端看门狗

| 子项 | 落点 |
|---|---|
| `update-journal.json`（原子写，含 `state/attempts/last_error`） | 新增 `selfupdate/journal.go` |
| 追加式日志 `<dir>/logs/update.log`（同时仍 `log.Printf`） | 新增 `selfupdate/log.go` |
| `GET /api/update/journal` + `/api/update/check` 的 `boot_notice` 改读 journal | `server/update.go` |
| 前端 `restarting` 加看门狗：60s 未变版本 → 拉 journal → 显示失败原因 + "打开日志目录/手动启动"指引 | `update-card.tsx` |
| 失败进度事件也写 journal（SSE 断了也能查） | `updateHub.finish` |

### P0-4｜健康门控：不是"活过 30 秒"，而是"版本对、接口通"

`Settle()` 改为：`GET /api/health` 自检（`version == journal.to` 且 200）→ 写 `confirmed`；N 次不通过 → 自动回滚。运行期不做编译，只做 HTTP 自探，符合本仓库约束。

### P1-5｜跨进程单写者 + 并发保护

`journal` 上加文件锁（Windows `LockFileEx`，Unix `flock`），所有换装/回滚入口先取锁；`updateHub.running` 保留为 UI 层的快速失败，但**不再承担安全职责**。

### P1-6｜信任锚加一道：双源 sha256 交叉校验

`scripts/gen-update-manifest.py` 已经在 `latest.json` 的 `assets[].sha256` 里写了每个 zip 的摘要，但 Go 侧 `selfupdate.Asset` 只有 `Name/URL/Size`——**这个字段被丢弃了**。把它接上：

```go
type Asset struct { Name, URL string; Size int64; SHA256 string `json:"sha256"` }
// Stage: 同时取 SHA256SUMS 与 latest.json 里的 sha256，两者不一致 → 拒绝更新
```

零成本、无发布侧改动，把"单一摘要来源"变成"两个独立来源互相印证"。更彻底的是签名（`SHA256SUMS.sig` / cosign keyless），可排 P2。

### P2-7｜迁移到 launcher + versions/（3.3 B 方案）

一次性迁移 + `pointer.json` + 保留 N=3 + `-apply-update` helper；launcher ≤ 100 行，单测覆盖"指针缺失/指向不存在/版本降级"三种异常。

## 5. 兼容与迁移

**必须兼容一轮旧协议**（当前线上是 v2.2.2，只认 `exit 75` + `artex-rea.new` + `upgrade.json`）：

| 步骤 | 做法 |
|---|---|
| 新版仍能**读**旧 marker/旧 `.new` | `Bootstrap` 先探测旧路径，若存在则走"一次性兼容换装"，成功后把 journal 写成 `confirmed` |
| 新版**不再写**旧路径 | 避免新旧混跑 |
| 遗留文件清理 | 启动时扫 `artex-rea.new.exe` / `.old.exe` / `.failed` / `.swap` / `.new.zip.part`：能删则删，删不掉（被锁）只记 journal |
| 现场已被污染（`.new.exe` 在跑） | 手工步骤：停掉 `.new.exe` → 比对两版 `-version` 决定保留哪个 → 删 marker 与残留 → 用 `start.bat` 启动 → 打开设置页确认 `boot_notice` 为空 |
| 发布侧 | 无强制改动；建议在 Release 说明里保留"请用 start.sh/start.bat 启动"的显式提示 |

## 7. 排障手册（给用户/运维）

```text
症状：点了更新，一直显示"正在重启"
 → 1) 看 <dir>\update-journal.json 的 state 与 last_error（这是唯一权威）
 → 2) 看 <dir>\logs\update.log 的尾部
 → 3) tasklist | findstr artex  → 是否有 .new.exe / .old.exe 在跑
 → 4) netstat -ano | findstr :8787 → 占用者 PID 对应哪个映像
 → 5) 若是 .new.exe 占着：停掉它，用 start.bat 重启，再看设置页的 boot_notice
```

原则：**永远不要手工把 `.new.exe` 改名成 `artex-rea.exe` 顶上**（会绕过校验且留下不一致的 marker）；要么让程序自己换装，要么走"删残留 + 重启"。

## 8. 取舍与建议

| 方案 | 收益 | 成本/风险 | 建议 |
|---|---|---|---|
| **A（P0）** 独立执行体 + 唯一备用名 + journal + 健康门控 + 启动守卫 | 直接消灭本次事故与"永久失败"，改动集中在 `selfupdate/` 与 `update-card.tsx` | 新增 2 个文件、约 300–400 行；需兼容旧 marker | **先做，一个提交** |
| A + 双源 sha256（P1-6） | 信任锚从"单来源"变"双来源互证" | 约 30 行 | 与 A 同批做 |
| **B（P2）** launcher + `versions/` + pointer | 换装变成一次指针写，self-lock 与锁竞争整体消失，回滚秒级 | 一次性迁移、多一层 exec、发布包结构变化 | 作为 v2.3 的目标形态 |

**一句话建议**：别再优化"如何安全地替换自己"，而是**让"自己"不再需要被替换**——先落 A 止血，再走 B 收敛。
