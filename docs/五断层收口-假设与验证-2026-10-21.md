日期：2026-10-21　对应提交：批次 2（B/C/D/E 收口）

## 0. 方法

每条假设写成一句**可证伪**的判断，再去找唯一的证据源（符号级，不引用会漂移的行号）。三种结论：

- **成立**：证据与假设一致，可以直接基于它改代码。
- **修正**：代码事实与假设不符，按事实改设计（文中写明差在哪）。
- **未闭环**：只能由运行期数据判定，列进第 4 节，不假装已验证。

## 3. 未闭环（明确不做/待定）

1. **E 的单写协程 + 批量提交 + 分库**：`AppendActivity` 的返回值是**活动 id**，被流式回放与消息回滚直接消费（`ActivityMeta`、`rollback` 路径），异步批量写入会破坏「写完成即可读 id」的契约。要做必须先把这条链路改成「先分配 id 再异步落库」或「同步写 + 后台合并」，属于独立设计，需要真机测 写 p99 / SQLITE_BUSY / 库增长 后再定，不在本轮硬推。
2. **C 的报告正文强口径**：报告读探索节点（H14），要按复核态过滤需要把报告的数据源换成 `findings` 表，属于报告重构。
3. **D 的历史包效果**：`recent_same_tool` 是否真的降低了重复调用、有没有引入新的误判，只能看运行数据。
4. **F 工具面分组注入**：用户口径是「5 个断层（A–E）」，F 仍不在本轮范围。

## 4. 回归风险提示（交给 CI / 真机）

- `ParseVerdict` 放宽到 3 字段后，**旧提示词**（自定义 `llm_judge_prompt`）仍输出 2 字段 → 兼容；但若自定义提示词要求输出代码块，仍会走 fail action。
- 低置信转人工会让**人工审批队列变长**，这是设计取舍；阈值 0.6 是常量，后续可提到设置项。
- `validation` 默认 `unverified`：**旧库所有发现默认都是未复核**，统计里 `unverified` 一开始等于总量，属于预期。
- `PRAGMA optimize` 失败被忽略（不影响启动），但若驱动不支持该语句，日志里不会有提示——这是有意的静默。

## 6. 批次 4（E 最后落实：观测 + 读池 + 预算）

**E 的验收口径**：worker=8 并发下 `SQLITE_BUSY`=0、写 p99 < 20ms、库增长 < 200MB/h。批次 3 给了「一个写者、一批一次 fsync」，但**没有留下任何可以读出来的数字**——出问题时只能猜。本批次补的是「能看见」，不是「更快」。

| 落地点 | 做了什么 | 为什么是它 |
|---|---|---|
| **只读连接池** | `openSQLite` 在主池之后开第二个池：同一 DSN 追加 `_pragma=query_only(ON)`，上限 3/3；`db.DB.ReadDB()` 统一取用，没有读池（内存库、测试句柄）时回落主池；`server/storage.go#storageCount` 改走读池 | 读语句误落到读路径上会当场报 `readonly database`，而不是悄悄抢写锁；统计/列表/导出不吃写池那 8 条连接。内存库不建读池——`file::memory:` 每个连接都是一个新库，第二个池会看到空库 |
| **写队列观测** | `db.WriteStats`：`batches` / `jobs` / `max_batch` / `last_batch` / `rollbacks` / `queue_depth` / `avg_batch` / `avg_wait_ms`，每批只加一次锁；`/storage/stats` 的 `memory_db.write_queue` 直接返回 | 回答三个具体问题：批量到底攒起来没有（`avg_batch`）、一次写入从入队到提交平均多久（`avg_wait_ms`，写 p99 的上界代理）、有没有在整批回滚（`rollbacks`）。`avg_batch` 只用**提交成功**的批做分母，回滚不稀释它 |
| **缓存预算** | `config/sqlite.go` 的 `cache_size` 由 64MiB 收到 32MiB | 这个 pragma 是**每条连接**的上限，而池是 8 写 + 3 读，64MiB 的最坏上限是 704MB，与「轻量」相悖；32MiB 对应 11 条连接最坏约 350MB，正常只用到工作集那几 MB |

**怎么读这些数字**（贴给运维/自己看的两行结论）：
- `avg_batch ≈ 1` 说明写入速率低于「5ms 一条」，批量没起作用、但也没有代价；`avg_batch` 上去说明窗口凑到了同伴，提交次数随之下降。
- `rollbacks > 0` 不是噪音：批内任一条失败会**整批**回滚（activity 追加可整体重放），这时要么是约束冲突要么是锁超时，`avg_wait_ms` 会同时抬高。

**明确不做：activity 分库。** 三条理由都在代码里：
1. activity 与父表在**同一个事务**里删改——`db/exploration.go:585/598`（删节点同事务删活动）、`db/intent_admission.go:16`、`db/task_archives_restore.go:102`（恢复任务按探索整批删）。SQLite 跨库只有 `ATTACH`，WAL 下不保证跨库原子提交，拆开就要把这些路径改成「两库各自补偿」，错一次就是孤儿行。
2. 62 处读写点里确实有跨表聚合（`db/exploration.go:1316/1338` 把 activity 与探索/节点一起聚合），拆库后必须把这两处改成先查主库再回填，属于重写查询而不是换连接。
3. 本机不允许编译/测试，62 点的机械重构没有验证手段；这类改动必须能跑起来再动。

**替代方案（已具备）**：`activity` 的增长边界目前靠两条既有路径——归档/删除任务时整批删除（`task_archives.go` 的搬迁与清理）、存储页按天数手动清理（`server/storage.go:448`）。若后续要自动保留，先加一个**默认关闭**的 `activity_retention_days` 设置项，再挂后台定时清理；不默认删用户数据。

**回归风险**：只读池在主库打开成功之后才建，失败只打一行日志并回落到主池，不会挡住启动；测试里 `&DB{DB: raw}` 这种句柄 `ReadDB()` 直接返回主池，行为与改动前一致。

## 8. 批次 6（活动保留定档：14 天 + 10 万行）

批次 5 只给了「按天」一个闸门、默认关闭。这一批把它定成**默认生效的双闸门**，并给出定档依据。

| 闸门 | 默认值 | 管什么 | 定档依据 |
|---|---|---|---|
| 保留天数 | **14 天** | 账期：够回放/审计一次任务的完整过程 | 任务的执行轨迹（activity）只在「回看这次怎么打的」时有用；漏洞/资产/证据都不在这张表里 |
| 行数上限 | **100,000 行**（≈200MB） | 体积：再忙的机器也不会把盘吃穿 | activity 单行 ≈1–3KB（summary + detail + metadata）；10 万行落在 100–300MB 区间 |
| 保护期 | **3 天** | 行数闸门不动比 3 天新的行 | 正在看的时间线不会因为「超限」突然缺页 |

两条闸门的关系：先按天数删（只删已结束探索），再按行数裁最旧的（同样只删已结束探索、且早于 3 天）。都走单写协程、每批 5000 行、单轮上限 10 万行，删完 `ReclaimFreePages`。

**为什么不是 30 天 / 90 天**：按 2KB/行估算，30 天在中等强度使用（7k 行/天）≈ 420MB，90 天 ≈ 1.3GB——这对「轻量」是反方向。要长账期就把天数调大，但行数上限会先兜住体积；反之只想要小体积就把行数上限降到 3 万（≈60MB）。

**为什么不是默认关闭**：上一版默认 0（关闭）等于「用户不点就无限增长」。「保底」的定义是不依赖用户操作——所以默认开，但把删除范围限制在**已结束探索的执行轨迹**，且页面上随时可改回 0。

**回归风险**：默认开启意味着升级后第一次跑（启动 3 分钟 + 6 小时间隔）会真的删掉 14 天前、已结束探索的活动行；这是有意为之，页面的「上次运行/上次清理行数/上次按上限清理」三个数值就是用来对账的。

两条结论直接由它得出：

2. `playwright 1.62.0` 已在，`connect_over_cdp` 可用，所以 L1 没有引入任何新的运行时依赖。

## 10. 批次 8（流式输出：把「等 AI 想完」拆成两条链路）

**病灶（只读实测，2026-10-21）**：设置里的「流式输出」开关开了跟没开一样——思考、正文、工具调用都是等模型整轮结束才一次性出现。原因不在开关，而在**两条链路都没接**：

1. `agent/capture.go` 的 `addDelta` 只把增量写进 `tbuf`，遇到 tool 边界 / `KindResult` / 出错才 `flush()` 成一条 `Activity`。所以**库里本来就只有整块**，前端再怎么刷也只能刷到整块。
2. `server/conversation_stream.go` / `exploration/activity/stream` 只推「已落库的 activity」，且只在 `AppendActivity` 之后 `Publish`。整块落库 = 一次推到。
3. 开关只经 `nonStreamingResolver(cfg)` → `SetNonStreaming` → `Provider.Complete`，切的是**HTTP 怎么收包**（SSE vs 一次性 JSON），跟 UI 呈现毫无关系——这就是「开不开都一样」的根因。

**修法：落库口径不动，另开一条「未落库」的实时通道。**

| 层 | 落地点 | 内容 |
|---|---|---|
| 采集 | `agent/live.go`（新）+ `capture.go` | `WithLiveDelta(ctx, fn)` 把接收器挂在 ctx 上；`addDelta` 每来一小段就 `emitLive`，`KindToolUse` 一出现就推 `tool_use`。**同时**继续累积进 `tbuf`，落库口径一字未改 |
| 扇出 | `server/broadcast.go` | `Broadcaster` 增加 `live`/`liveSeq` 两张表与 `SubscribeLive`/`PublishLive`；`liveEmitter` 把逐 token 增量压成**累计全文**帧，**40ms 节流**（约 25 帧/秒）；`tool_use` 帧顺带清空文本缓冲，避免下一轮 thinking 接上一轮 |
| 传输 | `server/server.go` | 活动流 SSE 多收一路 `liveCh`，写成 `event: live` + `data: {...}`。**故意不带 `id:`**——这类帧不进游标，断线重连不会被它污染，也不需要补偿（下一帧是全文） |
| 渲染 | `web/src/components/transcript.tsx` | 新增 `LiveThinking`：默认**只显示一行**（尾部 200 字，前缀 `…`），行内随帧滚动更新，点击展开全文（展开用 `<pre>`，不做上下渐隐）；正文实时块带闪烁光标；工具调用渲染成 `🔧 名称 …` 一行 |
| 归属 | `sessions-tab.tsx` | 新增 `liveFrame` 状态：`es.addEventListener("live")` 收帧；**有新 activity 落库就清空**（避免与已落库的行重复显示）；按 `intent_id` 把帧路由到对应会话，主会话（没有 intent_id）只认 `worker === "chat"` 的帧 |

**开关语义打通**：`agent/worker.go` 新增 `Streaming() = !nonStreaming()`，`server/engine.go` 只在 `worker.Streaming()` 时挂 live 发射器。于是「流式输出」开关第一次同时作用于**两条链路**：关掉 → HTTP 走一次性 JSON，UI 也不再有逐字刷新（回到整块），而不是「UI 装样子」。

**为什么不在 `activity` 表里写 delta**：
- 体积：一次长回答轻松上万帧，`activity` 是主库最大的表，这会把它变成日志流。
- 口径：回滚（按 seq 截断）、校验点（`MaxVisibleActivityID`）、审计对齐都假设「一行 = 一段完整语义」。塞 delta 进去要重写这三处。
- 结论：**实时性放在传输层，不放在存储层**。刷新页面后看到的是整块历史（正确），运行中看到的是逐字（够用）。

**回归风险**：
- 双路渲染的时序：live 块与落库块之间靠「新 activity 到达即清空 liveFrame」切换，最坏会有一帧的重叠/空档（同色同字体，肉眼是「接上了」）。
- `live` 帧不带 `id:`，所以 `Last-Event-ID` 的补偿逻辑完全不受影响；`EventSource` 断线重连后最多丢一帧，下一帧是全文。
- 非流式档位（开关关闭）下**没有** live 帧：这是有意为之，用它来验证开关确实作用到了 UI。
- 正文实时块目前是**纯文本 + 光标**，落库后才走 markdown；流式 markdown 的增量解析（半截代码块/表格）留作后续，不在本次范围。

**本次没做（明确边界）**：正文的流式 markdown 增量渲染；工具结果的 ZCode 式「一行预览 + 按类型折叠」（当前仍沿用既有 `ToolBlock`）；L2 Firefox 加固档与 L3 设置页下载按钮（见 §9）。
