# 五断层收口：只读假设—验证闭环

日期：2026-10-21　对应提交：批次 2（B/C/D/E 收口）
约束：本机不做任何编译/测试/构建；全部结论来自**读代码**与 `gofmt -l/-d` 语法/格式门禁，运行期结论留给云端 Actions 与真机。

## 0. 方法

每条假设写成一句**可证伪**的判断，再去找唯一的证据源（符号级，不引用会漂移的行号）。三种结论：

- **成立**：证据与假设一致，可以直接基于它改代码。
- **修正**：代码事实与假设不符，按事实改设计（文中写明差在哪）。
- **未闭环**：只能由运行期数据判定，列进第 4 节，不假装已验证。

## 2. 批次 2 改了什么

**B 编排（意图粒度）**
- `add_intent` 新增 `expected_evidence`：进意图 payload，worker 收尾与复核都按它判断「算不算完成」。
- planner prompt 增加两条硬口径：每条意图写 `expected_evidence`；单意图最多 5 个执行步骤，超过就拆成多条。
- （硬校验仍是批次 1 的 0 意图契约：0 意图 + 目标未达成 + 无在跑意图 → 补跑一轮。）

**C 验证（复核态进口径）**
- `findingFilterFromQuery` 支持 `validation=verified|unverified`，导出与列表共用同一解析。
- `FindingStats` 增加 `verified` / `unverified` 两个计数，前端可直接展示「报了多少 / 确认了多少」。

**D 审批（置信度 + 最小历史包）**
- 裁决协议增加可选 `confidence`（0–1）；解析器放宽到 2–3 个字段，非法值按「未提供」处理；`confidence` 同时接受 JSON 数字与字符串（模型常给数字），`decision`/`comment` 仍只接受字符串。
- `server/intercept.go`：`allow` 且 `confidence < 0.6` → **转人工**（`ask`），理由前缀 `[低置信放行转人工]`；`deny/ask` 不降级。
- `ReviewInput` 增加 `recent_same_tool`（v4 → v5）：最近 5 次同工具调用的 工具名/状态/一行理由/时间，由 `db.RecentInterceptCalls` 直接从 `intercept_pending` 取，模型无法影响内容。
- 同步改写 `JudgeContextBoundary` 中「不附带历史」那段，明确该字段的作用边界。

**E 承载**
- 启动时对主库执行一次 `PRAGMA optimize`（长期运行的库统计会过期）。
- 批次 1 已加：`cache_size(-64MiB)`、`mmap_size(256MiB)`、`temp_store(MEMORY)`、`VACUUM INTO`。

## 3. 未闭环（明确不做/待定）

1. **E 的单写协程 + 批量提交 + 分库**：`AppendActivity` 的返回值是**活动 id**，被流式回放与消息回滚直接消费（`ActivityMeta`、`rollback` 路径），异步批量写入会破坏「写完成即可读 id」的契约。要做必须先把这条链路改成「先分配 id 再异步落库」或「同步写 + 后台合并」，属于独立设计，需要真机测 写 p99 / SQLITE_BUSY / 库增长 后再定，不在本轮硬推。
2. **C 的报告正文强口径**：报告读探索节点（H14），要按复核态过滤需要把报告的数据源换成 `findings` 表，属于报告重构。
3. **D 的历史包效果**：`recent_same_tool` 是否真的降低了重复调用、有没有引入新的误判，只能看运行数据。
4. **F 工具面分组注入**：用户口径是「5 个断层（A–E）」，F 仍不在本轮范围。

## 4. 回归风险提示（交给 CI / 真机）

- `ParseVerdict` 放宽到 3 字段后，**旧提示词**（自定义 `llm_judge_prompt`）仍输出 2 字段 → 兼容；但若自定义提示词要求输出代码块，仍会走 fail action。
- 低置信转人工会让**人工审批队列变长**，这是设计取舍；阈值 0.6 是常量，后续可提到设置项。
- `validation` 默认 `unverified`：**旧库所有发现默认都是未复核**，统计里 `unverified` 一开始等于总量，属于预期。
- `PRAGMA optimize` 失败被忽略（不影响启动），但若驱动不支持该语句，日志里不会有提示——这是有意的静默。
