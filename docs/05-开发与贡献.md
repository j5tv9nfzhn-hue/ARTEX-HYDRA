#### 开发与发布约定（长期生效 · 最高优先级）

本节优先级高于 `CONTRIBUTING.md` 与 `MAINTAINING.md` 的通用开发说明；冲突时以本节为准。修改本节应与修改 `release.yml` 同等审慎，并在同一个提交内同步。

约定分两类，不要混用：**第 1～6 条**约束「AI 助手 / MCP 客户端在本机工作副本上作业」的行为；**第 7～9 条**（门禁分层、代理、发布）是仓库级约定，对任何执行 `git push`、打 tag 的人与自动化都成立。人类开发者在其他机器上正常开发，仍按 `CONTRIBUTING.md` 的「开发环境」执行本地构建与测试，不受第 2 条限制。

##### 1. 源码唯一位置

项目源码只存在于工作副本 `C:\Users\Administrator\Desktop\ARTEX-HYDRA`（及其远端 `j5tv9nfzhn-hue/ARTEX-HYDRA`）。所有改动直接落在该目录，不另建副本、不在别处「另起一份工程」。

##### 2. 本机不做任何测试 / 编译 / 构建 / 打包

在本机（含通过 MCP shell 间接调用、含写 `.bat` / `.ps1` / `.cmd` 去跑、含用 `docker run` 跑等价命令）：

**禁止**

```text
go build / go vet / go test / go run / gofmt / golangci-lint
npm ci|install|test|run build|run build:static、npx tsc、npx biome、next build
build.sh、dev.sh、任何打包 / 压缩 / 出 zip 的脚本
```

**允许**

```text
读文件、写文件（源码 / 配置 / 脚本 / 文档）、列目录
git status / diff / log / show / ls-files 等只读查看
git add / commit / push / tag（按第 5、6 条的网络与时机规则）
gh 只读查询（run list / release list / api GET）
```

理由：本机是用户的生产机，跑构建会污染工作树、占用 CPU 与磁盘，且与云端环境不一致；云端 Actions 才是唯一的权威构建环境，本机的「跑一下看看」既慢又不能证明发版可用。

**替代手段**：写完回读文件，静态核对 import / 符号名 / 类型签名 / 调用点参数 / 结构体字段 / i18n 键是否存在。宁可写得保守，也不在用户机器上跑命令兜底。

##### 3. 验证由云端承担

| 工作流 | 职责 |
|---|---|
| `.github/workflows/release.yml` | **唯一的构建流水线**：gate（编译/静态）→ frontend → binaries（6 目标）→ release；`workflow_dispatch` 可干跑不发布 |
| `.github/workflows/detections.yml` | 检测规则与指标回归（`push` 时忽略 `v*` tag） |
| `.github/workflows/verification-helper.yml` | 手动触发，单独模块 |

本机的结论只能是「静态看是对的」，不能是「跑通了」。

##### 4. 用静态自检替代编译

提交前逐项核对：

1. 新用的符号是否真实存在（`grep` 定义处，不凭记忆）。
2. 函数签名 / 返回类型 / 错误处理是否与调用点一致。
3. 结构体字段名、JSON tag 是否与前端类型、golden 文件一致。
4. 新增的 `import` 是否齐全，删除代码后是否留下未使用的 import。
5. 新增界面文案是否同时写进 `web/messages/zh.json`，键名一致。可跑 `python3 -I scripts/check-i18n-keys.py` 全量核对（零依赖、只读、不构建）：键缺失在真机上不会报错，只会把**键名**渲染到界面并刷 `MISSING_MESSAGE`，编译与类型检查都发现不了。`t` 由 prop 传进子组件的情况脚本判定不了归属，会列入「跳过」清单而不报错。
6. 改了 `capability` 相关能力项时，同步 `mcp_tools.golden.json` 与计数断言。

##### 5. 网络：访问 GitHub 必须走本地代理 10808

裸直连会稳定超时（约 20 秒后 `Failed to connect to github.com:443`），而 `gh api` 走另一条链路可能仍然可用——**不要**因此误判为「仓库坏了」。

```bat
:: git（按次传参，不写全局 config）
git -c http.proxy=http://127.0.0.1:10808 -c https.proxy=http://127.0.0.1:10808 push origin main
git -c http.proxy=http://127.0.0.1:10808 -c https.proxy=http://127.0.0.1:10808 ls-remote origin refs/heads/main

:: gh
set HTTPS_PROXY=http://127.0.0.1:10808&& set HTTP_PROXY=http://127.0.0.1:10808&& gh run list --limit 6
```

故障处理顺序：

1. 先探测：`curl -x http://127.0.0.1:10808 -sS -o /dev/null -w "%{http_code}" https://github.com`，得 `200` 再 push。
2. 单次 20 秒无响应即判不可达；最多重试 2 次（合计 3 次）。
3. 3 次仍失败 → **停止并如实报告**。不裸直连硬刷、不无限重试、不改端口乱试。
4. **禁止**用 `gh api POST /git/refs` 绕过 push：commit 不在远端时必然 `422 Object does not exist`，还会让远端出现悬空引用。

##### 6. 推送 / 打 tag / CI：发起即返回

- 不阻塞等待、不轮询日志、不盯 Actions 进度、不为「确认成功」反复查询。
- 唯一必须串行的动作：**tag 必须在新 commit 已到远端之后创建**。因此允许 `push → ls-remote 校验 → push tag` 一次性完成，校验通过立即结束。
- 失败信息由用户转述，或按需再改源码；不靠本机复现失败。

##### 6.1 版本号：tag 是唯一真相来源

- tag 形如 `vX.Y.Z`，或四位 `vX.Y.Z.W`（同一 patch 重发微修订时用，如 `v2.5.0.6` 跟在 `v2.5.0.5` 之后）；带 `-rc.1` 之类后缀的 tag 会被客户端判成不可比较、静默禁用一键更新，`release.yml` 直接拦下。
- 全仓只有一条版本线：服务器版（`artex-rea-*`）由 tag 与 `latest.json` 发出，**不得给任何产物族单独起低号**——客户端 `has_update = CompareVersions(当前, 最新) < 0`，低号会让已装高版本的用户判成「已是最新」而静默断掉更新通道，GitHub 的 `/releases/latest` 指针也会被降级包占住。
- 版本只在两处落地，都由 tag 推导：二进制 `-X main.version`（`build.sh` 去掉前导 `v`）与前端静态包的 `NEXT_PUBLIC_APP_VERSION`（`release.yml` 传 `$GITHUB_REF_NAME`、`build.sh` 传 `ARTEX_BUILD_VERSION`）。
- `web/package.json` 的 `version` 只当本地开发占位（semver 不允许四段）；运行期界面版本以 `/api/health` 的二进制版本为准，所以界面显示的号与二进制实际的号永远一致。

##### 7. 门禁分层：编译失败必拦，测试失败不拦

这是本项目对 CI 的核心口径。**产物健康**与**代码健康**是两件事，不能互相绑架。

| 类别 | 判定 | 典型内容 | 失败时的行为 |
|---|---|---|---|
| **编译 / 静态检查** | 确定性 | `go build ./...`、`go vet ./...`、`go vet -tags embedui`、`gofmt`、`golangci-lint`、前端 `build:static`（含 TS 类型检查） | **硬门禁：必须拦住，不得出包** |
| **测试** | 概率性 / 环境相关 | `go test ./...`、`node --test`、`detections/tests` | **信号灯：只报告健康度，不得阻塞打包与发版** |
| **发布流程** | 确定性 | 资产缺失、zip 数量不符、sha256 不匹配、上传失败、草稿未转正 | **硬门禁：必须失败并清理，不留半成品** |

三条红线：

1. **「测试不拦」≠「什么都不拦」。** 编译类、类型类的确定性失败必须拦死；不得把这条口径当作放松门禁的理由。
2. **测试红了要显著标注**（PR / Release 说明里写清楚哪几个包红），不得静默放过；更不得为了让测试变绿而删测试或改断言。
3. **发布失败必须原子回退**：`release.yml` 的 `if: failure()` 会删除草稿、保留 tag，下一次可原地重跑。

当前落地方式：

```text
release.yml（唯一的构建流水线）
gate       tag 格式 + go build + go vet + go vet -tags embedui + gofmt + golangci-lint
frontend   npm ci → npm test / biome（信号）→ build:static（硬门禁，含类型检查）
binaries   6 目标交叉编译 + 头校验 + 打包
release    校验 6 个 zip → sha256sum → 建草稿 → 上传 → latest.json → 转正
           if: failure() → 删除草稿，保留 tag
signals    go test / 语言检查 / 文档链接（continue-on-error，只报告不拦）
```

**为什么只有一份构建**：2026-10-21 之前 `ci.yml` 与 `release.yml` 各有一套前端构建与 Go 编译，两处维护、两套缓存 key，还会出现「ci 绿了但 release 挂了」。现在合并为 `release.yml` 一份；`workflow_dispatch` 用于打 tag 前干跑（不发布）。


**为什么测试不进门禁**：测试失败不代表二进制坏掉；把测试挂在发版链路上，会让一次 flaky 测试挡住整个版本。编译与静态检查才是「产物能不能用」的必要条件。

##### 8. 版本与发布

- **每版必须发 GitHub Release**，tag 与 Release 同名（`vX.Y.Z`，或四段 `vX.Y.Z.W`），二者缺一视为该版未发布。
- **第四段用于同一 patch 的重发**：`v2.4.0` 修好后又必须换一个 tag 时用 `v2.4.0.1`，不占 patch 位；跨 patch 的正常迭代仍用 `vX.Y.Z`。四段与三段按数字逐段比较（`2.4.0 < 2.4.0.1 < 2.4.1`），客户端更新检测两种都认。
- 版本被删除后**重发沿用同一版本号**，不递增；前提是新 commit 已经成功推到远端。
- 更新源白名单只有 `j5tv9nfzhn-hue/ARTEX-HYDRA`：`selfupdate` 只接受该仓库的 Release，且保留**白名单 + SHA256 双闸门**。`jiwoochris/*`、`Autumn-27/artex` 已彻底移除，不得再进入检测或下载链路。
- 自动更新（安装）**默认关**；自动检测默认开；两者都要有开关，且状态可持久化。
- **发布说明必须写全量变更**：由 `scripts/gen-release-notes.py` 从 git 历史按类型分组生成，不再使用 `gh release create --generate-notes`（它只汇总 PR 标题，直接提交的改动会全部丢失）。正文上限 8 KB——它会进 `latest.json`，客户端每次检测都要下载。
- **产物必须单一**：`latest.json` 的 `assets[]` 是客户端的**授权来源**——`selfupdate.AssetName()` 按 `artex-rea-<ver>-<goos>-<goarch>.zip` 拼名字，再用 `FindAsset` 精确匹配。清单里混进别的产物族虽不会被误装，但等于承认它"也是本仓库的正式发行物"，下游任何按前缀或模糊匹配的消费方都会被带偏。因此生成端用白名单硬拒绝（见第 8 节下方的「产物单一性」表），不做静默过滤。
- 一次 tag 推送只应产生 **1 个**发布 run：只保留一个构建工作流后，一次 tag 推送只会产生 `release.yml` 这一次运行；`detections.yml` 用 `tags-ignore: ["v*"]` 排除 tag。

##### 9. 提交粒度

- 一次语义完整的改动合成**单个提交**，提交信息用中文，写清「改了什么 / 为什么 / 影响面」。
- 不提交构建产物（`dist/`、`server/webui/dist/`、`web/out/`）、不提交本地配置与密钥。
- 提交前默认执行 `git status` 与 `git diff --stat` 复核，确认没有夹带无关文件。

##### 10. 常见误判对照表

| 现象 | 真实原因 | 正确做法 |
|---|---|---|
| `git push` 20 秒后 `Failed to connect to github.com:443` | 没走代理 | 按第 5 条加 `-c http.proxy=...:10808` |
| `git push` 返回 `Empty reply from server` | 代理链路抖动 | 换代理参数重试一次；仍失败则报告 |
| `gh api POST /git/refs` 返回 `422 Object does not exist` | commit 还没推到远端 | 先 push，校验 `ls-remote` 后再建 tag |
| 首页 404 | 构建没带 `-tags embedui` | 那是构建参数问题，不是代码问题（见「构建与产物」） |
| CI 红但 Release 正常出包 | 红的是 `signals`（测试信号） | 属预期行为，按第 7 条处理 |
| `gate` 红、无 artifact | 编译或静态检查失败 | 硬门禁生效，必须修代码 |

### 本地化原则

目标是保留 [Autumn-27/ARTEX](https://github.com/Autumn-27/ARTEX) 的技术行为，同时将项目自有韩文统一为简体中文。上游原分支曾记录无法公开访问，保留链接用于归属，不保证可用性。

- **保留推理语义。** `agent/promptcatalog.go` 与 `agent_prompts` 的原有中文行为正文不作无关翻译；角色、范围、工具边界不能因语言重构改变。其他项目自有韩文提示、说明和注释仍应译为简体中文。
- **明确用户输出语言。** `report_finding`、`record_fact`、最终报告、对话默认中文，`agent/prompt.go` 的 `langDirective()` 在角色 system prompt 末尾追加约束；收尾也遵循选定语言。
- **协议与原始材料不改写。** 命令、payload、API/JSON 字段、枚举、工具名、SQL、URL、用户输入、原始日志和外部供应商诊断保持原样。
- **中文作为唯一词库。** UI 使用 `web/messages/zh.json` 的稳定消息键（仓库只有这一份词库，`web/src/i18n/config.ts` 的 `LOCALES` 只含 `zh`）；历史 ko/en/es 配置一律归一回退为 zh。提取脚本中残留的外语输出路径属历史遗留，不构成新的界面语言选项。
- **兼容旧配置。** ko 归一为 zh，空值或未知值按各层既定优先级回退；不把未知环境变量误当作有效值屏蔽文件配置。
- **格式与结构必须保留。** `%s/%d/%v/%w`、ICU 参数、模板占位符、Markdown 结构及用于解析的审批标记需同步前后端和测试。
- **输出约束是提示而非硬过滤。** 模型可能混入技术英文或受角色影响；不能为了“纯中文”破坏代码或证据。模型端到端质量需在授权沙箱独立验证，不能仅凭构建成功推断。
- **禁止新韩文残留。** `scripts/check-language.py` 同时检查源码、注释、词库、脚本、配置说明和文档；允许中文，不能沿用旧的“禁止 Han”门禁。

上游同步、词库提取与漂移检查见 [MAINTAINING.md](06-维护与发布.md)。

### 开发环境

> **AI 助手 / MCP 代理在本机作业时不执行本节任何构建命令**，其作业边界见
> [README.md 的「开发与发布约定」](05-开发与贡献.md#开发与发布约定长期生效--最高优先级)；人类开发者在自己的环境按本节执行。

Go 后端可内嵌 Next.js 静态前端，数据库为 **SQLite**（单文件，无需安装、无需服务）。涉及 `report_finding.traffic_refs` 或报告自动绑定时，先阅读 [README.md 的「安全设计要点」](02-系统架构.md#安全设计要点)与「历史文档归档索引」。

#### 要求版本

- Go 1.26 或以上，以 `go.mod` 为准。
- Node 22 LTS 或更新版本；Node 类型擦除测试至少需要 22.6，与 CI 使用 Node 22 一致。
- Docker（可选）：用于可复现的依赖构建环境；数据库测试已不需要容器（各包自带临时 SQLite 库）。

#### 后端（Go）

```bash
go build ./...
go vet ./...
go test ./...
```

没有本地 Go 时可用 Docker，named volume 保存模块、编译缓存：

```bash
docker run --rm -v "$PWD":/src -w /src \
  -v artexko-gomod:/go/pkg/mod -v artexko-gocache:/root/.cache/go-build \
  golang:1.26 sh -c 'go build ./... && go vet ./... && go test ./...'
```

##### 数据库测试（SQLite，无需外部服务）

数据库相关包（`agent`、`config`、`db`、`evidence`、`llmrec`、`server` 等）的测试在各自的包里创建**临时 SQLite 库**（各包 `TestMain` 把临时库路径写入 `ARTEX_SQLITE_PATH`，复用与生产相同的 DSN/pragma 契约），不依赖任何数据库服务，跨包也没有共享库与全局锁；CI 同样没有独立的数据库 job。显式配置失败必须报错，不允许静默跳过：


### 贡献流程

1. 大改动先开 Issue 协调方向；拼写、链接、明确缺陷可直接提交 PR。
2. 在自己的工作分支完成改动，遵循所在开发环境的分支约束。
3. **实际运行相关验证并记录边界。** Go 运行 build/vet/test（数据库测试已内置于各包、无需外部服务）；Web 运行 Node 回归、Biome 与静态构建。无工具、依赖无法获取、SKIP 或仅解析源码，均应明确标记，不得当作完整通过。
4. 任何自有文本改动后运行语言检查；文档改动运行内部链接检查。锚点按 GitHub slug 计算，修改标题时必须同步引用。

   ```bash
   python3 -I scripts/check-language.py --source
   python3 -I -m unittest discover -s scripts/tests -v
   python3 -I scripts/check-doc-links.py
   # 在 web 静态构建后执行
   python3 -I scripts/check-language.py --web
   ```

5. 使用 [PR 模板](../.github/PULL_REQUEST_TEMPLATE.md)说明内容、原因、执行命令与结果；UI 改动附截图并注明演示数据。
6. 用户可见改动在 [CHANGELOG.md](08-变更日志-en.md) 的 Unreleased 中记录。纯内部重构、测试可酌情省略。

### 检测规则与测试贡献

[`detections/`](../detections/) 提供 Sigma、Suricata、MITRE ATT&CK 层、指标及可复现测试。八类规则测试与额外门禁机械执行以下契约：

- **每个指标必须有可观察的源码依据。** 字符串、User-Agent、行为阈值不可猜测，注明来源，例如 `artex-enrich/1.0` 来自 `enrich/enrich.go`。[指标测试](../detections/tests/indicators/)要求源码与规则持续一致；CSV 改动必须同步 [MISP 事件](../detections/indicators/artex_indicators.misp.json)，[MISP 测试](../detections/tests/misp/)逐行比较并由 pymisp 验证格式。
- **诚实说明局限。** Sigma `description` 和 Suricata 注释说明漏报、误报；泛化行为（如破坏性命令）不是 ARTEX 专属指纹，单次命中不能完成归属判断。
- **通过静态验证。** Sigma 使用 `sigma check --validation-config detections/tests/sigma_lint/validators.yml`，不仅是默认核心验证器；标题、字段、日志分类、引用也需符合 SigmaHQ。四项单仓库不适用的例外及理由在 validators.yml 中。Suricata 须通过 `suricata -T`。
- **附可复现测试。** 输入确定性生成，不提交 pcap 等二进制产物；版本无关的触发、无误报属性使用精确断言，随版本变化的计数采用下限并注明基线。新增关联规则须在[后端可移植性测试](../detections/tests/sigma_backends/)验证，与[规则支持矩阵](04-防御与检测.md#随仓库发布的检测规则)一致。
- **同步 ATT&CK。** `attack.*` 标签与 [Navigator 层](../detections/attack/artex_navigator_layer.json)技术、分值双向一致，不增加规则不存在的推测技术。
- **仅提供防御与检测资料。** 不接受帮助未经授权攻击的利用步骤或规避检测教程。

```bash
detections/tests/sigma/run.sh           # 结构、转换与指标保留
detections/tests/sigma_match/run.sh     # 恶意事件触发，正常事件静默
detections/tests/sigma_lint/run.sh      # SigmaHQ 验证器与基线
detections/tests/sigma_backends/run.sh  # 关联规则后端支持
detections/tests/suricata/run.sh        # 合成 pcap 与告警断言
detections/tests/attack/run.sh          # 层与规则双向一致
detections/tests/indicators/run.sh      # 指标与源码一致
detections/tests/misp/run.sh            # CSV/MISP 同步与格式
```

[run-all.sh](../detections/tests/run-all.sh)按 CI 顺序执行全部套件，单项失败仍继续汇总，任意失败最终返回非零；另执行 harness 同步、triage 自测和防御内联模板门禁。测试只需 Docker，不向仓库写入生成产物。

[检测 CI](../.github/workflows/detections.yml)在规则、层、指标以及其来源文件变化时触发，包括 `enrich/`、`selfupdate/`、`guard/`、`db/`、`cmd/artex/main.go`，防止上游改变 User-Agent、标记、端口或 schema 后资料过期。

规则依据、局限见 [detections/README.md](04-防御与检测.md#随仓库发布的检测规则)，断言与执行方法见 [detections/tests/README.md](04-防御与检测.md#随仓库发布的检测规则)。

#### 构建与产物

| 场景 | 命令 | 说明 |
|---|---|---|
| 日常开发（后端） | `go run ./cmd/artex` | 不含内嵌前端；前端另起 `cd web && npm run dev`。`dev.sh` 一键起前后端 |
| 日常开发（前端） | `cd web && npm run dev` | `/api` 代理到后端 8787 |
| 正式构建（当前平台） | `./build.sh` | 先构建前端再编译；需 Node.js/npm 与 rsync |
| 正式构建（指定目标） | `./build.sh --target windows/amd64` | 支持 linux、darwin、windows 目标 |
| 发布打包 | `./build.sh --release` | 构建三端默认目标（linux/darwin/windows × amd64/arm64）并产出 zip |

编译标志（`build.sh` 固定）：

```text
CGO_ENABLED=0 GOOS=<os> GOARCH=<arch> \
go build -tags embedui -trimpath \
  -ldflags "-s -w -buildid= -X main.version=<版本>" \
  -o dist/artex-rea-<os>-<arch>/artex-rea        # Windows 目标为 artex-rea.exe
```


- `-tags embedui`：启用 `server/webui_embed.go`，把 `server/webui/dist` 编进二进制。**默认构建走 `server/webui_stub.go`，首页返回 404**——这是「忘了带 tag」最常见症状。
- `-trimpath` 去本地绝对路径保证可复现；`-ldflags "-s -w -buildid="` 去符号去 buildid；`-X main.version=` 默认取 `git describe --tags --always --dirty`（去 `v` 前缀），可用 `ARTEX_BUILD_VERSION` 覆盖。
- UPX 默认关闭（`ARTEX_COMPRESS=off`）；`--upx` 强制（缺 upx 直接失败）；`ARTEX_COMPRESS=auto` 缺 upx 时保留未压缩二进制；macOS 目标自动追加 `--force-macos`。

前端静态导出：

```text
cd web && npm ci && npm run build:static   # 产出 web/out
rsync -a --delete web/out/ server/webui/dist/
```

`build.sh` 自动完成同步；`release.yml` 的 `frontend` job 用 `cp -a` 等价操作。`server/webui/dist/` 是生成目录，不手工维护。

产物清单：

- 服务器版单目标：`dist/artex-rea-<os>-<arch>/artex-rea`（Windows 为 `artex-rea.exe`；可用 `ARTEX_OUTPUT`/`ARTEX_OUTPUT_DIR` 改路径）。
- 服务器版发布包（`--release` 或 `ARTEX_PACKAGE=1`）：`dist/artex-rea-<版本>-<os>-<arch>.zip`，内含 `artex-rea`/`artex-rea.exe`（内嵌前端、去符号）、`start.bat`/`start.sh`（启动脚本）、`skills/`、`config.example.json`、`README.md`。
- `dist/SHA256SUMS`：只对**本次构建实际打出的那几个包**求校验和，不扫 `dist/` 目录。目录里若残留别的产物族（历史桌面端、手工放进来的包），`build.sh` 直接报错要求先清理——用通配求校验和等于给脏产物盖章。
- CI（`release.yml`）发布服务器版六端 zip。

**产物单一性（只有一条产物线）**：本仓库的正式发行物有且只有 `artex-rea-<版本>-<os>-<arch>.zip`（Linux/macOS/Windows × amd64/arm64，共 6 个）加 `SHA256SUMS`、`latest.json`。这条约束在三个环节各有一道闸，任一处发现别族产物就**拒绝发布**，而不是过滤后继续：

| 环节 | 位置 | 行为 |
|---|---|---|
| 求校验和 | `build.sh` `write_checksums()` | 只认 `PACKAGED_ARCHIVES`（本次真正打包的目标）；目录里多出的 zip 直接 `die` |
| 上传 | `.github/workflows/release.yml` | 上传前先校验 `dist/` 只含六端包，再逐名上传，不用 `dist/*.zip` 通配 |
| 生成清单 | `scripts/gen-update-manifest.py` | `expected_assets()` 白名单对账；多余包、缺平台包、`SHA256SUMS` 混入别族条目，全部 `return 2` 拒绝 |

运行时文件落点：

- **配置**：`ARTEX_CONFIG` > 当前目录 `config.json` > 可执行文件旁 `config.json`（先存在者优先）。
- **基目录 `config.BaseDir()`**：可执行文件所在目录；`go run` 的临时/缓存二进制会被识别并回退到当前工作目录。
- **SQLite**：`ARTEX_SQLITE_PATH` > 配置 `database.path` > 配置目录 `artex.db`。连接约定见 `config/sqlite.go`（WAL、busy_timeout、`synchronous=NORMAL`、`foreign_keys`、`_texttotime`、`_txlock=immediate`）。
- **数据目录**：`--data`，默认 `BaseDir()/data`；内含 `tasks/<任务ID>/`、`transcripts/`、`.delete-staging/`。
- **技能目录**：`ARTEX_SKILL_DIR` > 配置 `skill_dir` > `BaseDir()/skills`。
- **密钥**：`jwt.key` 与凭据密钥位于可执行文件旁，不在可浏览的 `data/` 内。
- **单次模式（`-reset-password`）**：离线重置管理员密码后退出——不占端口、不跑自更新、不起后台 worker，只打开 SQLite 重写密码哈希（`reset-password.sh` 为其封装）。

启动与一键更新：`start.bat`（Windows）/`start.sh`（Linux、macOS、Docker ENTRYPOINT）是推荐入口。

| 退出码 | Windows `start.bat` | `start.sh` |
|---|---|---|
| 0 | 正常停止（Ctrl-C、页面「停止」），窗口关闭 | 正常停止，脚本结束 |
| 2 | 端口被占用：打印占用端口与处置办法，**不重试**，留住窗口 | 同左（不重试，直接退出） |
| 75（`selfupdate.ExitRestart`，EX_TEMPFAIL） | 已把重启交给新进程/上层，脚本不干预 | 立即重新拉起 |
| 其他 | 异常退出：留住窗口给用户看报错 | 1、2、4…秒退避重启，最多 60 秒 |

重启逻辑在 exe 里：更新或回滚装好后先写 `updates/restart.request` 意图，入口监护循环只在意图存在时把新版本拉起来（5 次/5 分钟封顶），用户按 Ctrl-C 退出的进程不会被复活。`start.bat` 因此**不再自己循环**——「异常就重试」会把一次端口冲突放大成无限重启，也会在 Ctrl-C 时弹出 `Terminate batch job (Y/N)?`。

一键更新链路：旧版进程经 `/api/update/apply` 下载并校验新版本 → 暂存更新包 → 写 `updates/restart.request` 并退出 75 → 入口监护循环把进程拉起 → `selfupdate.Bootstrap` 校验并冒烟测试新二进制 → 换装 → 再退出 75 → 拉起新版。下载、SHA256 校验与版本替换全部在 Go 的 `selfupdate` 包中实现，脚本只负责把程序放到前台。
