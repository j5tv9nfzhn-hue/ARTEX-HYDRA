# 成本效率优化实施记录（批次 E）

回答「这一轮为省 token、让产出可见、让操作顺手改了什么、为什么、落在哪里」。对应三个反复出现的用户痛点；代码注释里本轮代号为**批次 E**。需要在 norma SDK 上游完成的优化单独整理在 [norma-SDK优化补丁清单](norma-SDK优化补丁清单.md)，本文不重复展开。改动的逐条依据以源码为准，本文只做导航与背景说明，不贴代码。

## 背景：三个痛点

1. **Token 消耗高。** 每轮/每次唤醒都会把规划态势、历史工具输出与摘要正文整段重复发给模型：输入 token 随对话与任务长度放大，工具输出一留就是几千到上万字符，而且整机没有预算概念——一个任务跑多久、花多少，没有上限也没有归因。
2. **长时间看不到有用价值。** 任务在动，但看不出产出：第一个漏洞多久出现、每小时能出多少、是不是卡在等人工审批，页面上没有稳定指标；`model_error` 收场后意图白丢，已投入的路线不会重试。
3. **不高效、不顺手。** 想给运行中的意图纠偏只能等它跑完或杀掉重来；定时触发器可以配到秒级，每个 tick 触发一整轮 LLM + 工具会话，用量会无声放大；通知只覆盖漏洞事件，任务结束/等待审批这类「人必须知道」的事项反而不推；回滚文案的承诺大于实际能力（回滚不会撤销目标侧的副作用）。

## 改动清单

> 原则：**工具取数路径保持全量**（`graph_overview` / `list_*` / `node_detail` / `list_assets` 想查随时查）；被收紧的只有**每轮/每唤醒自动注入**的部分——这些内容重复计费，是输入 token 的大头。

### 1. 自动注入侧瘦身（输入 token）

| 改了什么 | 为什么 | 落点模块 |
|---|---|---|
| planner 每轮态势 JSON 收紧列表条数（open_intents 30、最近完成意图 8、finding 8、fact 12、cold digest 8、goal 30、hint 20），并加 16KB 字节硬上限；超限时按优先级逐键装填、追加截断说明 | 每轮重复携带；截断的都是「最新一窗」，更早/更全用工具翻页查 | `agent/prompt_slim.go`（planner 注入路径） |
| worker 首消息概览加 12KB 上限、cold digest 收紧到 8 条；worker system 的「意图原文 + 锚定资产」块 8KB、锚定资产最多 30 条 | 每次 run 都带、每条意图都重复；更全字段用资产工具查 | `agent/prompt_slim.go` |
| cold digest 正文单条 600 字符（保留首尾、中段省略，完整内容 `expand_digest(id)` 展开）；planner 注入里的触发消息单条 2048 字节 | digest 正文被 planner 每轮 + 每个 worker 首消息重复携带，是正文放大的主要来源；触发消息来自外部数据，不设限时一条几十 KB 的结论会撑爆每轮输入 | `agent/prompt_slim.go` |
| 压缩摘要生成侧输出上限收紧到 800 token（注入侧另有 600 字符/条的兜底） | 先限长生成、再从注入端截断，双保险 | `agent/compaction.go` |
| 工具输出进入对话历史的字符上限 30000 → 12000（SDK 默认 30000） | 历史里的旧工具输出每轮都会重发；超限部分不丢——全文落盘到 run 的 ToolOutputDir，历史只留头部 + 落盘指针，可用 Read/Bash 重读 | `agent/assembly.go`（映射 agentcore 的 MaxToolOutputChars） |
| system prompt 整段进 Anthropic 缓存（缓存断点 = 整段 system；没有 deferred 工具块时也整段缓存） | 原来只有静态前缀进缓存，整段缓存后 planner/worker/chat 的 system 在缓存区间内跨轮复用，首轮 1.25x 写入即回本 | `agent/deferred.go` |
| planner 心跳空转跳过：心跳到点、无触发消息、无图变更、且仍有在跑意图时，跳过整轮 planner LLM | 原行为心跳到点即烧一整轮；任务无变动时每 10 分钟重复计费 | `server/engine.go` |

### 2. 任务级 Token 预算（硬闸）

| 改了什么 | 为什么 | 落点模块 |
|---|---|---|
| 新增设置 `default_task_token_budget`（0=不限）：新建任务不填预算时取它；任务表新增 `token_budget` 列，可逐任务覆盖 | 让「一个任务最多花多少」可配置、可逐任务调整 | `server/manager.go`、`db/tasks.go`、创建任务接口 |
| 引擎在每次 run（worker 意图运行 / 规划轮）收尾检查该任务累计 input+output 用量，达到预算即自动暂停（`paused_by_token_budget`）并在活动流留痕；恢复后继续累计 | 收尾时读数必然包含刚结束这一 run 的全部消耗，且不打断进行中的 LLM 调用；先落库再停引擎，不会出现「内存已暂停、UI 仍显示运行」 | `server/engine.go`（checkTokenBudget）、`db/llm_usage.go`（TaskTokenTotal） |

### 3. LLM 重试与意图重跑的成本导向收敛

| 改了什么 | 为什么 | 落点模块 |
|---|---|---|
| `model_error` 收场的意图重跑默认 4 次、硬失败 2 次，指数退避 3+6+12+24≈45 秒 | 每次重跑都是一整轮 LLM + 工具调用；上限压到「扛过短时抖动」与「不把抖动放大成烧钱循环」之间，更长的大面积故障留给用户观察后手动重跑 | `server/engine.go` |
| 新增设置 `llm_retry_policy`（JSON）：五层重试（connect / empty / stream / breaker / intent）的次数与间隔集中配置；`attempts`：0=内置默认、-1=关闭、>0=次数；`interval_ms`：0=原有退避、>0=固定间隔 | 原来次数/间隔写死在代码里，不同渠道需要不同策略；配置带钳制（attempts ≤20、interval ≤1 小时），手误不会把抖动放大成永久循环 | `db/llmretry.go`、`server/engine.go` |
| 单个 LLM profile 可覆盖 connect / empty / stream 三层 | 个别渠道特别不稳时只调该渠道，不动全局；未填字段仍继承全局策略 | LLM profile 的 `retry` 字段（`db/config.go`） |

### 4. 价格表与费用视图

| 改了什么 | 为什么 | 落点模块 |
|---|---|---|
| 新增设置 `price_table`（JSON）：模型名子串 → `{input, output, cache_read, cache_write}`，单位 USD/百万 token | 各渠道/账号折扣千差万别，不做内置价目目录；让用户填自己的实际价格 | `server/pricing.go` |
| 读时计价：费用在读取用量/成本视图时按当前价格现算，不落库 | 调价后历史 token 立即按新价重算，无需迁移，也不产生「写入价/当前价」两套口径 | `server/pricing.go`、用量与成本视图 API |
| 匹配取最长子串（`claude-opus` 优先于 `opus-4`）；写入时校验（非法 JSON / 负数 / 空 key → 400）；读取时坏配置降级为「不算钱」 | 更具体的配置覆盖更宽的；坏配置绝不能把已有的 token 视图打崩 | `server/pricing.go`、`PUT /api/settings` |

### 5. Token 归因与进度指标

| 改了什么 | 为什么 | 落点模块 |
|---|---|---|
| 每次 LLM 调用落 `llm_usage` 账本：任务、意图、worker 泳道、profile、模型、延时、token 四档（input/output/cache_read/cache_write）、状态 | 预算硬闸、费用视图、按 profile/模型汇总共用这份「这笔消耗属于谁」的账本 | `llmrec`（WithTaskID / WithWorker）、`agent/runinfo.go`、`db/llm_usage.go` |
| 任务列表/详情新增进度指标：`first_finding_ms`（首个发现用时）、`findings_per_hour`（产出速率）、`pending_approvals`（等待人工审批数，>0 显示「等待审批」徽章） | 正面回答「长时间看不到有用价值」：产出速度与是否卡审批直接可见 | `server/dto.go`、`db/exploration.go`、`server/server.go` |

### 6. 触发器与通知护栏

| 改了什么 | 为什么 | 落点模块 |
|---|---|---|
| 定时触发器最小间隔 60 秒：创建/更新低于 60 秒直接拒绝；存量低于下限的行按 60 秒调度并只告警一次（不改用户数据） | 秒级轮询会在每个 tick 触发一整轮 LLM + 工具会话，用量无声放大 | `server/triggers.go`（创建/更新校验）、`server/scheduler.go`（调度兜底） |
| 预置「报告撰写」（reporter）agent 的 finding 触发器默认关闭，描述中明示成本 | 「发现即写报告」= 每个 finding 新起一整会话；成本敏感场景由用户按需开启 | `server/orchestration.go` |
| 通知新增任务级事件 `task_status_changed`（完成/失败/超时/暂停）与 `approval_pending`（等待人工审批）；存量渠道默认关、新建渠道默认开；任务级事件跳过 `min_severity` 级别门 | 这两类事件「人必须知道、不看页面任务会一直卡着」；但替存量渠道默认打开会瞬间改变行为，所以 opt-in 不迁移；任务级事件没有级别概念，过级别门会被静默挡掉 | `notify/notify.go`、`notify/filter.go`、`server/notify_api.go` |

### 7. 人工干预与诚实文案

| 改了什么 | 为什么 | 落点模块 |
|---|---|---|
| steer 纠偏：把人工指令投递给正在运行的 Worker 意图，不暂停、不重跑、不改变意图状态；Worker 在下一步工具调用前收到并重新规划 | 原来想给运行中的意图纠偏只能等它跑完或杀掉重来 | `server/intent_intervention.go`（`POST /api/tasks/{id}/intents/{iid}/steer`）、前端任务会话页 |
| 回滚文案诚实化：检查点回滚明确「只恢复平台侧记录，不撤销已在目标系统产生的副作用」；更新回滚明确「数据库结构不会回退」 | 原文案承诺大于实际能力，容易被误读为会撤销攻击副作用/回退数据库 | `web/messages/zh.json` |

## 配置指南

以下都属于运行时可改、无需重启的配置（系统配置页写入 settings 表）：

| 配置键 | 名称 | 类型 | 默认 | 说明 |
|---|---|---|---|---|
| `default_task_token_budget` | 新建任务默认 Token 预算 | 整数 | `0`（不限） | 新建任务不填预算时取它；累计 input+output 达到后任务自动暂停（`paused_by_token_budget`），恢复后继续累计 |
| `price_table` | 模型价目表 | JSON 字符串 | 空（只显示 token，不算费用） | 形如 `{"模型名子串":{"input":…,"output":…,"cache_read":…,"cache_write":…}}`，USD/百万 token；最长子串匹配；读时计价，改价立即对历史生效 |
| `llm_retry_policy` | LLM 重试策略 | JSON 对象 | 空（各层内置默认） | `connect`/`empty`/`stream`/`breaker`/`intent` 五层；`attempts`：0=默认、-1=关闭、>0=次数（≤20）；`interval_ms`：0=原有退避、>0=固定毫秒（≤1 小时） |
| agent 触发器 `interval_sec` | 定时触发间隔 | 整数（秒） | `0`（不定时） | 最小 60；创建/更新低于 60 秒被拒绝；存量低于 60 秒按 60 秒调度并告警一次 |
| 通知渠道 `filter.on_task_status` | 接收任务状态事件 | 布尔 | 存量渠道 `false`；新建渠道 `true` | 任务完成/失败/超时/暂停时推送；opt-in，存量渠道不迁移 |
| 通知渠道 `filter.on_approval` | 接收等待审批事件 | 布尔 | 同上 | 工具调用在等人审批时推送；不受 `min_severity` 级别门限制 |
| reporter 触发器 `enabled` | 发现即写报告 | 布尔 | `false` | 开启后每个 finding 新起一整会话写详细报告；成本敏感建议按需开启 |
